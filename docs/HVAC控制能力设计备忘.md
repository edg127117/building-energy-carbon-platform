# 未来 HVAC 控制能力设计备忘

## 1. 状态

中央空调 V1 只采集、处理、计算、查询和发布数据，不提供控制能力。本备忘只
记录未来设计约束，不包含可执行 Controller、Service、数据库脚本、MQTT 下行
主题或占位算法。旧电表控制实现只保留在 Git 历史中，不得恢复为 HVAC 控制。

## 2. 必须满足的边界

- 控制功能必须有部署级开关，默认关闭；关闭时不注册控制入口、后台扫描或协议连接。
- 目标设备必须来自 `biz_equipment`，并校验当前用户的建筑范围和设备控制能力。
- 指令使用有类型 DTO，明确参数单位、范围、精度、前置状态和互斥条件。
- 业务 Service 只负责编排、校验、审批和状态机，不硬编码 MQTT、Modbus、
  BACnet 或厂家 API。
- 协议下发通过独立 Adapter；每个 Adapter 明确连接、超时、重试和失败影响。
- 每条指令必须有全局唯一追踪号、创建人、审批人、目标、参数、协议和完整审计记录。
- 状态机至少区分待审批、已拒绝、待下发、已下发、已确认、执行失败和超时；
  ACK 必须关联追踪号，不能把“发送成功”当作“设备执行成功”。
- 下发前必须校验安全联锁、设备能力、当前运行状态和并发冲突；失败默认阻断，
  不得静默降级。
- 多实例部署时必须设计幂等领取和并发控制，不能依赖单机定时任务假设。
- 自动化测试使用 Fake Adapter 和测试专用配置，不连接真实楼宇设备。

## 3. 单独设计时必须回答的问题

1. 哪些 HVAC 设备和动作允许控制，能力模型如何表达？
2. 建筑业主、能效管理方和平台管理员分别具有什么申请、审批和执行权限？
3. 安全联锁、人工确认、紧急停止和回滚策略是什么？
4. 各协议 ACK、超时和设备实际状态回读如何统一？
5. 指令审计保存多久，如何关联告警、工单和调适报告？
6. 如何在专用测试环境完成硬件在环和故障注入验收？

上述问题形成独立设计并通过安全评审前，不得新增可执行控制代码。
