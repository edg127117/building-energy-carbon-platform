## 正常容量与积压测量

正常容量矩阵为 `12/96/500 条快照 × 1/4/8/16 并发`，每组 16 次请求，共 12 组、192 次，均返回 HTTP 200 和完整结果。合成负载包括外购电力与热力，固定燃烧算式另由既有核心测试覆盖；本结果不声称覆盖全部真实燃料组合。

| 单请求快照数 | 客户端并发 | 本组最大响应时间 |
| --- | --- | --- |
| 12 | 16 | 228.1 ms |
| 96 | 16 | 742.3 ms |
| 500 | 16 | 2844.6 ms |

全部组合观测到 HTTP 工作线程峰值 8、碳业务数据库连接峰值 4、等待连接线程峰值 5；各组结束时等待数为零。累计 120,576 次 JDBC 执行，单次 SQL 最大 196.6ms、借连接最大 181.5ms。等待连接确实发生，不能表述为“永不堵塞”。每组只有 16 个样本，所记录的 p95/p99 实际等于该组最大值，不作统计 SLA 推断。

冻结前积压用例：100 条持久化变化合并为 12 栋建筑 × 2 年 = 24 项，受单批 10 项上限约束拆成 3 批。分析、执行和审批发布合计约 4736ms；自审、无建筑权限审批均被拒绝，授权人审批后 24 个候选发布、24 个旧结果变为 `SUPERSEDED`。此用例先集中执行影响分析再启动工作线程，证明冻结前归并和后续审批，不替代真实调度入口的归并窗口验证；后者仍有下表中的丢变化缺陷。

## 已复现的阻断

| 问题 | 原始观测 | 设计要求 |
| --- | --- | --- |
| 查询/总超时 | 真实 InnoDB 行锁阻塞 4 秒，2 秒截止请求仍等待约 4 秒；慢输入同样只能事后超时 | 查询、总执行均有界，记录耗时与慢计算 |
| 普通计算恢复 | JVM 中断后，相同幂等键仍返回过期的 `CALCULATING`；按批次 ID 查询才能转 `FAILED_TIMEOUT` | 相同幂等键能识别超时并恢复，运行锁不能长期残留 |
| 影响分析恢复 | 领取变化后终止 JVM，重启仍为 `ANALYZING`，没有后继计算项 | 持久化任务重启可恢复 |
| 批次领取恢复 | 批次已领取、计算项尚未开始时中断，重启批次变 `DEAD`、计算项仍 `PENDING` | 待执行项不能因这个崩溃窗口丢失 |
| 候选计算恢复 | 候选计算中断后，原普通计算锁残留，重算重试耗尽进入 `DEAD` | 超时回收、重启续执行和重复执行防护共同成立 |
| 成功项恢复 | 单项成功已提交、批次尚未完成时中断，重启批次变 `DEAD`、项仍 `SUCCEEDED` | 保留成功候选并形成可审批批次 |
| 冻结后变化 | 已经 `PENDING_APPROVAL` 的批次仍追加新触发，新变化被标记处理而没有后继计算 | 冻结后不追加，新变化保留给后继批次 |
| 归并边界 | 不同修正窗口合入一批；不同原因/组织边界的变化也可挂到原活动批次 | 原因、修正窗口、组织权限边界参与归并 |
| 失败隔离 | 一项 `SUCCEEDED`、一项 `FAILED_RETRYABLE`，整批停在 `FAILED_RETRYABLE` | 成功项不用等失败项耗尽重试即可形成审批批次 |
| 连续模拟重算 | 第一轮模拟候选完成后，后来有效快照变化没有再生成候选 | 模拟结果也需持续识别后续有效变化 |
| 分母冲突 | 同年度两个有效面积版本导致整个请求 HTTP 409 | 面积强度为空并说明冲突，总排放量仍生成 |
| 旧工作线程越权写入 | 两个真实 JVM 取得不同租约 token 后，旧线程仍把新租约下的 `CALCULATING` 项写成 `FAILED_RETRYABLE` | 租约必须参与写入校验，旧工作线程不能覆盖新所有者 |
| 手动触发并发幂等 | 相同指纹 32 个并发请求只留下 1 条变化，但有 3 个 HTTP 500 | 重复请求稳定返回同一已持久化触发，而非内部异常 |

以上是软件实现问题，不是缺少真实设备、专业因子认证或生产硬件导致的未验证项。不得用补齐真实数据代替修复。

另一个失败断言来自两个 JVM 的竞争领取：16 次测试控制调用中 3 次数据库死锁，4 个批次最终均处于 `CALCULATING`。该用例要求全部控制调用成功，因此判为失败；原始结果**不证明已经重复领取或丢任务**，需区分瞬态死锁重试能力与租约 fencing 缺陷。

通过的 9 项为：真实 HTTP 年度总量/两项强度/明细落库、12 组合容量、普通请求幂等与竞争保护、双硬上限、冻结前积压与审批发布、重试耗尽与人工恢复、月季无强度及年度分母缺失、未领取变化重启继续执行、发布事务中途终止后回滚并重新审批。发布回滚验证确实在未提交 `PUBLISHING` 事务中终止了 JVM，不是只手工修改数据库状态。
