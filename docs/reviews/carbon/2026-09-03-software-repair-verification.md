## 修复内容

- 普通计算传播请求截止时间，规则查询使用有超时的短事务；事务外计算使用有界工作许可，超时且未实际退出的工作仍占用许可。截止后的完成写入被事务检查和数据库条件拒绝。
- 同幂等键回查先回收已过期批次，仍返回原批次；新键可在回收同建筑、周期和性质的过期锁后开始新批次，不修改旧结果或幂等键。超时记录耗时和慢计算标记。
- 影响分析增加持久化租约、重试和恢复；重算领取、开始、成功、失败、收尾和续租均校验当前租约。统一先锁批次再处理项，避免旧工作线程越权写入和原竞争领取的反向锁顺序。
- 归并使用原因、修正窗口、组织边界和结果性质，等待可配置归并窗口；冻结后的新变化保留待处理，旧候选审批发布后再针对继任结果计算，不追加到冻结范围。
- 成功项先进入审批，失败项保留身份、重试次数、责任主体和触发依据，转入关联恢复批次。连续模拟变化可以产生后续模拟结果，手动触发保留请求的结果性质。
- 年度分母冲突仅使对应强度为空并说明原因，不阻断排放总量；保留年度唯一两项强度及月季只提供排放量的口径。
- 新增 [V40](../../../src/env/init/V40__mysql_carbon_recalculation_recovery.sql) 仅增加恢复、归并及父子批次关系字段和索引，不初始化业务因子、分母或改写历史结果。

容量矩阵为 `12/96/500 条快照 × 1/4/8/16 并发`，每组 16 次，共 192 次 HTTP 请求，均成功生成完整结果。

| --- | --- | --- |
| 12 | 16 | 376.2ms |

HTTP 工作线程峰值 8、业务连接峰值 4、等待连接峰值 5，各组结束时等待为零。累计 120,576 次 JDBC 执行，单次 SQL 最大 346.2ms、借连接最大 326.1ms。存在短时排队；每组仅 16 个样本，p95/p99 等于组内最大值，不构成生产 SLA。第一轮同组合最大约 5.04 秒，最终轮约 6.04 秒，保留波动，不挑选较快轮次作为最终数值。

100 条变化冻结前归并为 12 栋建筑 × 2 年 = 24 项/3 批，分析、计算及审批发布约 8935ms。真实定时入口风暴排空约 2631ms，后续模拟变化继续形成第二批。不同原因/组织/窗口、冻结后的继任计算及失败子批次独立恢复均有专门断言。

普通计算、影响分析、已领取未开始、候选计算中断、成功项已保存、发布事务未提交等窗口均使用真实 JVM 强制终止和重启；两 JVM 并发领取及旧 token 写入用例通过。恢复不以手工改状态代替进程重启。

真实 InnoDB 行锁用例配置总截止 2 秒，最终约 1372.4ms 返回 `504 / CARBON_CALCULATION_TIMEOUT`，观测时活动/等待连接均为零。慢输入约 2248.8ms 返回 504，批次为 `FAILED_TIMEOUT`、耗时 1950ms、慢计算标记为真且运行锁为空。

### 断言补强与独立复核

第一轮修复后 49 项断言全部通过，但人工核对原始响应发现真实 SQL 超时仍返回 500：JDBC 关闭连接后，Spring 回滚异常掩盖了原 `QueryTimeoutException`。因此没有直接宣告通过；补充回滚异常中的原始异常识别、事务超时分类及 3 个正反例单测，并在原用例增加 504 和错误码断言，重跑完整矩阵后通过。

独立代理基于冻结设计、本次源码差异、最终 XML 和 JSON 证据进行只读复核，未修改文件或重复运行数据库测试。结论为“本轮修复无新增确证阻断，反例修复证据通过”；确认原 24 项断言未削弱，超时和调度等待条件反而加强，并核对新增 4 项。普通全量回归和打包由主代理执行，不冒充独立代理重新执行。

- 不证明正式业务因子、真实面积/人数、真实建筑结果、真实设备、生产连接池及长期调度容量。
- 测试身份替代登录流程，上游变化通过测试装载进入依赖仓储；不证明生产登录、上游业务修正与依赖事件的同事务一致性，也不证明仅通过公开业务 API 完成全流程。
- 不以版本 ID、JSON 和哈希存在代替完整追溯契约已验收；全设计条款的收口和用户正式版本批准保持独立。
- 独立复核提示未专门注入“重算批次 `CALCULATING` 但租约为空”的存量坏状态。V39 原领取路径已原子写入状态和租约，未发现正常路径产生该组合；如实际升级检查发现该状态，需单独处理，不能用本轮正常迁移证明其可恢复。
- SQL 行锁用例发生在普通批次创建阶段，直接证明响应与连接池释放；不单凭该用例断言既存批次终态。已有运行批次的超时终态由慢输入、普通重启及近邻测试覆盖。
