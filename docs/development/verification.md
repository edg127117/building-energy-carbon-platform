# 开发测试与结果验证规范

## 1. 基本原则

修改后必须执行与范围匹配的验证，并如实记录实际命令、成功、失败、跳过项和未执行原因。测试失败时不得把任务描述为可合并或已完成。

测试命令由当前仓库配置和 CI 决定；命令变化时先核对 `pom.xml`、`web/package.json` 与 `.github/workflows`，不要沿用历史任务文档中的旧命令。

## 2. 后端验证

修改 Java 生产代码时：

1. 先运行与改动直接相关的定向测试；
2. 再运行完整后端测试入口：

```powershell
.\mvnw.cmd test
```

涉及打包、资源、配置装配或 CI 行为时，按范围补充：

```powershell
.\mvnw.cmd verify
```

必须核对测试配置不会连接个人或生产 MySQL、TDengine、Redis、MQTT Broker 或第三方服务。多数据源测试应明确 Bean、`Qualifier`、SQL 方言和测试替代实现。

## 3. 前端验证

修改 Vue 或 TypeScript 生产代码时：

1. 运行相关 Vitest 定向测试；
2. 运行当前完整前端验证入口：

```powershell
npm run test:run -- --maxWorkers=1 --minWorkers=1 --pool=threads
npm run lint
npm run check
npm run build
```

命令在 `web` 目录执行。页面和状态逻辑还要核对：

- 加载、空数据、部分失败、全部失败和过期状态；
- 快速切换、关闭、卸载和迟到响应隔离；
- 权限与建筑范围不会只依赖前端；
- 不生成随机业务数据，不在浏览器重算后端指标；
- API 字段、单位、时间语义和错误状态与后端契约一致。

## 4. 跨前后端改动

接口、DTO、错误语义、时间范围、权限或业务字段变化时，同时检查：

- 后端 Controller、Service、DTO 和数据访问测试；
- 前端 API、Type、Composable/Store、页面和组件测试；
- 接口路径、字段可空性、单位、枚举、时间区间和错误码；
- `PROJECT_GUIDE.md` 中的稳定链路是否需要更新；
- `PROJECT_STATUS.md` 中的用户可见完成状态是否发生变化。

只完成后端或前端一侧时必须标记为部分完成，不得描述为完整用户功能。

## 5. 外部资源和测试隔离

普通自动化测试不得依赖真实外部环境，优先使用 H2、Mock、Fake、测试专用配置或可控容器。真实 MySQL、TDengine、Redis、EMQX、现场设备和第三方接口只允许在明确标记的集成或现场验收中使用。

新增外部资源能力时同时提供测试环境关闭、替换或模拟方式。启动建库、建表、修复、定时任务、补偿、MQTT 连接和演示数据应有明确开关；关键错误不得静默吞掉。

## 6. IoT/HVAC 专项核对

- MySQL 只承载结构化业务数据，TDengine 只承载时序数据和指标；SQL 不跨数据源执行；
- MQTT 上行、质量校验、分钟聚合、公式计算、缓存和查询展示保持明确边界；
- Redis 缓存不是时序事实的永久存储；
- 后端 WebSocket 端点存在不代表前端已经消费；
- 历史、最新值、数据质量和查询时新鲜度不能混写；
- 页面展示必须来自当前真实 API 数据，不能用假历史、默认指标或浏览器计算掩盖缺失链路。

## 7. 文档与流程类改动

纯文档、规则、脚本或 CI 修改不机械运行无关业务测试。应执行与变化直接相关的 Markdown 链接、脚本测试、配置解析、仓库 guardrail、`git diff --check` 和路径范围检查。

仓库流程防护的专用命令、成功标记和失败处理查看 [`repository-guardrails.md`](repository-guardrails.md)。Hook 或 CI 通过不代表业务语义已经人工核验。

## 8. 结果记录

提交和 PR 材料必须区分：

- 已执行且通过；
- 已执行但失败；
- 被跳过及原因；
- 自动化测试不能覆盖的人工确认；
- 本地环境或外部资源尚未验证。

不得使用历史测试数量代替本次结果，也不得把启动成功、接口存在或后端完成推断为完整用户功能。
