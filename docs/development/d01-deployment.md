# D01 升级与恢复操作边界

本文说明 D01 及后续填报迁移的维护流程：兼容 V83→V84、V84→V85、V85→V86、V86→V87 和 V85→V86→V87，并支持 V87→V88 和 V88→V93。V86/V87 的包格式、版本授权及验收以第 8 节为准，V88 见第 9、10 节，V93 单表升级见第 11 节；第 6、7 节的 V85 候选和现场安排保留用于追溯。隔离演练通过不代表已在运行测试系统执行；实际停写、备份、迁移、切换只在批准的维护窗口运行。测试发布仍固定在 `18080→18081`，不操作 80 端口、其 Nginx 或 `/var/www/iot-platform/current`。

## 1. 前置核验

- 记录实际后端包、前端包、清单和 SHA256，不能只依据 `current` 目录名推断运行的后端版本；前后端可能分别发布。
- `d01_release.py prepare` 在旧系统运行时核验目标版本前一版的 Flyway 历史与校验和（目标 V84 对应 V83，目标 V85 对应 V84；V86/V87 必须按第 8 节显式声明源版本），检查候选包包含对应迁移和独立入口，准备产物和冻结计划；不停止服务、不改 `current`、不改控制开关。
- 运行环境必须为 TEST，`MYSQL_FLYWAY_ENABLED=false`、`TDENGINE_INITIALIZATION_ENABLED=false`，迁移使用独立账号。配置文件、服务 unit、控制开关和 MQTT clientId 在各阶段保持原值。
- MySQL 主库、`iot_platform_archive` 和 TDengine 都必须有可恢复备份。旧的 `backup-server-compat.sh` 不作为 D01 备份依据；D01 使用 `d01_backup.py`，不在本任务中改动服务器既有定时备份任务。
- 先在新建隔离实例恢复备份、核对存量摘要。`SHA256SUMS` 只证明文件完整，不能代替恢复和业务验收。
- 核实磁盘余量、源数据规模、备份峰值临时空间和新账本增长量。备份工具默认至少需要 10GiB 空闲空间；按实测备份量上调 `--min-free-bytes`，这个默认值不代表已通过容量验收。待处理队列上限不等于全部 D01 表的行数或磁盘上限。
- 清点其他后端实例、直写程序、导入与重算、定时采集。明确所有写入均被隔离；暂停审核和配置提交。确认 Broker 会话、持久化、队列容量及保留时间，以及 HTTP 调用方的重试能力。QoS 1 本身不证明维护期间不丢数据；若无法保证保留，须由用户明确接受维护窗口内 HTTP/MQTT 数据可能缺失且无法补采，记录授权依据，不补造数据、不宣称无损。
- 若要求停写前完成恢复核验，先在线核验当前基线完整备份并在隔离实例实际恢复；没有可用备份时不得直接停机。此项只验证恢复能力，不能代替停写后本轮一致性备份及绑定它的恢复报告。恢复工具、镜像及传输入口提前就绪，记录耗时以评估停机预算；权限不通或预计明显超时应报告并保持原服务运行。

## 2. 凭据与发布包

脚本要求 Linux、Python 3.10+、Java 21、Docker CLI 和 systemd，维护入口使用 sudo/root。把 `d01_release.py`、`d01_backup.py`、`daikin_test_deployment_config.py` 放在同一受控目录；维护期间禁止其他发布流程或人工改动配置及 `current`。

发布包根目录包含 `building-energy-carbon-platform.jar`、`web/index.html` 和 `MANIFEST.txt`，清单填写 `commit`、`backendJarSha256`、`webIndexSha256`、`expectedMigration=84`、`85`、`86`、`87`、`88` 或 `93`（V86及以上还必须填写 `sourceMigration`），必须与 JAR 的最大 MySQL 迁移版本一致。V93 只允许第 11 节的单表计划。通用 `Deploy-BuildingEnergyCarbonTest.sh` 拒绝 D01 包，避免绕过冻结及独立迁移。

通过受保护渠道创建 root 所有的普通 0600 JSON 文件（须与 sudo 后的实际执行用户一致），不把密码写进命令行、日志、Git 或清单：

- schema 凭据：`{"url":"jdbc:mysql://127.0.0.1:<端口>/iot_platform?...","user":"<独立迁移账号>","password":"<秘密>"}`。URL 不得携带 user/password 参数。
- backup 凭据：`{"mysql":{"user":"<备份账号>","password":"<秘密>"},"tdengine":{"user":"<备份账号>","password":"<秘密>"}}`。必须使用核实有效的账号，不从容器初始化环境推断当前密码；MySQL 账号需具有双库、routines/events/triggers 所需备份权限。

凭据经独立进程环境或 stdin 使用；迁移不会启动 Spring 应用。独立入口是打包后的 `com.platform.tools.D01SchemaMigration`，由 PropertiesLauncher 加载，支持 `validate83`，V84 至 V88 及 V93 的 `upgrade<版本>`、`validate<版本>`；不提供 V89～V92、baseline、repair、clean 或降级操作。

### 一次维护的临时授权

需要由维护执行者自动完成阶段操作时，使用 `Install-D01TemporaryAuthorization.py` 安装一次性入口。管理员须核对安装器和完整工具包的 SHA256；执行安装器时先读取文件内容、校验这些字节，再执行已校验的内容，不能把“先 sha256sum、再按可写路径执行”当作防替换保证。工具包只包含五个固定 Python 文件、D01 专用 `taosdump-d01` 与其许可证清单、一个固定发布包；包内候选提交、JAR、前端和导出工具摘要均锁定，不允许后续上传新程序替换它们。

- 安装目录 `/opt/building-energy-d01-maintenance` 及祖先必须由 root 持有且不可被普通用户写入；状态、凭据、锁、备份和恢复报告保存在 `/var/lib/building-energy-d01-maintenance/private`，权限为 0700/0600。
- 安装器采用 `umask 077` 后，必须显式设置工具目录和数据父目录为 0755，确保降权文件准备进程能遍历、读取公开工具；私有目录仍为 0700，凭据仍为 0600。仅给 `mkdir` 传入 0755 会被 umask 收窄，不能代替实际权限验证。
- 精确 sudo 白名单只允许 `/usr/local/sbin/building-energy-d01-maintenance` 的固定动作；不放行 Python、shell、Docker、systemctl、通配参数或 `SETENV`。执行环境清空后重建，Python 使用 `-I`，模块仅从已校验的安装目录导入。
- 维护包发布到用户目录、解包及 `current` 切换由降权后的 `user1` 子进程执行；内部子进程仅接受 root 父进程创建的 socketpair 通道，通过内核对端 UID/PID 验证，绑定阶段和期限，不提供可直接调用的发布/切换动作。特权迁移只执行管理员保护的 JAR 副本，不执行用户可替换的发布目录 JAR。
- 安装时不再询问数据库密码或凭据路径。只复用既有 S02 维护入口 `/etc/building-energy-carbon-test/s02-admin.json`，要求文件及祖先由 root 持有、不可由普通用户修改、无软链接，文件权限不宽于 0600。从 `mysql_migration_password`、`mysql_root_password`、`td_root_password` 读取已有账号凭据，分别用于 `platform_migrator`、MySQL `root` 和 TDengine `root`；不扫描其他目录、不执行配置文件、不从容器初始化变量推断当前密码，也不创建、改密或重新授权数据库账号。
- 授权发布前，核对正在运行的测试进程、固定本地端口、容器 ID 和卷，探针结束后复核进程及容器未替换。迁移账号通过发布包内已校验的 JDBC 驱动访问实际 Flyway 端点，备份账号通过固定容器 ID 的 mysql 通道核查登录及权限，并比较两者的服务器 UUID 和实际认证身份；应用 MySQL/TDengine 均须为非 root，且进程不得携带已分离的管理员凭据。保留 S02 双库迁移账号契约，检查主库和归档库的 CREATE/SELECT/INSERT 及 Flyway 写历史权限，再独立检查两库的备份权限；角色间接授权或部分撤销不能未经核实当作完整权限。复用凭据仍需满足至少 16 字符要求。TDengine 在固定回环 REST 入口检查已有管理员权限及源库存在，禁止代理和重定向携带凭据。
- 缺文件、缺字段、认证失败或权限不足时，输出对应的稳定错误码、不输出密码和原始数据库错误；不发布 sudo 授权、不停止服务。管理员无需猜密码，按缺失项修复既有受保护配置后再执行同一安装命令。安装成功只证明本轮只读登录/权限检查通过，不代表实际 taosdump、完整备份或恢复通过；这些仍是停写前独立门禁。
- 授权有效期为安装后 24 小时；入口自身检查期限，专用 systemd timer 到期移除本次 sudo 白名单和复制的凭据。结束时必须主动执行 `sudo /usr/local/sbin/building-energy-d01-maintenance revoke`，保留备份和审计证据。撤销不启停业务服务；到期或失败时仍处于停机状态，须报告管理员处理，不能为了恢复访问而续期或放宽权限。
- 撤销不加载或检查备份、迁移模块，避免这些模块损坏阻断清理；仍校验 root 保护配置和本次授权规则。若 launcher、撤销程序或配置本身损坏，或者管理员改过 sudoers，自动清理不能保证完成，必须由管理员核对后撤销本次规则及复制凭据。不可捕获的强杀可能留下未完成安装文件；完成标记缺失时维护动作拒绝，已启用的到期 timer 仍可撤销，不把这种情况描述为安装成功。
- 失效 timer 只管理本次授权。安装仅新增这组维护文件和 timer，不停止、重启测试服务，也不改应用控制开关。已有同名授权拒绝覆盖；安装失败或中断会停止、禁用本次 timer 并按创建记录清理本轮文件和目录，保留预存文件；清理失败明确报告，由管理员核查对应路径，禁止递归清理测试部署目录。授权规则发布后仍须等待安装完成标志才可执行维护动作。
- 仅在旧尝试已撤销且失败于 `prepare`、无停写记录、尚未生成 incoming 包或候选目录、旧凭据已删除、timer 已停用、旧程序哈希未变且原服务仍运行时，管理员可显式使用 `--replace-revoked-prepare`。安装器先将固定维护文件及完整记录移入 root 私有的 `/var/lib/building-energy-d01-maintenance-history`，再安装新授权；不删除历史、不改测试发布目录、不允许替换已停写或已迁移的尝试。已生成部分产物或归档路径跨文件系统时提前拒绝；归档中途失败会停止并报告，由管理员核查，不能自动删除或恢复旧授权。

固定动作顺序：`prepare` → `online-backup` → `export-online` → 隔离实际恢复 → `record-online-restore` → `freeze` → `backup` → `export-backup` → 隔离实际恢复 → `record-restore` → `migrate` → `cutover` → 业务验收 → `revoke`。`status` 只输出阶段、时间和服务状态。导出是备份二进制流，应直接写入受保护文件，不能输出到聊天或普通日志。

`online-backup` 是业务仍在运行时分别导出各引擎的恢复能力检查，不保证跨库同一时刻一致，不能替代停写后的本轮备份。`freeze` 还要求 120 秒内的维护人员核查记录：`checked_at`（UTC 秒）、`no_other_deployment=true`、`external_writers_fenced=true` 和非敏感 `reference`，从 stdin 读取；这是已有维护者的现场确认，不是软件自动证明所有外部写入者不存在。

两类 `record-*-restore` 从 stdin 接收 `{"report": <恢复报告>, "evidence": <实际恢复证据对象>}`。报告采用下文 `D01_RESTORE_VERIFIED_V1` 字段，入口为证据生成固定文件名和哈希，校验具体备份及新实例身份。它是可信维护人员的结果记录，必须在实际恢复与数据核验完成后提交，不能用构造 JSON 代替恢复。任何状态变更动作失败都停止自动推进并保留现场，不提供通用命令、任意 SQL 或自动回退入口。

已撤销且失败于在线备份的尝试使用单独的 `--replace-revoked-online-backup`。只接受完整的 `PREPARED` 状态及 `PREPARED→FAILED` 事件，拒绝任何冻结、迁移、候选启动字段；核验原版本、运行控制、配置、既有站点和进程启动时间。旧 incoming 包和候选目录原地保留，核对包、JAR、前端首页摘要；部分 MySQL 备份随整个 root 数据目录归档。新提交必须使用不同且不存在的发布路径。该入口不清空旧记录、不复用部分备份、不停止服务，也不提供失败阶段重置。归档后新授权失败时历史仍保留；归档中断须人工核查。

### TDengine 导出客户端与诊断

现场 3.2.3.0 的 `taosdump` 对 stdin 密码使用 `scanf("%20s", ...)`，超过 20 字节会截断。D01 从同一上游提交 `3bb61cc2ccea8e092cc96dc3619969302567fd4d` 构建单独客户端，只将该输入改为有边界的完整行读取，输入过长或缺少换行立即拒绝。构建脚本固定源码和基础镜像摘要；不替换容器自带程序、不升级数据库、不缩短或重设密码，不把密码放进命令行。源码依据：[上游对应版本](https://github.com/taosdata/taos-tools/blob/3bb61cc2ccea8e092cc96dc3619969302567fd4d/src/taosdump.c)。

在本机 Docker Desktop 构建：`docker build --output type=local,dest=target/d01-taosdump-client scripts/d01-taosdump`。将产物 `taosdump-d01` 和 `LICENSE`（包内名为 `taosdump-LICENSE`）纳入授权包。构建固定基础镜像、上游提交与源码包 SHA256；系统构建依赖来自 Ubuntu 官方仓库，未声称逐字节可重复构建。每轮授权锁定实际产物 SHA256。维护入口每次核验工具哈希，并要求目标原生库与隔离验证版本的 SHA256 一致；仅复制到固定目标容器新建的私有临时目录，单线程导出后清理。备份中不包含工具、密码或原始导出日志。缺少固定客户端或原生库不匹配时拒绝，不能回退到有截断缺陷的旧工具。

失败诊断保存为私有 `tdengine-diagnostic.json`，只含固定阶段、退出码和白名单类别，例如认证失败、连接失败、空间不足、输入不合法；操作记录也保留该诊断。未知输出标为 `unclassified`，不把未经筛选的 stdout/stderr、SQL、密码或 DSN 写入记录。授权仍需在失败后撤销。

运行 `python scripts/Verify-D01ExportIsolated.py` 可在新建本机容器重现旧客户端长密码失败，并验证修正版导出、新实例恢复、时间/值/质量/标签一致、错误密码拒绝及脱敏诊断。这是合成数据验证；真实备份与恢复仍须在新授权后分别完成。

## 3. 维护阶段

以下是受信管理员直接操作的模板，不是本次交付已经执行的命令。临时授权始终使用上一节固定维护入口及其每次哈希校验；直接运行底层脚本不提供该授权封装，管理员须自行核验脚本与同目录客户端的摘要及所有权。先填写经核验的包、凭据、容器、卷和备份目录；不使用自动探测结果替代目标确认。

```bash
sudo python3 d01_release.py prepare --release <发布名> \
  --archive <测试目录/incoming/包.tar.gz> --sha256 <包哈希> \
  --schema-credentials <受保护schema凭据.json>
```

记录输出的状态文件路径。确认上游保留/重试及外部停写后，在维护窗口冻结：

```bash
sudo python3 d01_release.py freeze --state <状态.json> --writers-fenced --ingress-retained
sudo python3 d01_backup.py create --freeze-state <状态.json> \
  --output-root <备份目录> --credentials-file <受保护backup凭据.json> \
  --mysql-container <MySQL容器> --mysql-volume <MySQL卷> \
  --tdengine-container <TDengine容器> --tdengine-volume <TDengine卷> \
  --tdengine-database iot_telemetry --min-free-bytes <容量核验后的字节数>
sudo python3 d01_backup.py validate --backup-dir <本轮备份目录>
```

如果已明确批准接受维护数据缺失，将上述 `freeze` 命令替换为下列命令。两种入口策略互斥；未选择策略、缺少授权依据或未确认外部停写均拒绝停止服务：

```bash
sudo python3 d01_release.py freeze --state <状态.json> --writers-fenced \
  --accept-ingress-loss --loss-acceptance-reference '<本次维护授权记录标识>'
```

此路径在冻结状态和备份清单中记录 `ingress_retained=false`、`ingress_loss_accepted=true` 及授权依据，不降低备份、实际恢复、独立迁移或业务审核门禁。授权依据只记录非敏感标识。维护记录须分别记下发出停写命令、确认停写、服务恢复和采集恢复的实际时间；服务恢复不等于缺测已补齐，也不能仅凭停机时长推算实际缺失条数。发现失败或预计明显超出已沟通预算时报告当前阶段和数据状态，不擅自扩大操作范围。

将本轮完整备份复制至独立环境，按已演练流程恢复到两个新容器，核对主库/归档库逐表内容、TDengine 时间/值/质量及源数据未被覆盖；保存实际执行证据。由执行此验证的同一维护人员形成 root 所有的 0600 `restore-report.json`，不是新增角色或业务审批。报告必须绑定本轮 `manifest.json` SHA256、新实例 ID 和执行证据文件哈希，不能用上一轮演练结果替代；未完成真实恢复不得填写通过标志。格式为：

```json
{"format":"D01_RESTORE_VERIFIED_V1","backup_manifest_sha256":"<本轮清单SHA256>","mysql_verified":true,"tdengine_verified":true,"source_preserved":true,"restored_container_ids":["<新MySQL容器ID>","<新TDengine容器ID>"],"evidence_file":"restore-evidence.json","evidence_sha256":"<执行证据SHA256>"}
```

报告是受信维护者的恢复验收记录，程序校验绑定及完整性，不把布尔值本身当作恢复动作。证据文件与报告放在同一受保护目录，迁移和切换都要求提供：

```bash
sudo python3 d01_release.py migrate --state <状态.json> --backup-dir <本轮备份目录> \
  --schema-credentials <受保护schema凭据.json> --restore-report <恢复验证报告.json>
```

`freeze` 显式停止测试 Nginx 和后端；后续备份、迁移、切换均检查两者 inactive，备份绑定本轮冻结身份和文件哈希，迁移/切换还校验该份备份的恢复报告。迁移失败保持停写，不能继续切换。`cutover` 再验证 V84，然后记录不可自动回退标记、切换测试软链接、分别启动后端和测试 Nginx并校验两者 active。失败停止候选，不启动旧包；停止失败单独报错。80 入口同时比较原始软链接文本、解析目标、master PID 与 systemd reload 记录。

当前应用没有统一的只读启动模式：启动即可能接入消息、运行恢复、聚合和保留任务，也可能恢复既有控制任务。不能把 HTTP 健康检查之前的时间视为“尚无业务写入”。D01 不擅自改变既有控制开关；维护前须依据既有控制安全流程核实待执行任务和设备下行链路，必要隔离由维护窗口安排。脚本完成状态仅为 `AWAITING_BUSINESS_ACCEPTANCE`，不等于业务验收完成；上游入口恢复由维护人员按核验结果控制。

## 4. 验收和回退

迁移验收：仅 V84 一条新成功记录，Flyway validate 通过，九张新表与五个预算种子存在；既有业务表内容不变，旧角色/职责不变，指定角色获得预期菜单授权；历史原始值不会由升级自动回填或修正。

业务验收在隔离数据或明确授权的验收数据上执行：重复合并、原始证据保留、普通更正与既有能源审核衔接、后到正确值进入历史查询和分钟/能源重算、撤销后恢复正确来源、任务积压/重试/到期处理；未审核的正式结果不得发布。验收数据不得混入原有正式结果。

现场恢复验收：测试页面/API、MQTT 重新订阅和积压排空、停机时间段的数据数量/身份/质量、既有查询与审核、控制配置与安全配置不变；80 端口站点软链接和进程不变。Redis 属于既有缓存：不在此工具自动整库恢复或清空，恢复前须另核验缓存与双库一致性及登录会话影响。

- 冻结前失败：旧系统继续运行，`prepare` 失败只保留未发布产物。
- 已停写、尚未启动候选：保留现场。V84 完整且尚无新业务写入时，只有核实旧包与增量结构兼容、运行时 Flyway 关闭后才可人工启动原包；本文不提供自动回退命令。
- 迁移部分失败：MySQL DDL 可留下已提交对象，重复 migrate 不等于恢复。保留失败历史和残留结构，使用隔离恢复演练确定恢复步骤；不得盲目 repair、clean、删除历史或直接重试。
- 候选开始启动后：即按“可能已有写入”处理，禁止直接返回旧包。优先兼容修复；若必须恢复备份，先保存升级后的 MySQL/TDengine 数据和新增证据，明确备份时刻后的损失范围及重放方案，经确认后才能执行。旧备份恢复不是无损回退。

## 8. V86/V87 填报发布适配

这是发布工具能力说明，不代表已安装服务器工具、升级数据库或发布应用。V84/V85 的既有迁移及校验和保持不变；不会自动审批参数、发布楼宇配置、授予职责或改变空调控制开关。

### 包与版本计划

| 源版本 | 清单字段 | 独立迁移顺序 |
| --- | --- | --- |
| V85 | `sourceMigration=85`，`expectedMigration=86` | `validate85` → `upgrade86` → `validate86` |
| V85 | `sourceMigration=85`，`expectedMigration=87` | `validate85` → `upgrade86` → `upgrade87` → `validate87` |
| V86 | `sourceMigration=86`，`expectedMigration=87` | `validate86` → `upgrade87` → `validate87` |

每个 `upgrade` 进程仍只允许执行一条相邻迁移。V87 包从 V85 升级时，两个进程共享同一次冻结、备份和恢复证据，中途不启动应用。清单最大版本必须与 JAR 内最大 MySQL 迁移版本一致；缺少源版本、错误标注、V84 直接到 V87、未知版本和旧候选 V84/V85 编号均不能自动兼容或 repair。若服务器尚非 V85/V86，先单独处理既有维护步骤，不能靠修改清单跨过它们。

旧的无版本状态只代表 V83→V84。临时授权同时固定源版本、目标版本、代码及包摘要；V86/V87 必须提供新的 `--authorization-reference`。旧授权不能扩成新版本计划。更换已撤销完成记录时，旧记录的目标版本必须等于本轮源版本；旧失败 prepare/online-backup 只能重试同一个版本计划。备份与恢复证据归档保留，不重置失败状态。

### 发布和失败处理

继续使用 `prepare` → 在线备份与新实例恢复 → `freeze` → 冻结备份与新实例恢复 → `migrate` → `cutover`。通用单步部署脚本继续拒绝含 D01 迁移的包；运行账户的 Flyway 和 TDengine 初始化保持关闭，DDL 只由独立迁移账号执行。

- `prepare` 核验实际源库，失败时不停止服务或切换 `current`。
- 备份、冻结身份、源容器/卷、恢复报告或证据摘要不匹配时，迁移及切换均拒绝。迁移及切换重新检查源容器 ID、镜像和挂载卷；V86→V87 的第二步也复核，不能把同名重建的实例当作原备份来源。
- V86 部分 DDL 或 V87 在 V86 成功后失败时，保持冻结及现有结构/证据；不自动重试、repair、降级、原地恢复或重启旧应用。切换必须重新验证完整 V87。
- 候选首次启动前写入不可自动回退标记；启动或验收失败时停止候选并保留现场，停机命令限时 60 秒并复核两项服务均为 inactive。命令失败、超时或服务仍活动时记录 `FAILED_STOP_ERROR`，不能误记已停止，也不重启旧应用。启动后可能已有业务写入，不能按“页面未就绪”推断无写入。
- 控制文件原始摘要、生效控制参数、MQTT clientId、服务配置、18080→18081 路由以及 80 站点链接/PID/reload 保持原有保护；维护流程不修改这些配置。

### 验收

## 9. V88 默认电力因子数据年兼容

V88修改 `chk_carbon_electricity_years`，允许已批准的2021/2022全国默认因子保留空数据年，详见[正式参数清单](formal-energy-parameters.md)。迁移不回填年份、不激活参数、不改变楼宇配置。迁移账号须具有主库 `ALTER` 直接权限，运行账号仍不授予DDL权限。新包必须包含V88迁移文件与独立迁移入口，通用发布脚本仍拒绝绕过分阶段维护。

在线及冻结备份、主库/归档库/TDengine实际独立恢复、停写授权、源实例身份和控制状态核验继续适用。升级或最终校验失败时保持冻结和失败历史，不自动repair、重跑、降级或恢复旧应用；恢复必须在明确恢复时点和损失范围后另行批准。V88隔离CI补验未停写与运行账号DDL拒绝、重复升级拒绝、失败记录保留，以及V87双库备份在新实例恢复后重新升级。软件验证通过不代表已取得维护窗口或已部署。


## 10. V88 同版本应用发布

本节为待发布工具能力，不表示已安装授权、执行维护或完成空调现场验收。用于保留 V88 正式参数、填报、审核及 D01 证据，只更新包含空调修复的应用和前端；不建立 V89，不重复执行 V88，也不自动审批或发布任何业务配置。

### 包与授权契约

清单必须同时填写 `sourceMigration=88`、`expectedMigration=88`、`releaseMode=APPLICATION_ONLY`，并固定候选提交、JAR 和前端摘要。JAR 最大迁移版本必须恰为 88，保留 V84 至 V88 及此前既有迁移内容。缺少显式模式、其他同版本组合、跨版本冒用该模式或未知模式均拒绝。旧包、旧授权或旧备份不能作为本轮授权。

安装器继续复用唯一受保护管理员配置，校验账号登录、同一实例身份、备份权限及容器/卷。纯校验仍使用独立 `platform_migrator` 凭据，但只要求双库 SELECT，不为换包新增 DDL 权限；V87→V88 的 ALTER 及其他升级权限要求保持不变。授权固定本轮源/目标版本、模式、代码及包摘要；特权包装层与底层入口均只允许 `validate88`，拒绝 upgrade、repair、clean、baseline 和任意动作。只执行管理员固定副本中的校验代码，不执行可写发布目录的特权 JAR。

本路径仅通过受控授权 launcher 执行，不以 root 直接执行用户可写目录中的发布脚本或 JAR。所需 SELECT 是最低权限要求，不自动撤销或扩充既有迁移账号权限。

已撤销且完成的 V87→V88 升级记录或 V88→V88 应用发布记录均可通过 `--replace-revoked-completed` 整体归档后重新授权。仍核对旧工具、当前基线 JAR、配置、完成阶段、凭据已删除及 timer 已停用；保留服务器原备份、恢复报告和失败记录。失败的 prepare/online-backup 重授权还必须匹配同一版本和发布模式，不能用换包授权扩大旧失败任务范围。

### 维护步骤与影响

1. 在最新主分支上完成合并回归、Linux 权限与真实 MySQL 隔离演练和 CI 后，从最终批准提交构建完整包。核对现场仍为 V88、当前应用版本及配置；若其他任务已更新，先重新评估，禁止用旧包覆盖其成果。
2. 本轮获批前保持在线。获批后只安装一次限定授权，执行 prepare 的 `validate88`；错误版本、迁移校验和不符或权限不足均在停止服务前拒绝。复用已有平台、厂家、MQTT 账号，不新建验收角色或 Broker 发布账号。
3. 先确认运行时 Flyway/TDengine 初始化关闭，应用账号无 DDL 权限或既有字符集启动修复已显式关闭；否则停在在线阶段处理前置条件，不能用迁移进程只读来宣称应用启动零 DDL。再完成在线主库、归档库、TDengine 完整备份及新实例实际恢复，绑定本轮在线报告；按实测备份、传输及恢复耗时评估停机预算。暂按 **15 分钟**预留维护窗口，非实测承诺；预估明显超出时先报告，保持服务运行。
4. 协调正在进行的参数准备、审核及其他发布，维护窗口由本任务独占；确认外部写入已隔离。HTTP/MQTT 数据无法补采时须另行接受本轮缺口，并记录实际停止、恢复服务及恢复采集时刻，不沿用旧窗口授权、不补造数据或宣称无损。
5. 沿用 `freeze` → 最终冻结备份 → 新实例实际恢复 → record-restore → migrate → cutover。`migrate` 为兼容动作名，此模式实际只执行 `validate88`；切换前再次 `validate88`。冻结文件及其哈希不变，在线报告不能替代最终报告，任何备份/恢复/源实例身份不符都阻断校验和切换。
6. 仅重启本测试环境 Web/后端，页面/API 暂不可用，采集、定时任务暂停，应用 MQTT 会断开并按原配置重连；不重启数据库或 Broker，不改 MQTT clientId、账户、ACL、持久会话或 80 端口站点。保持既有测试管理员权限与空调控制配置，验收不发控制指令。

### 失败处理与现场验收

- 停写前失败保持原服务；停写后失败保留冻结现场并报告。候选一旦尝试启动，失败即停止候选并保留 current、备份、状态及诊断，不自动重启旧应用或恢复数据库。即使没有结构迁移，也不能假定候选没有新写入；人工恢复须另行确认兼容性、写入证据与恢复时点风险。
- 发布前后核对 V88 全部 Flyway 历史与校验和、正式参数/填报/审核基线、既有来源和身份；只把经过正常审批的在线业务变化与发布造成的变化区分，不能回滚其他任务的配置来通过验收。
- 发布后先核对完整包、页面与 API、服务和控制/MQTT 配置；观察至少三个连续成功采集轮次，确认设备/字段时间前进、查询与页面一致，记录原 MQTT 连接恢复及新遥测到达。基础健康检查不等于业务验收。
- 只有新鲜有效的开/关观测进入运行或确认关机；过期、无观测、停用及压缩机字段过期均为未知。现场存在此类设备时核对卡片、表格、筛选、空间汇总、总览和详情；现场没有对应反例时使用隔离载荷回放补证，并明确不属于真实设备验收，不改线上数据造反例。
- 不人为使共享厂家账号失效，不修改真实设备或重复发送 PUT。有限重新登录、拒绝退避与不重发由隔离回归证明；发布后同一进程出现自然认证失效时再核对恢复。尚未发生真实失效时，该项保持现场观察中，不能描述为已完成长期恢复验收；自然失效观察不延长临时维护授权。
- 业务核对结束后撤销本轮 sudo 授权及复制的临时凭据，保留管理员已批准权限、服务器原备份、审计链及故障记录。准备阶段与 CI 通过不代表本维护窗口获批或已执行。
