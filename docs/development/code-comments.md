# 生产代码中文注释与审计规范

## 1. 适用范围与目标

修改 Java、Vue 或 TypeScript 生产代码时必须读取本文件。注释的目标是帮助维护者理解业务用途、调用链、数据来源、边界和设计原因，不追求注释数量，也不把代码逐行翻译成中文。

新增或修改代码后，应能回答：

- 当前类、组件、方法或函数负责什么，以及不负责什么；
- 谁调用它，输入从哪里来，结果交给哪个页面、接口、任务、数据源或外部系统；
- 为什么采用当前校验、公式、状态变化、异常或降级策略；
- 哪些单位、范围、时间语义、副作用和限制无法从命名直接看出。

## 2. 类、组件和分层重点

新增业务类、页面或核心组件时使用简洁、直白的中文说明整体职责和上下游。修改已有文件时，必须复核原有说明是否仍与当前实现一致。

不同层次优先说明：

- Controller：接口用途、关键参数、权限入口、调用的核心 Service；
- Service：业务校验、流程编排、事务、结果组装、状态决策和下游依赖；
- Repository、Mapper：MySQL 或 TDengine 边界、查询对象、时间区间、聚合和数据限制；
- Adapter、Client、Listener：外部系统、调用目的、失败影响、重试、补偿和降级；
- DTO、Type：字段来源、业务含义、单位、范围、可空性和字段约束；
- Entity、DO：持久化对象、关键字段和容易误解的数据约定；
- Config：配置控制的能力、开关效果以及生产与测试差异；
- Page、Component：业务目标、数据提供方、加载/空数据/失败/过期状态和关键编码；
- Composable、Store：状态生命周期、API 编排、对象切换清理和持久化副作用；
- 前端 API、Request：后端路径、响应用途、Token、统一错误处理和 401 副作用；
- Router：认证恢复、角色限制、重定向及其与后端鉴权的边界。

## 3. 关键方法与函数

是否需要说明由职责决定，不由 `public`、`private` 或文件类型决定。满足任一条件时属于关键项：

- 业务入口或主要处理阶段；
- 权限、角色、建筑范围、数据归属或参数组合校验；
- 状态变化、事务、幂等、并发、重试、补偿或恢复；
- MySQL、TDengine、Redis、MQTT、HTTP、WebSocket 或文件访问；
- DTO、Entity、时序行、缓存、外部报文和页面模型之间的重要转换；
- 聚合、公式、分辨率、时间区间或数据质量处理；
- 异常转换、降级、兜底、空数据或部分成功；
- 方法名无法完整表达的限制、副作用或设计选择；
- 由主流程依赖并承担完整步骤的私有或受保护方法。

关键项的说明应按实际需要覆盖：所在流程阶段、输入语义、上游来源、下游调用、数据源、选择当前方案的原因、返回去向、异常含义和副作用。行内注释只解释局部分支，不能代替方法整体契约。

## 4. 必须说明的业务边界

无法从命名和结构直接判断的限制必须在最接近实现的位置说明，例如：

- 测点数量、查询时长和 `[from, to)` 等时间语义；
- 分辨率、聚合方式、默认值、数据质量和新鲜度语义；
- 多数据源选择、特殊 Spring 注入和配置开关；
- `400`、`403`、`404`、`503` 等状态背后的业务原因；
- 缓存失败、外部资源失败、降级后的影响；
- 前端展示字段与后端响应、指标编码和单位的对应关系；
- 为保持模块边界、性能或一致性采用的特殊写法。

重要展示值应能追踪：

`模板 → 页面辅助逻辑 → Composable/Store → 前端 API → Controller → Service → Repository/Mapper → 数据源字段`

重要写入或异步流程应能追踪：

`请求或外部事件 → Controller/Adapter/Listener → Service/Executor → Repository/Client → 数据源或外部系统 → 状态、事件或响应`

跨越三个以上关键层，或包含异步、跨库、状态机等复杂流程时，同时保留设计或模块流程文档；全局文档与就近代码注释不能互相替代。

## 5. 不应添加的注释

通常不为以下内容添加说明：

- 普通 getter、setter、简单赋值、判空和单行委托；
- 框架注解或固定模板的基础含义；
- 已由清晰命名完整表达的简单逻辑；
- 与附近说明重复的内容；
- Java、SQL、Vue 或 TypeScript 语句的逐行中文翻译；
- “当前任务”“本次修改”等过程历史；
- 尚未接入的预留能力被描述为已经生效；
- 用长注释掩盖职责混乱、命名不清或过度复杂。

## 6. 完整文件检查

只要生产文件发生变化，就检查该文件的完整当前内容，而不是只看 diff 新增行：

1. 列出全部可识别方法、构造器和函数，包括私有项；
2. 按职责判定关键项和简单项；
3. 核验新增或改变的职责、调用链、字段、单位、状态和异常；
4. 核验已有注释是否准确、是否含过期承诺或任务历史；
5. 删除重复、无信息和逐行翻译式注释；
6. 判断是否需要同步更新 `PROJECT_GUIDE.md` 或 `PROJECT_STATUS.md`。

## 7. 任务级注释审计文档

生产 Java、Vue 或 TypeScript 发生变化时，每个 PR 新增一份审计快照：

```text
docs/reviews/comment-audits/<year>/<YYYY-MM-DD>-<task>.md
```

按 [`repository-guardrails.md`](repository-guardrails.md) 中的命令生成。报告必须覆盖每个变化生产文件及扫描器识别的全部方法、构造器和函数，并人工补充扫描器未识别的动态或匿名符号。

允许的判定只有：

- `关键-已新增说明`
- `关键-已更新说明`
- `关键-现有说明已核验`
- `简单-无需说明`

每项必须填写具体业务说明或免注释原因，不能保留“待填写”“待核验”。新任务不能复用 base 中已有报告；同一 PR 后续改变生产代码时更新本 PR 新增的同一份报告。报告合并后成为不可变历史快照。

没有生产代码变化时，PR 的“注释审计”填写“不涉及生产代码”，不创建空报告。CI 只能检查结构和证据完整性，主代理仍负责语义判断。

## 8. 合格标准

- 阅读类级或组件说明即可理解整体职责和边界；
- 阅读关键方法说明即可理解输入来源、下游、数据源、输出和限制；
- 权限、状态机、跨库、异步、缓存和外部资源边界有就近说明；
- 前端关键展示值和后端写入链路可继续定位；
- 私有关键方法没有因可见性被遗漏；
- 注释简洁、准确、长期有效，没有明显重复。
