## 第一章 项目概述

### 1.0 项目背景与讨论纪要

**项目来源**：以 COP 计算为展示核心，验证中央空调系统能效调适的可行性。

**核心讨论（2026-07-16 会议）**：

| # | 要点 | 结论 |
|---|------|------|
| 1 | 设计冻结 | 本周输出设计方案，下周起按图施工，冻结书是开发的硬性前置门槛 |
| 2 | MVP 范围 | 一个月内只做"数据采集 + 单体设备能效计算"，不涉及联合调试和动态控制 |
| 3 | 为什么不做控制 | 郑总明确："啥都没有基础的情况下贸然去控，回头把人楼都搞跳了"，安全性优先 |
| 4 | 数据获取 | 三层兜底：厂家 API/云端 → 本地通讯协议(Modbus/BACnet) → 模拟程序(外机铭牌参数输入) |
| 5 | 理论依据 | 《建筑设备与系统调适》第五章，中日两本教材参照，基本逻辑一致 |

| 9 | 人员管理 | 需涵盖四类角色：建筑业主、能效管理方、对方开发、己方管理后台 |
| 10 | 数据库基础 | 以空调数据库设计书（第二版）为基础，融合《建筑设备与系统调适》第五章模型进行扩展 |
| 11 | 风系统联动 | 水冷风循环存在耦合效应，单点调整未必有效，需多节点联动——这也正是前期"只算不控"的底层逻辑 |

**讨论中明确排除的内容**：

- 联合调适 / 系统级 COP（本期不做，单体设备先行）
- 水系统的 TAB（静态水力平衡调节，本期不考虑）
- 锅炉模块（试点建筑楼顶预计无锅炉）
- 动态控制 / 联动控制（"控会出麻烦"）
- Kafka 消息队列（EMQX 自身具备削峰能力，留待微服务拆分时引入）

### 1.1 项目目标

以所在大楼楼顶中央空调系统为试点，构建"中央空调经常性调适平台"demo 版，实现以下核心目标：

1. **数据采集**：通过 API/通讯协议/模拟程序获取冷水机组、冷却塔、风系统（AHU）的实时运行数据
2. **COP 计算**：基于《建筑设备与系统调适》第五章公式，计算冷水机组、冷却塔、水泵、风系统的单体设备能效
3. **可视化展示**：以流动动画系统图 + 点击弹窗公式的形式，直观呈现 COP 计算过程


### 1.2 试点建筑

所在大楼楼顶中央空调系统——含冷水机组 × 1、冷却塔 × 1、冷冻水泵 × 1、AHU × 1（待上屋顶勘察确认）

```
传感器/模拟器
    │
    ▼
EMQX (MQTT Topic: device/{deviceId}/data)
    │
    ▼
Java @Async 虚拟线程 MQTT 消费
    ├── 数据质量标记 (0=真实/1=插值/2=典型值兜底)
    ├── ConcurrentLinkedQueue 缓冲 → @Scheduled 500ms 批量刷 TDengine
    ├── Redis 设备状态缓存更新
    └── WebSocket 推送关键数据到前端
    │
    ▼
COP 算法引擎
    ├── 从 TDengine 按分钟拉取测点数据（is_for_calc=1）
    ├── 公式 5-1 → 5-2 → 5-3 计算冷水机组 COP
    ├── 公式 5-4 计算冷却塔效率
    ├── 公式 5-5 计算水泵效率
    ├── 公式 5-7 计算风系统耗功值

    │
    ▼

    ├── WebSocket 接收实时 COP 值 → 更新系统拓扑图监测点亮动

```

### 3.4 非功能特性决策

以下是对常用企业级非功能特性的本期决策：

| 特性 | 本期需要？ | 决策理由 | 下期规划 |
|------|:---:|------|------|
| **读写分离** | ❌ 不需要 | 只有 1 台 MySQL 实例。业务查询量极低（1 栋楼 19 个测点，查询 QPS < 10），不存在读写压力瓶颈。此特性用于高并发读场景（QPS > 1000），本系统远未达到 | 多建筑接入后 QPS 上升时引入 MySQL 主从 + ShardingSphere 读写分离 |
| **分布式锁** | ⚠️ 本期用不上，但要有能力 | 当前唯一的并发冲突点是 COP 算法引擎的 `@Scheduled` 定时任务——同一分钟的数据只被算一次，不存在多实例抢锁。真正需要分布式锁的场景是多实例部署下定时任务重复执行，本期单实例部署不存在此问题 | 多实例部署时引入 Redisson 分布式锁保护定时任务。Redis 已经部署，届时只需加注解，无需额外组件 |
| **多级缓存** | ⚠️ 部分需要 | **需要两层**：① Redis 缓存设备在线状态 + 最新 COP 实时值（已规划）；② 前端 Vue 组件内 `keep-alive` 缓存拓扑图 SVG（避免重绘）。**不需要**本地 Caffeine/Guava Cache 做二级缓存——单实例部署下 Redis 网络延迟 < 1ms，加本地缓存反而增加两层数据一致性问题 | 多实例时引入 Caffeine 本地缓存 + Redis 远端缓存两级架构，通过 Redis Pub/Sub 广播失效通知 |
| **主从复制** | ❌ 不需要 | 只有 1 台 MySQL，不需要。即使将来要读写分离也必须先有主从复制，但那是 QPS 上来之后的事 | 接入 10+ 栋建筑后，对 MySQL 做一主一从，从库专用于报表查询和历史数据导出 |
| **事务** | ✅ 需要，但范围可控 | MySQL 业务表需要事务保证数据一致性的场景：① 设备注册 + 测点批量绑定（两张表写入必须同时成功或同时回滚）；② 用户创建 + 角色分配（涉及 sys_user / sys_role / sys_user_role 三张表）。**仅需要本地事务**（Spring `@Transactional`），不需要分布式事务（Seata/Saga）——因为 TDengine 时序数据不需要事务语义（传感器数据丢了就丢了，用数据质量标记兜底，不强要求原子性） | 跨库操作（MySQL + TDengine）需要分布式事务时引入 Seata，属于微服务阶段的事 |

**决策原则**：一个月约束下，非功能特性遵循"不提前引入、不超额设计"。基础设施只有 Redis 是本期新增的必需品（设备状态缓存 + Token 缓存 + 菜单缓存），其余全部延后到真正产生需求时再引入。

## 第五章 数据采集方案

### 5.1 三层兜底策略

郑总明确指示数据获取三种方式，按优先级排序：

```
方案 A: 厂家 API / 云端接入     ← 优先
   │  (不可用)
   ▼
方案 B: 本地通讯协议直接采       ← 备选
   │  Modbus / BACnet 从机组获取
   │  (不可用)
   ▼
方案 C: 模拟程序生成             ← 兜底
   (基于外机铭牌参数 + 物理规律)
```

### 5.2 模拟程序逻辑设计

**核心原则**：上屋顶拍外机参数表 → 输入铭牌参数 → 程序按物理规律生成波动数据。

**冷水机组模拟逻辑**：

```java
// 公式 5-1：制冷量 Q₀ = V × ρ × c × ΔT / 3600
double density = 1000.0;           // 水的密度 (典型值)
double specificHeat = 4.18;        // 比热容 (定值)
double flowRate = simulateFlow();   // 基于铭牌额定流量 ±15% 随机波动
double tWin = simulateTWin();      // 进水温度，高于出水 4~8℃
double tWout = simulateTWout();     // 出水温度，典型 7℃
double deltaT = tWin - tWout;       // 温差 > 0

double coolingCapacity = flowRate * density * specificHeat * deltaT / 3600.0; // kW

// Nᵢ 两级取值：优先 PPE 瞬时功率，兜底用电参数反算
double inputPower;
if (hasPPE) {
    inputPower = readPPE();          // 直接读取 WCR1_PPE (kW)
} else {
    double voltage = simulateVoltage(); // 压缩机电压 (典型 380V)
    double current = simulateCurrent(); // 压缩机电流 (基于铭牌额定)
    double pf = simulatePF();          // 功率因数 (典型 0.80~0.95)
    inputPower = voltage * current * pf * 1.732 / 1000.0; // kW
}

// 公式 5-2：COP = Q₀ / Nᵢ
double cop = coolingCapacity / inputPower;
```

**模拟数据波动策略**：在额定值的 ±10%~±20% 范围内按正弦波 + 随机噪声叠加，模拟真实传感器漂移。

### 5.3 数据质量标记

| 质量等级 | 含义 | 数据来源 | 影响 |
|:---:|------|------|------|
| 0 | 真实采集 | API / 通讯协议接入 | 可信度最高 |
| 1 | 插值补全 | 相邻时刻线性插值 | 短期缺失 ≤ 5 分钟 |
| 2 | 典型值兜底 | 模拟程序 / default_value | 长期离线 |

质量标记**一路透传**到 COP 计算结果，确保可追溯计算可信度。

## 第六章 COP 计算场景

### 6.1 冷水机组 COP — 公式 5-1、5-2、5-3

**公式 5-1（机组制冷量计算）**：

```
Q₀ = V × ρ × c × ΔT / 3600

  Q₀  — 机组制冷量 (kW)
  V   — 冷冻水流量 (m³/h)
  ρ   — 冷冻水平均密度 = 1000 kg/m³（典型值）
  c   — 冷冻水平均定压比热 = 4.18 kJ/(kg·℃)（定值）
  ΔT  — 冷冻水进、出口平均温差 (K)
```

**公式 5-2（冷水机组能耗系数 COP 计算）**：

```
COP = Q₀ / Nᵢ

  COP — 冷水机组能效比
  Q₀  — 制冷量 (kW)，来自公式 5-1
  Nᵢ  — 机组平均实际输入功率 (kW)
```

**Nᵢ 的取值（两级优先策略）**：

```
优先级 1（PPE 直接读数）：
  Nᵢ = WCR1_PPE

优先级 2（电参数反算兜底）：
  Nᵢ = U × I × cosφ × √3 / 1000
```

- `WCR1_PPE` — 智能电表直接输出的瞬时功率 (kW)，优先使用
- `WCR1_Voltage` / `WCR1_Current` / `WCR1_PF` — 无直接功率读数时，通过三相电功率公式反算 Nᵢ

**COP 计算三步流程**：

```
步骤1: Q₀ = V × ρ × c × (T_in − T_out) / 3600     ← 公式 5-1
步骤2: Nᵢ = PPE（优先）｜ U×I×cosφ×√3/1000（兜底） ← 两级取值
步骤3: COP = Q₀ / Nᵢ                                ← 公式 5-2
```

**公式 5-3（溴化锂吸收式制冷机组能效系数 COP 计算）**：

```
COP = Q₀ / ((W × q) / 3600 + P)

  COP — 吸收式机组能效比
  W   — 燃料消耗量，燃气 (m³/h) 或燃油 (kg/h)
  q   — 燃料低位热值 (kJ/m³ 或 kJ/kg)
  P   — 消耗的电力 (kW)
```

> 公式 5-3 适用于溴化锂吸收式冷水机组。试点建筑预计为电制冷机组，公式 5-3 本期暂不涉及，保留作为后续建筑类型扩展时的备用公式。

**计算触发**：每分钟新数据到达后自动重算 → 写入 `st_indicator_minute` (indicator_code=WCR_COP) → Redis 缓存最新值 → WebSocket 推前端。

### 6.2 冷却塔效率 — 公式 5-4

```
η_ic = (T_ic,in − T_ic,out) / (T_ic,in − T_iw) × 100%

  η_ic      — 冷却塔效率（逼近度）
  T_ic,in   — 冷却塔进水温度 (℃)
  T_ic,out  — 冷却塔出水温度 (℃)
  T_iw      — 环境空气湿球温度 (℃)
```

> 室外湿球温度(T_iw)若无直接传感器，可通过干球温度 + 相对湿度查焓湿图换算。

### 6.3 水泵效率 — 公式 5-5、5-6

水泵效率需要两个公式串联计算：先用公式 5-6 求平均扬程 ΔH，再将 ΔH 代入公式 5-5 求效率。

**公式 5-6（水泵平均扬程 ΔH）**：

```
ΔH = (P_out − P_in) / (ρ × g)

  ΔH    — 水泵平均扬程 (mH₂O)
  P_out — 水泵出口压力 (Pa)
  P_in  — 水泵入口压力 (Pa)
  ρ     — 水的平均密度 = 1000 kg/m³
  g     — 自由落体加速度 = 9.8 m/s²
```

**公式 5-5（水泵效率 η）**：

```
η = V̇ × ρ × g × (ΔH + Z) × 10⁻⁶ / (3.6 × W) × 100%

  η   — 水泵效率 (%)
  V̇  — 水泵平均流量 (m³/h)
  ΔH  — 水泵平均扬程 (mH₂O)，来自公式 5-6
  Z   — 水泵进、出口压力表高度差 (m)
  W   — 水泵平均输入功率 (kW)
```

> 公式 5-5 的计算参数较多，有实际数据就算、没有就跳过（郑总指示）。

### 6.4 风系统单位风量耗功值 — 公式 5-7

```
W_s = P / (3600 × η_t)

  W_s — 风机单位风量耗功率 (W/(m³·h))
  P   — 风机全压值 (Pa)
  η_t — 包含风机、电机、变频器及传动效率在内的总效率 (%)
```

| **第一版（本期）** | MyBatis-Plus 代码生成器 | 后台选表 → 点"生成" → 下载 .zip → 解压到项目目录 → mvn compile → 重启后端服务 | ✅ 是（新增 Controller/Service/Mapper 必须重启 Spring Boot） |
| **第二版（下期）** | JSON Schema 驱动动态渲染 | 后台编辑 JSON → 保存到数据库 → 前端通用渲染引擎即时读取 → 页面立即可用 | ⚠️ 前端即时生效，后端如需新接口仍需重启 |
| **第三版（远期）** | 拖拽表单/图表设计器 | 拖拽组件 → 绑定数据源 → 自动生成 JSON → 保存即生效 | ❌ 否（全链路热呈现，无需任何重启） |

**第一版的真实操作过程**（借鉴 Enjoy-IoT 的若依代码生成器）：

```
后台 Web 界面 → 勾选 biz_equipment 表 → 点击"生成代码"
    │
    ▼
下载 .zip（包含：BizEquipment.java / BizEquipmentMapper.java
                / BizEquipmentService.java / BizEquipmentController.java
                / equipment.vue 列表页 / equipment-form.vue 表单页
                / insert_ahu_menu.sql）
    │
    ▼
解压到项目 src/main/java 和 web/src/views 对应目录
    │
    ▼
mvn compile（编译新增的 Java 类）
    │
    ▼
重启 Spring Boot 后端（新 Controller 注册到 Spring 容器）
    │
    ├─ 前端：Vite HMR 检测到新 .vue 文件 → 浏览器即时刷新（无需重启）
    └─ 菜单：执行 insert_ahu_menu.sql → Redis 刷新用户菜单 → 导航栏即时出现新菜单项
```

> **关键区别**：第一版把"重复手写 CRUD 代码"变成了"生成 CRUD 代码"，省掉的是**写代码的时间**（2~4 小时 → 5~10 分钟），但**编译和重启系统**的过程仍然是必须的。真正达到"零重启"热呈现是第二阶段之后的事。

**三阶段操作对比（以新增一个设备管理页面为例）**：

| | 第一版（本期） | 第二版（下期） | 第三版（远期） |
|------|:---:|:---:|:---:|
| 下载 .zip？ | ✅ 下载 | ❌ 不下 | ❌ 不下 |
| 后端解压文件？ | ✅ 解压 .java 文件到 src | ❌ 不解（通用 CRUD 控制器已就绪，任何表都能被它增删改查，不需要为每个表写 Controller） | ❌ 不解 |
| 前端解压文件？ | ✅ 解压 .vue 文件到 web/src/views | ❌ 不解（前端部署了通用渲染组件，从数据库读 JSON 自动画出表单和列表，新增页面只是一条 JSON 记录） | ❌ 不解 |
| 后端需重启？ | ✅ 必须重启（新 Controller/Service/Mapper 需注册到 Spring 容器） | ❌ 否（通用控制器已存在，不需要注册新 Bean） | ❌ 否 |
| 前端需刷新？ | ❌ Vite HMR 自动热更新，不丢状态 | ❌ 读新 JSON 即时渲染 | ❌ 拖拽保存即时渲染 |

**为什么第二版能去掉 .zip 和解压？**

```
第一版思路：生成"文件" → 解压部署 → 编译重启
  每个表 = 独立的 Entity.java + Controller.java + Vue 文件
    → 新增一个表就要新增 5~7 个文件 → 部署重启

第二版思路：生成"数据" → 写数据库 → 即时生效
  一个通用 Controller 处理所有表（基于 MyBatis-Plus 动态 SQL）
  一个通用渲染组件画出所有页面（基于 JSON Schema 驱动）
    → 新增一个表只是往数据库插入几条 JSON 配置记录
```

## 第十章 Enjoy-IoT 借鉴方案

### 10.1 借鉴了哪些？为什么借鉴？

#### 10.1.1 若依 RBAC 权限模型

**借鉴了什么**：Enjoy-IoT 基于若依框架的 `sys_user` → `sys_role` → `sys_menu` 三级权限模型（用户-角色多对多、角色-菜单多对多、按钮级权限控制、数据范围权限）。

**为什么借鉴**：
  - **匹配度 100%**。四类角色（建筑业主/能效管理方/对方开发/己方管理）天然适配。建筑业主只看到"系统拓扑动画 + COP 只读"菜单项，己方管理看到全部后台菜单，就是 RBAC 的经典场景
  - **省开发时间**。从零写 RBAC 至少 3~5 天（建表、JWT 集成、Spring Security 配置、前端路由守卫、按钮权限指令）。参考若依表结构和拦截器逻辑，1 天跑通
  - **经受过验证**。若依是 Java 生态最广泛使用的后台脚手架，Enjoy-IoT 在此基础上运行 2800+ Star 的项目，权限逻辑成熟

**落地方式**：直接参考 `sys_user`/`sys_role`/`sys_menu`/`sys_role_menu` 表设计，实例化为本系统的四类角色和 5 级菜单树。

#### 10.1.2 代码生成器

**借鉴了什么**：MyBatis-Plus Generator 模板引擎——选表 → 一键生成 Entity/Mapper/Service/Controller/Vue 页面/SQL 脚本。

**为什么借鉴**：
  - **直接响应郑总"摒弃纯代码开发"要求**。第一版做不到零重启，但可把"手写 CRUD"变为"生成 CRUD"
  - **技术栈完全重合**。都使用 MyBatis-Plus，生成器模板可直接改词条复用，无需从零编写
  - **一个月时间约束**。如果每个设备类型都手写全套 CRUD，一个月做不完

**落地方式**：己方后台第一版核心能力（冻结书 9.3 节）。

#### 10.1.3 物模型三层设计

**借鉴了什么**：Enjoy-IoT 把 IoT 设备能力抽象为三层——Property（属性/测点值）、Function（功能/可调用动作）、Event（事件/状态变化通知）。

**为什么借鉴**：
  - **给数据分类，避免平面化**。系统天然有这个结构，之前未显式抽象：
    - **Property** → `biz_data_point` 中 19 个测点（温度/流量/功率），分钟级采集
    - **Function** → COP 算法引擎中 5 个公式（5-1/2/3/4/5/7），可调度执行
    - **Event** → 数据质量标记（0/1/2）就是事件信号；未来散热片异常、泵效率突变都是 Event
  - **为扩展留接口**。将来加告警——"测点值超阈值"就是一个 Event，告警规则就是订阅 Event 的条件判断。现在不按三层设计，将来告警模块要从零重构数据流
  - **与毕博士设计书对齐**。`biz_data_point.data_type`（ANALOG/DIGITAL/EVENT）已隐含三层分类

**落地方式**：`biz_data_point` + COP 算法引擎 + `data_quality` 字段构成完整三层抽象。

#### 10.1.4 品类管理树形结构

**借鉴了什么**：Enjoy-IoT 设备品类采用树形结构——品类(大类) → 产品(子类) → 设备(实例)。

**为什么借鉴**：
  - **直接落到 `biz_equipment` 两级枚举**：`type_code`(大类) = WCR/WCT/WCP/AHU，`equip_category`(子类) = CHILLER/TOWER/PUMP/AHU
  - **防止未来扩展时混乱**。现在只有 1 栋建筑 4 类设备，但扩展到 10 栋建筑各差异化的设备配置时，扁平列表必然混乱，树形结构一开始就做好了

**落地方式**：`biz_equipment.type_code` + `equip_category` 两级枚举（冻结书 4.3 节）。

#### 10.1.5 消息队列可插拔

**借鉴了什么**：Enjoy-IoT 采用策略模式，支持 Spring Event / Redis / RabbitMQ / Kafka / RocketMQ 通过配置切换，不绑定具体 MQ。

**为什么借鉴**：
  - **本期不需要 Kafka，但不能把路堵死**。冻结书明确本期不用 Kafka，但如果写死 `kafkaTemplate.send()`，将来换 RocketMQ 要大改
  - **策略模式是最低成本的"预留"**。定义 `MessagePublisher` 接口 → 本期唯一实现 `SpringEventPublisher` → 将来加 `KafkaPublisher` 只需加一个实现类，改一行配置

**落地方式**：Spring Event（本期）→ 预留 Kafka/RabbitMQ 接口，采用策略模式（冻结书 3.2 节）。

#### 10.1.6 协议组件抽象

**借鉴了什么**：Enjoy-IoT 的协议组件支持动态配置 + 多实例独立部署，每种协议实现统一的 Component 接口。

**为什么借鉴**：
  - **映射到三层数据获取策略**。郑总要求 API → 通讯协议 → 模拟程序三层兜底，每层即一个协议组件：`ApiComponent` / `ModbusComponent` / `SimulationComponent`
  - **本期只实现 MQTT + 模拟，但不写死**。Modbus 组件留接口，上屋顶勘察后需本地采时 2 天即可接上

**落地方式**：本期 MQTT + SimulationComponent → 预留 Modbus/BACnet 组件接口（冻结书第五章）。

#### 10.1.7 动态菜单 + Redis 缓存

**借鉴了什么**：Enjoy-IoT 菜单树存 MySQL，Redis 缓存用户菜单。角色变更 → 清 Redis → 下次请求重建。

**为什么借鉴**：
  - **四类角色看到不同菜单**。建筑业主只看"系统拓扑"，己方管理看全部，差异必须动态渲染
  - **后台改菜单无需所有人重登录**。Redis 缓存 + 按需刷新 = 菜单变更对在线用户透明
  - **性能**。5 级菜单树如每次 JOIN 5 张表读取开销大，Redis 缓存后 O(1) 读取

**落地方式**：菜单树存 MySQL → Redis 缓存 → 角色实时切换（冻结书 9.2 节）。

### 10.2 没借鉴哪些？为什么不借鉴？

#### 10.2.1 规则引擎（设备告警/联动）

**不借鉴原因**：冻结书明确本期"不做告警引擎"。郑总指出告警规则是为未来散热片诊断做数据建模准备，非本期计算场景。引入规则引擎 = 凭空多一个子系统，一个月做不完。

**但预留了接口**：`biz_data_point.value_max`/`value_min` 保留，`biz_alarm_rule`/`biz_alarm_record` 表结构保留。规则引擎待下期"订阅 Event + 比对阈值"即可。

#### 10.2.2 第三方平台接入 SDK

**不借鉴原因**：郑总说的"对方开发后台"只需 REST API + WebSocket 推送，Swagger 文档 + JWT Token 即满足需求，不需要封装 SDK。理由：对方开发是团队内同事，非外部客户，不需要 SDK 降低门槛；API 仅查询 COP + 设备状态，接口数量少，文档即可说清楚；做 SDK 需额外维护和版本管理，一个月不够。

#### 10.2.3 OTA 固件升级

**不借鉴原因**：中央空调机组不是 IoT 设备，没有固件概念。业务场景是上屋顶拍外机参数表，而非远程推送固件。这是场景差异，非技术取舍。

#### 10.2.4 无人机接入 / AI 算法

**不借鉴原因**：Enjoy-IoT 另一个产品线是无人机智巡平台，与本系统中央空调能效计算是完全不同的业务方向，无任何交叉。

#### 10.2.5 视频接入

**不借鉴原因**：中央空调机房无需视频监控。如将来加，是独立系统集成的事，不需要在 COP 计算平台中内置。

#### 10.2.6 其他未借鉴的 Enjoy-IoT 功能

| 功能 | 不借鉴原因 |
|------|------|
| 告警中心（完整告警生命周期管理） | 本期不涉告警，预留数据段即可 |
| 数据流转（转发到其他第三方平台） | 数据不出平台，暂无第三方系统对接需求 |
| 可视化大屏（通用 Dashboard） | 需定制 SVG 系统拓扑动画，非通用图表 |
| 短信渠道（阿里云/腾讯云） | 无短信通知需求 |
| 云存储（MinIO/OSS/七牛云） | 无文件上传需求 |
| SSO 单点登录 | 独立系统，不存在多系统统一认证场景 |
| 在线用户监控 | 非必需功能 |
| 数据解析（脚本解析设备原始报文） | 数据格式统一为 MQTT JSON，不需要脚本解析层 |

## 附录 C — 规模扩展路线图（1栋 → 50栋）

> **说明**：以下内容是设计阶段的前瞻性讨论，不纳入当前 V1 实施范围。多实例、MySQL 读写分离、Kafka、Nginx、Redisson 分布式锁和按建筑 WebSocket 路由均不能据此视为已经实现；真正扩展前必须重新核对当前架构并单独设计。

### C.1 规模对比

| 维度 | 本期（1栋4设备） | 扩展（50栋1000+设备） |
|------|:---:|:---:|
| 建筑数量 | 1 栋 | 50 栋 |
| 设备数量 | 4 台 | 1000+ 台 |
| 测点总数 | 19 个 | 15000+ 个 |
| 每分钟 MQTT 消息 | 4 条 | 1000 条（~17 条/s） |
| 每分钟 COP 计算 | 4 次 | 1000 次 |
| 并发用户 | 1~3 人 | 50 人 |
| 后端部署 | 单实例 | 多实例（2~3 节点） |

### C.2 各层扩展调整

| 层 | 本期方案 | 50栋方案 | 改动量 |
|---|---|---|---|
| **MQTT 消费** | 虚拟线程异步 | 不变（EMQX 单节点吞吐 >10万 msg/s，1000 台设备远未到瓶颈） | 0 |
| **TDengine 写入** | ConcurrentLinkedQueue + 500ms 刷盘 | 改刷盘频率至 200ms；多行 VALUES 批量 INSERT（一条 SQL 500 条） | 小 |
| **COP 引擎** | 串行 `@Scheduled` 计算 4 次 | 改为虚拟线程并行计算 1000 次；加 30s 超时保护 | 🔴 大 |
| **MySQL** | 单库 | 读写分离（主库写入，从库查询报表）；ShardingSphere 透明路由 | 🟡 中 |
| **Redis** | 设备状态缓存 | 新增：分布式锁（Redisson 保护定时任务）+ 设备列表分页缓存 | 🟡 中 |
| **WebSocket** | 全局广播 | 改为按建筑路由推送（`sendToBuilding(buildingId, data)`） | 🟡 中 |
| **RBAC** | 功能权限（四类角色） | 新增数据范围权限（角色只能看被授权建筑的 COP） | 🟡 中 |
| **Nginx** | 无（单实例） | 反向代理 + 前端静态资源托管 + WebSocket ip_hash 粘性会话 + SSL | 🆕 新增 |

### C.5 原设计提出的前置动作（历史建议）

> 下表保存原设计建议，示例技术和路径不保证与当前实现一致，不构成当前任务要求。

| 动作 | 目的 | 备注 |
|------|------|------|
| API 路径统一加 `/api/` 前缀 | 将来 Nginx 按路径分流时不需要改代码 | Controller 注解和前端 axios baseURL 统一 |
| WebSocket 路径统一用 `/ws/` 前缀 | 同上，`/ws/*` 单独配置粘性会话 | Spring WebSocket `registerStompEndpoints("/ws")` |
| MyBatis-Plus 实体类用雪花算法 ID | 分库分表时无需改主键生成策略 | 设计书 `biz_equipment` 等表已采用 `BIGINT` 主键 |
| RBAC 表预留 `data_scope` 字段 | 将来加入数据范围权限时只需改值，无需 DDL | 参考若依 `sys_role.data_scope` 设计 |
| Messaging 层定义 `MessagePublisher` 接口 | 将来换 Kafka 只加一个实现类 | 本期唯一实现 `SpringEventPublisher` |

### C.6 扩展时机判断

| 触发条件 | 应引入的特性 |
|------|------|
| 建筑数量 > 5 栋 | MySQL 读写分离 |
| 后端单实例 CPU 持续 > 60% | 多实例部署 + Nginx |
| 多实例部署后 | Redisson 分布式锁 + WebSocket 按建筑路由 |
| 并发用户 > 20 人 | Redis 设备列表分页缓存 |
| 建筑数量 > 50 栋 | COP 引擎虚拟线程并行计算 |
| 需要拆微服务 | Kafka + 分布式事务（Seata） |
