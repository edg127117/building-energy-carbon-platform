# 当前文档健康与历史任务文档治理设计

> **文档状态：历史任务设计记录**
>
> 本文保留任务当时确认的设计、假设和取舍，部分内容可能已被后续提交替代。
> 判断当前状态前，请先查看 [历史文档目录](../README.md)、
> [项目指南](../../../PROJECT_GUIDE.md) 和 [项目状态](../../../PROJECT_STATUS.md)。

## 1. 背景

项目已经建立 `AGENTS.md`、`PROJECT_GUIDE.md` 和 `PROJECT_STATUS.md` 三个统一入口，但仓库仍有大量任务级设计和实施计划。当前审计基线包含 25 份 specs 和 26 份 plans，共 51 份历史任务文档。

只读扫描确认：

- 没有内容完全相同的重复文件；
- 可按文件名直接配对的 spec/plan 有 24 对；
- `building-scoped-equipment-point-identity-design` 与 `industrial-asset-point-identity-implementation` 属于同一任务但名称不同；
- `rbac-code-comments` 只有实施计划，没有独立设计文档；
- 成对文档的逐行完全重复最高约 28%，主要是范围、约束和验收标准复用，不属于整份重复；
- plans 中有大量未勾选步骤，复选框描述原计划，不代表当前项目完成状态；
- 早期文档仍包含旧电表链、`COP 尚未实现`、`/ws/dashboard` 等后来被替代的内容。

这些历史内容不会自动成为 Codex 长期记忆，但在当前任务中被直接读取时可能被误认为当前事实。本任务通过中央目录和文件级警告同时控制误读风险，并修正仍面向当前读者的六份文档。

## 2. 目标

- 为 `docs/superpowers` 建立一个统一目录，说明每份 spec 与 plan 的关系、状态和替代链。
- 让直接打开任一历史任务文档的人或 AI 第一眼就知道它不是当前状态入口。
- 保留历史正文和当时的设计依据，不把旧文档改写成现在的情况。
- 对六份当前有效文档执行证据驱动核验，修正确认过期、错误或个人机器专属内容。
- 让当前事实、设计基线、未来约束和历史任务记录具有明确优先级。

## 3. 非目标

- 不删除、移动或合并历史 specs/plans。
- 不批量重写历史正文、命令、复选框和当时的假设。
- 不因为内容与现在不同就认定它在创建时一定错误。
- 不修改业务代码、数据库、接口或运行配置。
- 不建立独立文档数据库或引入文档生成依赖。
- 不把本任务扩展为全系统业务验收或完整外部环境冒烟。

## 4. 方案选择

采用“中央目录 + 文件级警告 + 当前文档定向修正”的双层治理方案。

只建立中央目录不足以保护直接打开旧文件的场景；只增加文件级警告又无法表达配对、名称不一致和替代关系。两层同时存在，历史正文保持原样，当前事实由现有项目入口统一承载。

## 5. 文档优先级

发生内容冲突时按以下顺序核验：

1. 当前 Git 版本的代码、自动化测试和已合并决策；
2. `AGENTS.md` 中的固定规则；
3. `PROJECT_GUIDE.md` 中的稳定架构、边界和入口；
4. `PROJECT_STATUS.md` 中的当前完成状态、风险和技术债；
5. 当前专题契约和未来约束文档；
6. `docs/superpowers` 中的历史任务设计和实施计划。

历史任务文档用于理解“当时为什么这样设计和准备如何实施”，不得单独用于判断当前行为。

## 6. `docs/superpowers/README.md` 中央目录

新增 `docs/superpowers/README.md`，包含以下内容：

### 6.1 目录用途

说明 `specs` 保存任务当时确认的设计，`plans` 保存任务当时的实施步骤。设计与计划的合理职责重叠不等于重复文件，复选框也不代表当前完成状态。

### 6.2 当前事实入口

提供到仓库根目录 `AGENTS.md`、`PROJECT_GUIDE.md` 和 `PROJECT_STATUS.md` 的相对链接，明确判断当前状态时先返回这些入口。

### 6.3 配对与状态表

每个逻辑任务占一行，至少记录：

- 任务主题；
- spec 文件；
- plan 文件；
- 关系状态；
- 当前使用说明或替代任务。

关系状态使用以下固定值：

- `成对历史记录`：spec 和 plan 均存在，文件名可直接对应；
- `名称不一致`：同一任务的 spec 和 plan 命名不同；
- `仅实施计划`：只有 plan；
- `被后续任务替代`：旧任务的关键现状或路径已经由后续任务改变；
- `待核验`：无法仅通过当前证据判断关系。

一个任务可以同时具有“成对历史记录”和“被后续任务替代”的说明，但表格只保留一个主要关系状态，替代关系写在使用说明列。

### 6.4 替代关系

至少明确以下已经证实的演进：

- 旧电表并行保留相关描述 → 旧电表 Demo 下线任务；
- `/ws/dashboard` → `/ws/hvac`；
- `COP 尚未实现` → HVAC 核心公式引擎任务；
- 临时 Docker 卷和主机名 → MySQL/Redis 稳定卷与 TDengine 稳定 hostname 任务；
- 旧的前端假数据状态 → HVAC V1 前端真实数据集成结果与 `PROJECT_STATUS.md`。

README 不复制各任务的详细设计，只提供导航、关系和使用边界。

## 7. 历史文件顶部警告

为 `docs/superpowers/specs` 和 `docs/superpowers/plans` 下的每份 Markdown 文件增加统一警告，不修改警告之后的历史正文。

Specs 使用：

```markdown
> **文档状态：历史任务设计记录**
>
> 本文保留任务当时确认的设计、假设和取舍，部分内容可能已被后续提交替代。
> 判断当前状态前，请先查看 [历史文档目录](../README.md)、
> [项目指南](../../../PROJECT_GUIDE.md) 和 [项目状态](../../../PROJECT_STATUS.md)。
```

Plans 使用：

```markdown
> **文档状态：历史任务实施计划**
>
> 本文保留任务当时计划的步骤、命令和验收方式，部分内容可能已被后续提交替代。
> 文中的复选框表示原计划步骤，不代表当前完成状态；执行任何命令前必须重新核验。
> 判断当前状态前，请先查看 [历史文档目录](../README.md)、
> [项目指南](../../../PROJECT_GUIDE.md) 和 [项目状态](../../../PROJECT_STATUS.md)。
```

对于已确认存在关键替代关系的文件，在统一警告后增加一行简短的“已知替代”说明，链接到中央目录对应条目。旧正文不删除、不改写。

本任务自身会按仓库规则新增一份 spec 和一份 plan。最终验证时它们也必须纳入目录清单并具有相同文件级警告，避免治理任务本身成为新的无标识文件。

## 8. 六份当前有效文档的修正

### 8.1 `PROJECT_GUIDE.md`

- 将文档导航改为带状态、用途和当前事实来源的清单。
- 增加 `docs/superpowers/README.md` 入口。
- 明确设计冻结书是设计基线，其中实施现状和时间计划不直接代表当前状态。
- 不复制 `PROJECT_STATUS.md` 的动态进度。

### 8.2 `PROJECT_STATUS.md`

- 删除固定的合并前提交号基线，改为“以本文件所在 Git 版本为准”。
- 新增“文档健康”表，列出六份当前文档的状态、核验结果和剩余问题。
- 已修正文档问题从技术债移到核验结果；未解决问题继续明确保留。
- 不记录本机进程、端口、容器或数据库瞬时状态。

### 8.3 `docs/设计冻结书-V1.0-19测点.md`

- 顶部增加状态说明：本文是 V1 业务和技术设计基线，不是当前进度表。
- 保留会议结论、范围、安全边界、19 测点、四项指标、公式和有效设计决策。
- 第 11 章改为当前能力概览，并把详细完成状态交给 `PROJECT_STATUS.md`。
- 第 12 章保留原始一个月计划，但明确标记为历史计划，不再表示当前待办。
- 附录 C 明确为未来扩展讨论，不代表多实例、读写分离、Kafka、Nginx 或分布式锁已经实现。
- 对其他章节只修正有代码、测试或已合并决策证明的实现冲突，不把未来设想描述为已生效能力。

### 8.4 `docs/MQTT-硬件数据对接说明.md`

- 对照 `application.yml`、`MqttConfig`、载荷解析、运行时质量校验和存储结果核验字段与行为。
- 核对主题、QoS、ACK、最大载荷、可信来源系统、19 个别名、HTTP 路径和 WebSocket 路径。
- 已经正确的内容保持不变，只有证据确认不一致时才修改。
- 示例凭据必须明确为非生产占位值，不写入真实密码。

### 8.5 `docs/HVAC控制能力设计备忘.md`

- 顶部明确“未来安全约束、当前未实现”。
- 对照代码确认没有控制 Controller、Service、下行主题、指令状态机和协议 Adapter。
- 正文与当前边界一致时只补当前证据入口，不扩展未来控制设计。

### 8.6 `docs/development/java21.md`

- 保留 Java 21、Maven Wrapper 3.9.9、Windows/Linux/macOS 和 CI 验证命令。
- 删除 `F:\jdk21`、个人机器 PATH 顺序和需要管理员权限的机器级修改脚本。
- 改成使用占位路径的通用 `JAVA_HOME` 与当前终端 PATH 配置说明。
- 对照 `pom.xml`、`.mvn/wrapper/maven-wrapper.properties`、`scripts/check-java21.ps1` 和 GitHub Actions 核验版本。

## 9. 错误、冲突和无法核验的处理

- 文档与代码冲突时，先确认代码是否符合仍有效的业务设计；不能直接把代码现状写成正确设计。
- 代码违背有效业务决策时，在 `PROJECT_STATUS.md` 记录偏差，不静默修改设计冻结书迎合代码。
- 无法确认创建时是否正确的历史内容，只标记为“已被后续任务替代”或“待核验”，不使用“原文错误”。
- README 清单与实际文件数量不一致时，验证失败，不允许提交为完成。
- 文件级警告已存在时不得重复插入；脚本必须具备幂等检查。
- 本地链接或证据路径不存在时先修正引用，不得留下失效导航。

## 10. 验证设计

### 10.1 目录覆盖

- 枚举 `specs` 和 `plans` 的全部 Markdown 文件。
- 校验 README 表格覆盖每个文件且没有重复条目。
- 校验所有文件顶部具有正确类型的历史警告。
- 校验名称不一致和仅计划任务有明确说明。

### 10.2 当前文档证据

- 使用静态搜索核对类、配置项、接口路径、版本号和脚本入口。
- MQTT 契约使用现有相关测试作为辅助证据；文档修改不冒充完整外部链路验证。
- 控制能力使用有效代码目录的负向搜索证明当前没有下行实现。
- Java 21 文档与 Wrapper、检查脚本和 CI 配置逐项一致。

### 10.3 文档质量和安全

- 检查全部新增相对链接。
- 扫描真实凭据、个人机器绝对路径、临时备份和未脱敏数据。
- 执行 `git diff --check`。
- 核对 Git diff 只包含本任务约定的文档和治理脚本；若使用一次性脚本，除非它成为长期维护工具，否则不提交。

本任务不修改生产代码，因此不使用文档检查替代 Maven 或前端回归测试；只有当现有测试被用作具体契约证据时才执行对应定向测试，并如实记录结果。

## 11. 实施与提交边界

- 本任务使用一个 `docs/current-document-health` 分支。
- 设计文档、实施计划、中央目录、历史警告和当前文档修正可以分成职责明确的多个提交，但不得混入业务代码。
- 最终推送任务分支，向用户交付中文 PR 标题、说明、检查结果和 Compare 链接。
- 用户创建并合并 PR 后，收到“已合并”通知才同步 `main` 和删除本地分支。

## 12. 验收标准

- 直接打开任一历史 spec/plan 都能看到历史警告和当前入口。
- `docs/superpowers/README.md` 覆盖全部历史文件、配对关系和已知替代关系。
- 51 份基线历史文档以及本任务新增的 spec/plan 都被统一治理。
- 六份当前有效文档与当前代码、配置、测试和已合并决策一致。
- 设计冻结书保留有效业务决策，同时不再把历史计划显示为当前待办。
- Java 21 文档不包含个人电脑专属路径或机器级 PATH 修改。
- 历史正文未被批量重写、删除或伪装成当前状态。
- 没有敏感信息、失效链接、重复警告和无关文件。
