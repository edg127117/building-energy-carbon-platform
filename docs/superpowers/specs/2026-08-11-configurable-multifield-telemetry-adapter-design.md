# 可配置多字段设备报文适配器设计

> 状态：已确认并完成书面复核。本设计定义一个可独立部署、由 MySQL 配置驱动的 JSON 多字段报文适配器，以及平台侧严格预登记的设备归属解析。设计文档不代表功能已经实现；完成状态仍以当前代码、测试和 [`PROJECT_STATUS.md`](../../../PROJECT_STATUS.md) 为准。

## 1. 背景

当前平台的 MQTT 接入契约是“一条报文只包含一个测点”：

```json
{
  "buildingId": "BLD001",
  "deviceId": "WCR1",
  "pointCode": "WCR1_PPE",
  "val": 120.5,
  "timestamp": 1785398400000
}
```

[`MqttConfig`](../../../src/main/java/com/platform/config/MqttConfig.java) 将 JSON 解析为对象并拒绝缺少 `pointCode` 的报文；[`TelemetryQualityValidator`](../../../src/main/java/com/platform/iot/quality/TelemetryQualityValidator.java) 再按 `buildingId + sourceSystem + pointCode` 解析标准测点。因此设备一次发送多个业务字段时，当前入口不能直接处理。

首个待接入设备可能发送：

```json
{
  "MAC": "123456789012345",
  "current_energy": 12.34,
  "current_co2": 7.88,
  "current_co2_factor": 0.639,
  "last_period_energy": 0.25,
  "last_period_co2": 0.16,
  "last_period_co2_factor": 0.639
}
```

未来设备仍会以“一条 JSON 携带多个字段”为主，但字段名称、嵌套路径、单位和设备身份字段可能不同。系统最终部署到同一云服务器，还是采用“云端接入、本地平台和数据”，当前尚未确定。

## 2. 目标

1. 接收单个 JSON 对象中的多个数值字段，并转换为统一的多指标标准报文；
2. 通过 MySQL 保存协议模板和字段映射，不把设备字段名写死在 Java 或 YAML；
3. 相同协议模板新增设备时不修改解析代码；
4. 不同 JSON 字段结构通过新增模板和映射接入，不重新开发适配器；
5. 适配器保持独立部署能力，同时适用于整个平台上云和云端只做接入两种方案；
6. 设备建筑归属由平台可信档案决定，不相信设备自行提交的建筑信息；
7. 复用平台现有的测点质量校验、原始事件存储、分钟聚合和公式链路，不在适配器中复制业务计算。

## 3. 第一版范围

第一版包含：

- JSON 对象解析；
- MQTT 原始主题订阅和标准主题发布；
- 按原始主题及可选协议版本选择一个已启用协议模板；
- 可配置设备身份路径、设备时间路径和序号路径；
- 可配置字段路径、标准指标语义、数值类型、单位、倍率、偏移量、必填和启停；
- 一条原始报文生成一个包含多个指标的标准报文；
- 平台按设备外部身份查询预先建立的设备、建筑和测点绑定；
- 未知设备拒绝进入正式测点链路，并留下结构化日志和监控计数；
- 原始 MQTT 消息和标准消息均使用 QoS 1，并明确确认边界；
- 为未知设备处理保留独立接口，便于后续替换实现。

第一版不包含：

- 建筑与空间管理页面；
- 设备、测点、协议模板和字段映射管理页面；
- 未知设备自动建档、待认领列表、人工认领和历史回放；
- 任意代码上传、动态编译或在平台进程中执行第三方代码；
- Modbus、BACnet、二进制、加密或厂商私有非 JSON 协议解码；
- 新的能耗、碳排业务页面、公式或报表；
- 把能耗和碳排字段错误映射为现有 HVAC 19 测点；
- 微服务化现有业务平台。

## 4. 方案选择

### 4.1 采用方案：独立协议适配器，平台保留业务归属

```text
设备原始 JSON
  → 可独立部署的通用适配器
  → 标准多指标 MQTT 报文
  → 平台设备身份与建筑归属解析
  → 标准测点事件
  → 现有 TDengine、聚合、质量和公式链路
```

适配器只理解协议模板、字段路径、类型和单位，不保存建筑业务归属。平台 MySQL 保存“外部设备身份 → 平台设备 → 建筑”和“设备 + 标准指标语义 → 平台测点”的可信绑定。

这样在两种部署方案之间切换时，适配器代码不变：

```text
方案一：设备 → 云端 EMQX → 云端适配器 → 云端平台
方案二：设备 → 云端 EMQX → 云端适配器 → 本地平台
```

只调整下游 Broker、凭据和 Topic 等部署配置。

### 4.2 未采用方案

#### 直接嵌入现有 Spring Boot 平台

首次实现较少，但采用“云端只接入、本地保存数据”时需要再次拆分，部署方案会反向约束解析核心。

#### 适配器同时管理建筑和设备归属

会让云端接入组件复制平台业务档案。方案二下还需要同步云端和本地建筑、设备数据，增加一致性和安全风险。

#### 每种报文编写一个 Java 适配类

短期直观，但字段变化会持续产生代码、测试和发布工作，不能满足配置驱动的目标。

## 5. 组件职责

### 5.1 原始 MQTT 入口

- 订阅配置的原始上行 Topic；
- 限制报文大小并验证 UTF-8 和 JSON 对象结构；
- 记录 Broker 接收时间；
- 依据 Topic 路由和可选 `protocol_version` 选择唯一启用模板；
- 只有标准消息成功发布后才确认原始消息。

推荐原始主题包含外部设备身份：

```text
device/raw/{deviceIdentity}/up
```

若载荷也包含 `MAC`，适配器必须校验 Topic 身份与载荷身份一致。`MAC` 在本设计中按不透明的外部设备标识字符串处理，不依据字段名称假定它一定是标准 48 位网络 MAC 地址。

### 5.2 协议模板解析器

- 从 MySQL 读取完整启用模板快照；
- 根据配置路径读取设备身份、时间、序号和业务字段；
- 先完成整包结构、必填字段和数值检查，再生成标准报文；
- 对数值执行显式倍率和偏移量转换；
- 不猜测累计值、周期值、单位或碳排因子的业务含义。

模板配置缺少目标语义或单位时不得启用。业务方必须把 `current_energy` 明确配置为累计读数或当前周期电量，适配器只执行已确认语义。

### 5.3 标准报文发布器

- 把同一原始包的所有指标保留在同一标准报文中；
- 发布到独立标准 Topic，例如 `device/telemetry/up`；
- 使用 QoS 1；
- 标准报文携带模板版本、设备身份、设备时间或接收时间、序号及各指标来源字段，便于追溯。

### 5.4 平台标准报文入口

- 根据外部设备身份查询平台预登记绑定；
- 未绑定身份调用 `UnknownDeviceHandler`，第一版仅记录并拒绝；
- 根据“平台设备 + 标准指标语义”解析具体 `pointId` 和 `pointCode`；
- 将一条标准多指标报文展开为多条内部标准测点事件；
- 每条事件继续进入现有质量校验和 TDengine 原始事件链路；
- 配置为非计算测点的能耗、碳排字段只保存，不参加现有 HVAC 公式。

## 6. MySQL 配置模型

第一版通过数据库初始化数据完成配置，不开发管理页面。

### 6.1 适配器侧配置

适配器侧配置使用独立逻辑 Schema，并跟随适配器部署。方案一可以与平台 MySQL 共用数据库实例但使用独立 Schema 和账号；方案二部署在云端的小型 MySQL 中，不连接本地平台业务库。这里保存的是协议元数据，不保存正式测点时序数据。

`iot_protocol_profile` 表达：

- 模板编码和版本；
- 原始 Topic 路由；
- JSON 数据类型；
- 设备身份路径；
- 可选协议版本路径、时间路径和序号路径；
- 是否启用。

`iot_protocol_field_mapping` 表达：

- 所属模板；
- JSON 字段路径，支持平铺字段和点分隔的嵌套路径；
- 标准指标语义编码；
- 数值类型；
- 源单位和目标单位；
- 倍率和偏移量；
- 是否必填、是否启用。

适配器以原子快照方式刷新配置。刷新失败时继续使用上一完整版本，不让 MQTT 热路径观察到半份配置。

### 6.2 平台侧可信绑定

平台补充两类逻辑关系：

```text
外部身份类型 + 外部身份值
  → equipId
  → buildingId
  → expectedProfileCode
```

```text
equipId + 标准指标语义
  → pointId
  → pointCode
```

该关系由未来“建筑与空间管理”和“设备与测点管理”页面维护。第一版通过初始化数据提前录入测试设备，禁止根据设备载荷中的 `buildingId` 自动创建或改写归属。平台还必须校验标准报文的 `profileCode` 与设备登记模板一致，防止设备身份与协议路由串用。

## 7. 标准报文契约

输入示例：

```json
{
  "MAC": "123456789012345",
  "current_energy": 12.34,
  "current_co2": 7.88,
  "current_co2_factor": 0.639,
  "last_period_energy": 0.25,
  "last_period_co2": 0.16,
  "last_period_co2_factor": 0.639
}
```

当模板已明确指标语义和单位后，适配器输出：

```json
{
  "standardVersion": "1.0",
  "profileCode": "ENERGY_METER_V1",
  "profileVersion": 1,
  "deviceIdentity": {
    "type": "MAC",
    "value": "123456789012345"
  },
  "eventTime": 1785398400000,
  "receivedTime": 1785398400000,
  "timeSource": "SERVER_RECEIVED",
  "seq": null,
  "metrics": [
    {
      "code": "CURRENT_ENERGY",
      "value": 12.34,
      "unit": "kWh",
      "sourceField": "current_energy"
    },
    {
      "code": "CURRENT_CO2",
      "value": 7.88,
      "unit": "kgCO2",
      "sourceField": "current_co2"
    },
    {
      "code": "CURRENT_CO2_FACTOR",
      "value": 0.639,
      "unit": "kgCO2/kWh",
      "sourceField": "current_co2_factor"
    },
    {
      "code": "LAST_PERIOD_ENERGY",
      "value": 0.25,
      "unit": "kWh",
      "sourceField": "last_period_energy"
    },
    {
      "code": "LAST_PERIOD_CO2",
      "value": 0.16,
      "unit": "kgCO2",
      "sourceField": "last_period_co2"
    },
    {
      "code": "LAST_PERIOD_CO2_FACTOR",
      "value": 0.639,
      "unit": "kgCO2/kWh",
      "sourceField": "last_period_co2_factor"
    }
  ]
}
```

示例中的单位用于解释标准契约；实际模板只有在设备厂商确认单位和字段语义后才能启用。

## 8. 时间、序号与幂等边界

- 有设备 `timestamp` 时，必须使用无损整数 Unix 毫秒并标记 `DEVICE_REPORTED`；
- 没有设备时间时，允许第一版使用适配器接收时间并标记 `SERVER_RECEIVED`；
- 有 `seq` 时原样传递，供平台识别丢包、乱序和补传顺序；
- 没有 `seq` 时保持空值，不伪造设备序号；
- 使用服务器时间且没有序号的报文不能承诺可靠的设备端断线补传和跨重投强幂等，只能用于受限测试或实时采集；
- 24 小时正式稳定性测试优先要求设备提供 `timestamp` 和持续递增 `seq`。

## 9. 错误处理与确认语义

| 场景 | 适配器处理 | 是否确认原始消息 |
|---|---|:---:|
| 空包、超限、非法 JSON | 记录固定错误码并丢弃 | 是 |
| 找不到启用模板或模板歧义 | 记录配置错误并丢弃 | 是 |
| 设备身份缺失或 Topic 与载荷身份冲突 | 记录安全错误并丢弃 | 是 |
| 必填字段缺失、类型错误、非有限数值 | 整包拒绝，不发布部分标准报文 | 是 |
| 标准 Topic 发布成功 | 完成转换 | 是 |
| 标准 Topic 发布失败 | 保留 Broker 重投机会 | 否 |
| 平台找不到设备或测点绑定 | 平台记录并拒绝正式入库 | 标准消息确认，避免毒消息阻塞 |
| 平台 TDengine 写入失败 | 沿用平台现有重试和不确认语义 | 否 |

第一版采用整包结构校验，避免同一设备报文因字段顺序或局部异常产生不可解释的半包结果。平台展开后的单测点写入仍遵循现有幂等和失败语义。

## 10. 设备注册与未知设备

第一版只支持严格预登记：

```text
创建建筑和设备档案
  → 绑定外部设备身份
  → 选择协议模板并建立指标测点绑定
  → 发放或绑定 MQTT 身份
  → 启用正式采集
```

未知设备不能自动获得建筑归属。`UnknownDeviceHandler` 第一版仅负责结构化日志和监控计数，不创建业务设备、不写正式测点、不回放数据。

后续可以在不修改协议解析器的情况下增加：

- `pending_device` 待认领记录；
- 最后在线时间、上报次数和示例载荷；
- 管理员选择建筑、空间、设备和模板；
- 原始报文有限期保存与绑定后回放；
- MQTT 凭据、Topic 身份和载荷身份的联合校验。

## 11. 旧协议迁移

新多字段协议使用独立标准 Topic，不把旧单测点 `device/data/up` 直接改造成含义不同的批量协议。迁移期间旧入口只服务经核验仍存在的旧发送方；记录实际使用方并完成一次过渡后删除，不为模拟器或测试永久保留旧业务协议。

现有 19 测点测试和模拟器必须随着正式协议调整，不能反过来约束真实硬件长期维持旧格式。

## 12. 验证设计

### 12.1 适配器单元测试

- 平铺和嵌套字段路径；
- 一包多字段转换；
- 模板选择、版本选择和模板歧义；
- 必填、可选、禁用和未知字段；
- 数值类型、有限值、倍率、偏移量和单位；
- Topic 身份与载荷身份一致和冲突；
- 设备时间、接收时间回退和序号；
- 配置快照刷新失败继续使用上一版本；
- 标准发布成功和失败对应的 ACK 决策。

### 12.2 平台单元和集成测试

- 已登记身份解析到正确设备和建筑；
- 未知设备不进入正式存储；
- 同一协议模板的两台设备解析到各自测点；
- 同一标准指标语义在不同设备上解析到不同 `pointId`；
- 一条标准多指标报文展开为完整测点集合；
- 任一字段不能跨建筑或跨设备串点；
- 非计算字段不参加现有 HVAC 公式；
- 存储失败、重复和重投继续遵守既有语义。

### 12.3 外部环境验证

- 普通自动化测试使用 Mock 或隔离 Broker，不连接现场设备或生产数据库；
- 现场 24 小时测试单独记录设备身份、协议模板版本、开始和结束时间、总包数、缺序数量、重复数量、解析拒绝、平台拒绝和存储失败；
- Docker、模拟器或浏览器验证不得表述为真实硬件现场验收。

## 13. 第一版验收标准

1. 示例设备通过初始化数据完成协议模板、字段映射、设备身份、建筑和测点绑定；
2. 一条包含多个字段的 JSON 被转换为一条标准多指标报文；
3. 平台将标准报文正确展开并写入各自配置的测点；
4. 新增同模板设备只新增身份和测点绑定，不修改 Java；
5. 新增不同 JSON 模板只新增模板与字段映射，不修改 Java；
6. 未知设备、未知模板、单位或类型错误不能进入正式数据；
7. 存储失败和消息发布失败保留重投机会；
8. 当前实现、自动化验证和现场 24 小时证据分别报告，不互相替代。
