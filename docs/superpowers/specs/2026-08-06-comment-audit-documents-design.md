# 中文注释审计文档化设计

> 状态：已确认。生产代码 PR 的完整中文注释审计从 PR 描述迁移到仓库内任务级 Markdown 文档；PR 仅保留简短说明和文档链接，同时保留旧版内嵌报告兼容。

## 1. 背景与问题

当前 `Repository Guardrails` 在 PR 模式下从 `$env:PR_BODY` 读取六个固定章节，并要求生产 Java、Vue 或 TypeScript 发生变化时，把 `New-CommentAuditReport.ps1` 生成且人工填写的完整报告直接粘贴到 PR 的“注释检查”章节。

该机制能够强制覆盖变化生产文件和全部可识别符号，但存在明显使用问题：

- 完整报告可能包含大量方法和函数行，PR 首页被机械审计表占据，业务变化和测试结论不突出；
- 用户把 PR 描述改成简版后，会同时丢失必需章节和全部审计证据，门禁立即失败；
- 报告只保存在 GitHub PR 页面，合并后无法在仓库内按任务、年份或业务模块检索；
- PR 描述承担了业务说明、测试证据和长期审计载体三种职责，边界不清。

本设计把完整报告迁移到仓库内专用目录，使它成为随任务合并的不可变审计快照；PR 描述恢复为简短入口。门禁仍按当前 PR 差异重新扫描并逐项核对，不能因为报告迁移而降低检查强度。

## 2. 目标

- 完整中文注释审计报告长期保存在仓库中，并可按年份和任务检索。
- PR 描述只强制保留“变更内容”“测试”“注释审计”三个简短章节。
- 有生产代码变化时，PR 的“注释审计”只提供一个仓库相对 Markdown 链接。
- CI 读取链接指向的文档，继续校验全部变化生产文件、全部可识别符号、判定枚举和具体原因。
- 同一 PR 新增提交后，旧报告因覆盖不完整而失败，迫使报告同步更新。
- 旧版把完整报告内嵌在 PR 描述中的开放 PR 继续允许通过。
- 纯文档、测试、构建配置和非生产脚本任务不生成空审计文档。

## 3. 非目标

- 不降低或删除用途优先的中文业务注释要求。
- 不自动替代人工判断关键方法、简单方法和注释时效。
- 不把审计报告改成有期限的 GitHub Actions Artifact。
- 不使用机器人自动修改 PR、创建评论或申请额外写权限。
- 不修改 Java、Vue、TypeScript 生产代码的判定范围。
- 不在本任务中重构其他 Git Hook、测试工作流或 Git 分支流程。

## 4. 方案选择

### 4.1 采用：仓库内任务级审计快照

每个包含生产代码变化的 PR 新增一份 Markdown 文档。CI 从 PR 链接定位文档，并使用现有扫描器结果校验其内容。文档随 PR 合并到 `main`，成为历史证据。

该方案的优点是永久、可检索、可与源码提交一起克隆和备份，且人工填写过程仍在普通代码评审范围内。代价是仓库会增加少量历史文档，因此必须坚持“一项任务一份、只有生产代码变化才生成”。

### 4.2 未采用：GitHub Actions Artifact

Artifact 不污染仓库，但通常具有保存期限，且不适合作为人工填写后再次交给 CI 校验的主要载体。它不能满足长期可追溯要求。

### 4.3 未采用：机器人 PR 评论

机器人评论能保持 PR 描述简短，但需要工作流写权限、评论更新和并发处理，也仍把唯一证据留在 GitHub。当前仓库不为此扩大外部写入权限。

## 5. 目录与命名

专用目录为：

```text
docs/
└─ reviews/
   └─ comment-audits/
      ├─ README.md
      └─ 2026/
         └─ 2026-08-06-hvac-unified-history-trends.md
```

规则如下：

- 文档路径固定为 `docs/reviews/comment-audits/<四位年份>/`。
- 文件名固定为 `<YYYY-MM-DD>-<任务短名>.md`，任务短名使用小写英文、数字和连字符。
- 文件名不依赖 PR 编号，保证创建 PR 前即可准备审计证据。
- 一个 PR 只允许引用一份审计文档。
- 新任务必须新增自己的文档，不能引用已经存在于 base 分支的历史报告。
- 同一 PR 后续提交继续更新这份新增文档；在 PR 合并前它始终表现为相对 base 的新增文件。
- 合并后的文档是历史快照，后续生产代码变化创建新文档，不回写旧报告。

`README.md` 说明目录用途、命名、生成命令、不可复用规则，以及历史行号只对应当时提交而不代表当前源码位置。

## 6. 审计文档契约

文档开头包含简短、可读的任务元数据：

```markdown
# HVAC 统一真实历史趋势中文注释审计

- 任务：HVAC 统一真实历史趋势
- 审计日期：2026-08-06
- 基线分支：main
- 审计范围：本任务相对基线的全部变化生产文件
```

不在文档中保存 `HEAD SHA`。审计文档本身需要进入提交，如果把最终 `HEAD SHA` 写入文件会形成自引用；历史版本由 Git 提交天然锚定，CI 则始终使用 PR 事件的 base/head SHA 重新扫描当前差异。

元数据之后继续使用现有稳定标记和表格格式：

```markdown
<!-- comment-audit:file=web/src/components/example/ExamplePanel.vue -->
- 职责：...
- 上游：...
- 下游：...
- 数据源：...
- 结果消费者：...
- 现有注释时效：已核验
- 人工补充符号：...

| 符号 ID | 位置 | 判定与处理 | 业务说明或免注释原因 |
| --- | --- | --- | --- |
| `loadData#1` | `L42` | `关键-已新增说明` | ... |
<!-- comment-audit:end-file -->
```

现有判定枚举保持不变：

- `关键-已新增说明`
- `关键-已更新说明`
- `关键-现有说明已核验`
- `简单-无需说明`

完整报告仍必须覆盖扫描器识别出的全部变化生产文件和符号。文件级职责、上下游、数据源、结果消费者、注释时效和人工补充符号仍为必填项。

## 7. PR 描述契约

所有 PR 只强制三个章节：

```markdown
## 变更内容

- 简要说明本 PR 的业务或工程变化。

## 测试

- 列出实际执行的测试和结果。

## 注释审计

[查看完整中文注释审计](docs/reviews/comment-audits/2026/2026-08-06-example.md)
```

行为规则：

- `解决的问题`、`不包含范围`、`文件范围检查`可以按任务需要保留，但不再由 CI 强制。
- 有生产代码变化时，“注释审计”必须包含且只包含一个有效的仓库相对 Markdown 链接，可以在链接附近补充一句说明。
- 没有生产代码变化时，“注释审计”填写“不涉及生产代码”，不要求生成文档。
- 链接目标必须位于允许目录，不接受外部 URL、绝对路径、`..` 或其他目录。

## 8. 门禁校验流程

`Test-RepositoryGuardrails.ps1` 保留现有变化文件和源码注释扫描，然后在 PR 模式下执行：

1. 校验三个必需 PR 章节非空。
2. 计算变化生产文件集合，判定逻辑保持现状。
3. 没有生产文件时结束注释审计校验。
4. 有生产文件时，先检查 PR 描述是否包含新版审计文档链接。
5. 找到新版链接后，验证路径、安全边界、文件存在性和相对 base 的新增状态，再读取 UTF-8 内容。
6. 没有新版链接但 PR 描述包含旧版 `comment-audit` 标记时，以整个 PR 描述作为审计内容，维持兼容。
7. 两种证据都不存在时失败。
8. 把选定内容交给现有元数据、文件块、符号行、判定和原因校验逻辑。

新版链接优先于旧版内嵌块，避免同一 PR 中两份证据不一致。发现多个允许目录链接时直接失败，不自动猜测使用哪一份。

## 9. 路径和安全边界

CI 只接受满足全部条件的文档：

- Markdown 链接目标是仓库相对路径。
- 规范化路径匹配 `^docs/reviews/comment-audits/\d{4}/\d{4}-\d{2}-\d{2}-[a-z0-9]+(?:-[a-z0-9]+)*\.md$`。
- 目标经完整路径规范化后仍位于仓库根目录之内。
- 目标是普通文件，不接受目录、符号链接或重解析点。
- 文件存在于 PR head 的工作树中。
- 文件在 `base...head` 差异中的状态为新增，不能引用 base 已存在的历史报告。
- 文件以 UTF-8 读取且内容非空。

校验器不得跟随外部 URL，也不得把 PR 文本拼成未规范化的任意文件路径。

## 10. 报告生成器

`New-CommentAuditReport.ps1` 保留当前用法：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/New-CommentAuditReport.ps1 -BaseRef origin/main -HeadRef HEAD
```

新增可选 `-OutputPath`：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/New-CommentAuditReport.ps1 `
  -BaseRef origin/main `
  -HeadRef HEAD `
  -OutputPath docs/reviews/comment-audits/2026/2026-08-06-example.md
```

输出路径模式下：

- 校验路径属于允许目录并符合命名规则；
- 创建缺失的年份目录；
- 使用 UTF-8 写入报告模板；
- 不覆盖已经存在的历史审计文档，除非它仍是当前 PR 相对 base 的新增文件；
- 保留生成器现有的未完成人工判定占位值，要求人工逐项完成；
- `-Format Json` 与 `-OutputPath` 不能同时使用，避免输出语义含混。

没有 `-OutputPath` 时，标准输出和 JSON 行为完全兼容现有调用方。

## 11. 错误语义

新增错误码使用现有 `GUARDRAIL_ERROR` 格式：

- `AUDIT_DOCUMENT_LINK_MISSING`：生产代码变化但没有新版链接或旧版内嵌报告。
- `AUDIT_DOCUMENT_LINK_MULTIPLE`：发现多个候选审计文档链接。
- `AUDIT_DOCUMENT_PATH_INVALID`：路径、年份、文件名或仓库边界不合法。
- `AUDIT_DOCUMENT_NOT_FOUND`：链接合法但 head 工作树中不存在文件。
- `AUDIT_DOCUMENT_NOT_ADDED`：文档不是当前 PR 相对 base 的新增文件。
- `AUDIT_DOCUMENT_UNSAFE_TYPE`：目标是目录、符号链接或重解析点。
- `AUDIT_DOCUMENT_EMPTY`：文件为空或只有空白。

读取成功后继续复用已有错误，例如 `AUDIT_FILE_MISSING`、`AUDIT_SYMBOL_MISSING`、`AUDIT_DECISION_INVALID` 和 `AUDIT_REASON_INVALID`，保证定位粒度不下降。

## 12. 兼容和迁移

- 已有旧版 PR 描述只要包含完整合法内嵌报告，继续通过。
- 新 PR 模板只展示新版文档链接流程。
- `AGENTS.md` 和开发指南改为新版流程，并明确旧模式只用于兼容，不再推荐。
- GitHub Actions 工作流继续传入 `PR_BODY`，同时使用已经 checkout 的 head 文件读取审计文档，不需要新增权限。
- 现有 Staged 模式和 pre-commit Hook 不读取 PR 描述，不受本次迁移影响。
- 本规则改造 PR 不修改 Java、Vue 或 TypeScript 生产文件，因此自身不生成空审计报告。

## 13. 预计文件范围

- 修改 `AGENTS.md`：调整交付和注释审计保存规则。
- 修改 `.github/pull_request_template.md`：简化为三个必需章节和文档链接。
- 修改 `scripts/New-CommentAuditReport.ps1`：增加安全的 `-OutputPath`。
- 修改 `scripts/Test-RepositoryGuardrails.ps1`：解析文档链接并兼容旧内嵌报告。
- 修改 `scripts/tests/Invoke-RepositoryGuardrailTests.ps1`：覆盖生成、路径、兼容和失效报告。
- 修改 `docs/development/repository-guardrails.md`：说明完整操作流程。
- 新增 `docs/reviews/comment-audits/README.md`：说明长期审计快照目录规则。

不修改业务生产代码、数据库、Docker、应用配置或其他工作流。

## 14. 测试设计

自动化至少覆盖：

- 新版三章节 PR + 新增且完整的审计文档通过。
- 旧版六章节 PR + 内嵌完整报告继续通过。
- 三个必需章节任一缺失时失败。
- 生产代码变化但新版链接和旧版报告都缺失时失败。
- 多个候选链接失败。
- 外部 URL、绝对路径、`..`、错误目录、错误年份或非法文件名失败。
- 文件不存在、不是新增文件、为空或不是普通文件时失败。
- 新增生产方法但审计文档缺少符号行时失败。
- 元数据、注释时效、判定或具体原因不完整时失败。
- 纯文档 PR 使用“不涉及生产代码”通过。
- `-OutputPath` 生成 UTF-8 模板且保留待人工填写项。
- `-Format Json` 与 `-OutputPath` 同时使用时失败。
- 不带 `-OutputPath` 的现有 Markdown/JSON 输出保持兼容。
- PR 模板、`AGENTS.md` 和开发指南包含一致的新路径与命令。

测试使用临时 Git 仓库构造 base/head，不依赖真实 GitHub、网络或用户工作区。

## 15. 完成标准

- 生产代码 PR 可以用简短三章节描述和一个审计文档链接通过门禁。
- 完整审计文档随 PR 合并后可在专用目录长期检索。
- 当前全部文件、符号、元数据、判定和原因校验强度保持不变。
- PR 新增生产代码但报告未更新时稳定失败并给出明确错误。
- 路径不能越界或引用历史报告。
- 旧版内嵌报告保持兼容。
- 文档、模板、脚本、自动化测试和 `AGENTS.md` 的规则一致。
- 所有相关测试通过，任务分支只包含本次仓库流程改造。

## 16. 后续边界

以下能力不在本任务中实施：

- 自动创建或编辑 GitHub PR；
- 自动发布 PR 评论；
- 审计文档网页索引或搜索页面；
- 把历史审计迁移为数据库；
- 为既有已合并 PR 批量补录报告；
- 改变生产代码注释质量标准或降低私有关键方法覆盖要求。
