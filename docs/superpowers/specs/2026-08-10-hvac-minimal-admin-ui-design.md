# HVAC 最小后台管理界面设计

> 状态：已确认并完成书面复核。本设计补齐用户、固定角色、菜单与建筑授权的最小管理界面；不扩展到建筑档案、空间、设备、测点、代码生成器或完整浏览器自动化平台。

## 1. 背景

当前后端已经具备四类正式角色、JWT 登录、动态菜单、用户生命周期、角色菜单分配、用户建筑范围和建筑访问申请审批能力。前端目前只有登录、403 和 HVAC 大屏，没有对应的后台管理入口。

本任务目标不是重新设计权限模型，而是把现有后端能力接成可操作、可验证、可继续迭代的最小管理界面，并补齐菜单管理实际需要的少量后端安全校验。

当前事实以以下代码为依据：

- [`SysUserAdminController`](../../../src/main/java/com/platform/system/controller/SysUserAdminController.java)；
- [`SysRoleAdminController`](../../../src/main/java/com/platform/system/controller/SysRoleAdminController.java)；
- [`SysMenuController`](../../../src/main/java/com/platform/system/controller/SysMenuController.java)；
- [`BuildingAccessAdminController`](../../../src/main/java/com/platform/system/controller/BuildingAccessAdminController.java)；
- [`BuildingController`](../../../src/main/java/com/platform/hvac/controller/BuildingController.java)；

设计文档只描述确认范围，不代表页面已经实现。完成状态必须继续以当前代码、测试和 [`PROJECT_STATUS.md`](../../../PROJECT_STATUS.md) 为准。

## 2. 目标

本任务完成后，平台管理员可以：

1. 查询、创建和维护用户；
2. 启用、禁用、逻辑删除、恢复用户并重置密码；
3. 给用户分配四类正式角色和建筑范围；
4. 查看四类固定角色并配置角色菜单；
5. 维护菜单树并区分已实现页面和未上线页面；
6. 直接给用户授权建筑；
7. 审批或拒绝建筑访问申请；
8. 通过受控动态导航进入真实存在的页面。

管理界面必须继续服从后端角色和建筑范围校验，不能把菜单或前端路由当作安全边界。

## 3. 明确不包含

- 不新增或删除正式角色，不允许修改稳定角色键；
- 不开发建筑档案增删改页面；
- 不开发空间、系统、设备、测点和别名管理页面；
- 不开发代码生成器前端；
- 不实现任意数据库 `component` 字符串到 Vue 文件的动态加载；
- 不新增数据库表；
- 不修改 HVAC 采集、计算、历史、详情、WebSocket 或控制链路；
- 不增加批量导入导出、复杂拖拽菜单或完整组件库重构；
- 不做移动端专项适配；
- 不在本任务引入 Playwright 等完整浏览器自动化框架。

## 4. 方案选择

### 4.1 采用方案

采用“共享管理框架 + 四个独立页面”：

```text
/system/users             用户管理
/system/roles             角色与菜单权限
/system/menus             菜单管理
/system/building-access   建筑授权
```

四个页面共用 `ManagementLayout`，但拥有独立的数据状态、请求生命周期和测试边界。

### 4.2 未采用方案

#### 单页面四个 Tab

首次开发略快，但用户、角色、菜单和授权状态会集中在一个大型组件中，后续增加设备或测点管理时会快速膨胀。

#### 通用 CRUD 页面生成器

最后管理员保护、角色菜单树、Token 撤销和访问申请审批都不是普通 CRUD。通用生成器仍需大量特例，不符合本次最小闭环目标。

## 5. 总体架构

```text
后端管理 Controller
  → 前端 systemAdmin API 适配层
  → 各领域 Composable
  → 页面与可复用业务组件
  → ManagementLayout
```

职责边界：

- API 适配层统一 URL、参数、DTO 和分页响应；
- Composable 管理加载、筛选、分页、选中项、提交、迟到响应和权威刷新；
- 页面只组合表格、表单、抽屉和确认弹窗；
- `ManagementLayout` 只管理导航、当前账号、返回大屏和退出；
- 后端继续负责事务、最后管理员保护、Token 撤销、菜单缓存和建筑范围缓存。

页面不得直接拼接 API 地址，也不得在浏览器重新实现后端权限算法。

## 6. 受控动态菜单

### 6.1 当前问题

现有菜单种子包含多个当前前端不存在的路径和组件，例如独立 COP、冷却塔、水泵、AHU、空间、设备、测点和代码生成器页面。当前前端尚未消费 `/menu/current`，因此这些 `path`、`component` 和 `perms` 没有形成真实导航或接口鉴权。

### 6.2 处理规则

- 保留菜单表、角色菜单关系和管理 API；
- 未实现菜单保留但设为隐藏，并在管理页面标记“未上线”；
- 新增或调整真实入口：HVAC 综合监测、用户管理、角色权限、菜单管理和建筑授权；
- 登录后通过 `/menu/current` 获取当前用户菜单；
- 前端使用明确的已实现路由注册表映射菜单路径；
- 未注册路径即使被配置为显示，也不创建可点击导航，并在菜单管理页提示风险；
- 菜单是否可见不改变后端 `@PreAuthorize` 结果；
- 不根据数据库字符串任意导入 Vue 组件。

### 6.3 导航失败边界

管理员如果隐藏了自己当前使用的菜单，当前页面可以完成本次操作，重新加载菜单后入口消失；后端管理权限不会因此撤销。管理员仍可以通过真实 URL 进入有权页面并恢复菜单配置。

### 6.4 本期真实菜单注册表

| 菜单 ID | 菜单 | 类型 | 真实路径 | 本期处理 |
| --- | --- | --- | --- | --- |
| `100` | 运行监测 | `M` | `/monitoring` | 由原常规调适根目录调整名称，保持启用和显示 |
| `101` | HVAC 综合监测 | `C` | `/hvac-demo` | 新增真实入口 |
| `200` | 系统管理 | `M` | `/system` | 保持启用和显示，仅管理员拥有 |
| `210` | 人员与权限 | `M` | `/system/access` | 由原人员管理目录调整名称 |
| `211` | 用户管理 | `C` | `/system/users` | 对齐本期真实页面 |
| `212` | 角色权限 | `C` | `/system/roles` | 对齐本期真实页面 |
| `220` | 建筑权限 | `M` | `/system/building-access` | 由原建筑管理目录调整为授权职责 |

## 7. 页面设计

### 7.1 用户管理

查询条件：

- 用户名、昵称或手机号关键字；
- 启用或禁用状态；
- 是否包含逻辑删除账号；
- 后端分页。

列表展示：用户名、昵称、手机号、角色、建筑范围、账号状态、删除状态和创建时间。

操作：

- 创建用户，同时选择角色和建筑；
- 编辑昵称和手机号；
- 全量替换角色；
- 全量替换建筑授权；
- 重置密码；
- 启用或禁用；
- 逻辑删除或恢复。

创建和编辑使用右侧抽屉；禁用、删除、恢复、密码和角色变化均需要明确确认。后端返回的自操作和最后管理员保护错误原样转为业务提示，不在前端绕过。

### 7.2 角色与菜单权限

- 只显示四类冻结角色及名称、数据范围和状态；
- 不提供角色新增、删除、角色键或数据范围修改；
- 左侧选择角色，右侧展示完整菜单树；
- 加载该角色当前菜单 ID，允许父子树勾选；
- 提交前得到明确、去重的菜单 ID 集合；
- 保存使用现有全量替换语义；
- 提示菜单变化影响导航，但不等于接口授权变化。

### 7.3 菜单管理

使用树形表格展示：名称、类型、路由、页面实现状态、显示状态、启停状态和排序。

页面实现状态按菜单类型解释，不能把目录自身路径当成页面路径：

- `M` 目录递归汇总后代 `C` 页面，显示“已实现子页面 x/y”；
- `C` 页面按前端显式注册表精确判断“前端已实现”或“前端未实现”；
- `F` 按钮权限不对应页面，显示“不适用”；
- 导航显示/隐藏、菜单启用/停用是独立的数据库配置状态，不代表页面是否已经实现。

支持：

- 新增顶级菜单或子菜单；
- 编辑菜单；
- 隐藏、显示、启用和停用；
- 删除没有子节点的菜单；
- 区分“已实现页面”和“未上线页面”。

表单字段包括父级、名称、类型、路由、组件说明、权限标识、图标、显示状态、启停状态和排序。未知路由可以作为未来资料保存，但不得成为可点击导航。

### 7.4 建筑授权

页面包含两个区域：

#### 直接授权

- 搜索用户；
- 查看用户当前角色和建筑范围；
- 从真实建筑分页接口选择建筑；
- 全量保存用户建筑授权；
- 保存后重新获取该用户权威详情。

用户管理页中的“建筑授权”操作复用同一个授权抽屉。

#### 申请审批

- 按待审批、已批准、已拒绝和已取消筛选；
- 展示申请人、建筑、申请原因、状态和审核轨迹；
- 对待审批申请填写可选意见后批准或拒绝；
- 已处理申请只读展示，不允许重复审批。

## 8. 后端最小补口

现有用户、角色和建筑授权接口继续复用。菜单管理补充：

1. 新增 `GET /menu/admin/tree`，管理员完整菜单树必须包含启用、停用、显示和隐藏菜单；现有 `/menu/tree` 行为不静默改变；
2. 菜单新增、更新使用受校验的请求 DTO，不直接接收可写数据库实体；
3. 父菜单必须存在；
4. 菜单不能以自己为父级；
5. 更新父级不能形成循环层级；
6. 菜单类型只能为 `M`、`C` 或 `F`；
7. `visible` 和 `status` 只能为 `0` 或 `1`；
8. 删除有子节点的菜单继续返回冲突；
9. 菜单结构变化继续清理受影响菜单缓存；
10. 初始化迁移启用真实入口并隐藏未上线入口，不删除未来菜单记录。

不为前端便利复制用户、角色或建筑权限算法。

## 9. 前端状态与一致性

- 每个页面只有一个当前查询上下文；
- 快速切换筛选、页码、角色或用户时，迟到响应不能覆盖当前状态；
- 同一提交不能并发执行两次；
- 修改成功后重新读取后端权威结果，不用乐观数据冒充保存成功；
- 修改角色菜单或菜单结构后重新读取 `/menu/current`；
- 角色变化导致目标用户 Token 被后端撤销时，不退出当前管理员；
- 建筑授权变化后只刷新目标用户和建筑范围；
- 网络失败保留最后一次成功列表并显示刷新失败；
- 页面卸载时隔离迟到请求结果。

## 10. 错误处理

| 情况 | 页面行为 |
| --- | --- |
| `401` | 统一清理当前浏览器登录状态并进入登录页 |
| `403` | 进入 403 页面，不渲染空管理页 |
| `404` | 提示目标已不存在并刷新当前列表 |
| `409` | 保留表单并显示用户名重复、最后管理员保护、菜单存在子节点等真实冲突 |
| 网络失败 | 保留最后成功数据，展示失败和重试入口 |
| 表单非法 | 不发送请求，定位到具体字段 |

同一操作只产生一次成功或失败反馈，不用重复 Toast 掩盖业务状态。

## 11. 安全边界

- 四个管理路由使用 `meta.admin` 改善前端体验；
- 所有管理写接口继续由后端 `PLATFORM_ADMIN` 校验；
- 密码不回显、不进入列表、不写日志；
- 重置密码只提交新密码，成功后后端撤销目标用户 Token；
- 菜单权限和前端路由不代替接口权限；
- 建筑授权以后端用户、建筑存在性和最后数据范围结果为准；
- 未实现路由不会因为数据库配置而自动获得代码执行能力；
- 不在前端或文档中提交 Token、默认生产密码或真实个人数据。

## 12. 界面与交互

管理界面使用“后台操作台”而不是展示型大屏：

- 延续现有深色背景、蓝色主操作、绿色正常、黄色待处理和红色危险语义；
- 使用现有 Ant Design Vue、Lucide 图标和字体体系；
- 颜色、间距、布局尺寸和状态色通过管理模块 CSS 变量及 Ant Design Token 集中定义，不散落为页面业务常量；
- 左侧约 220px 导航，顶部展示当前账号、返回 HVAC 大屏和退出；
- 内容区使用紧凑筛选、标准表格、抽屉和确认弹窗；
- 超过三个行内操作时收入“更多”；
- 未上线、已停用、已删除和待审批不能只依赖颜色区分；
- 所有输入有真实标签、校验提示和键盘焦点；
- 首期以桌面和常见笔记本宽度为主。

不增加大量动画、玻璃装饰、拖拽菜单或与操作效率无关的视觉效果。

## 13. 视觉可替换约束

后期调整或替换风格时，必须尽量保留 API 与业务状态层：

```text
后端接口
→ API 适配层
→ Composable/业务状态
→ 页面展示组件
```

约束：

- API 地址、分页和 DTO 转换不写入 Vue 页面；
- 用户启停、角色保存和建筑授权流程不写入视觉组件；
- 主题色、间距、侧栏尺寸和状态样式集中管理；
- 四个页面共用 `ManagementLayout`；
- 视觉替换主要影响布局、组件和页面契约测试；
- 只有业务流程、字段或后端契约变化才要求重写业务状态层。

因此，颜色和布局调整属于小到中等改动；整体替换 UI 组件库属于中到大改动，但不应要求重写后端管理能力。

## 15. 真实环境验收

在专用 Docker 测试环境和真实浏览器中验证：

1. 管理员进入四个管理页面；
2. 创建测试用户并分配角色和建筑；
3. 测试用户只看到获授权导航和建筑；
4. 禁用用户后旧 Token 失效；
5. 恢复用户并使用重置后的密码登录；
6. 修改角色菜单后导航正确变化；
7. 创建、修改和删除隐藏测试菜单；
8. 普通用户提交建筑申请，管理员批准后获得建筑权限；
9. 非管理员直接访问管理 URL 和 API 均被拒绝；
10. 浏览器控制台无异常、重复请求、密码或 Token 输出。

本任务不新增完整 E2E 框架。后端流程测试、前端组件和契约测试、真实 Docker 与浏览器冒烟共同构成本阶段证据；完整浏览器自动化继续作为后续独立工程任务。

## 16. 完成标准

只有同时满足以下条件，才能将“最小后台管理页面”标记为完成：

- 四个页面均使用真实后端数据；
- 所有确认操作和失败状态可恢复；
- 用户、角色菜单和建筑授权形成端到端闭环；
- 未实现菜单不产生失效导航；
- 非管理员前后端均无法执行管理操作；
- 后端与前端完整自动化门禁通过；
- Docker 和浏览器验证结果如实记录；
- `PROJECT_GUIDE.md`、`PROJECT_STATUS.md` 和历史设计目录与实际实现同步；
- 未把建筑档案、设备测点、控制或完整 E2E 平台带入本任务。

## 17. 交付与后续边界

设计与实施计划保存在独立规划分支，不单独创建文档 PR。书面设计确认后生成详细实施计划；编码在新的 Codex 工作树和独立功能分支中从最新 `main` 开始，规划分支只作为只读资料来源。

功能 PR 不自动合并。只有用户确认已经合并后，才允许同步主线并清理分支或工作树。
