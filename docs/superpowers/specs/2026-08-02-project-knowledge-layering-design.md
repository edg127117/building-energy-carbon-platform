# 项目信息分层与维护机制设计

## 1. 背景

当前仓库已经积累了较完整的设计文档和实施计划，但缺少一个统一、简短的项目指南和当前状态入口。与此同时，Codex Memories 中混入了项目提交、PR、测试数量和阶段进度等易变化内容，导致个人长期偏好与项目事实的边界不够清楚。

本设计建立四层信息结构，让后续任务能够快速找到可信信息，并避免同一事实散落在 Memories、仓库文档和会话记录中。

## 2. 目标

- 让项目架构、模块边界、数据链路和文档入口有一个稳定的查阅位置。
- 让当前阶段、完成情况、阻塞项、技术债和下一步有一个动态状态入口。
- 让 `AGENTS.md` 明确规定后续 AI 应读取、维护和归档哪些信息。
- 让 Codex Memories 回归个人偏好、一般背景和跨项目通用经验，不再承担项目状态管理。
- 保留现有设计与实施历史，不进行无必要的迁移和重写。

## 3. 非目标

- 不修改业务代码、数据库结构、接口或运行配置。
- 不重写现有 `docs/superpowers/specs` 和 `docs/superpowers/plans`。
- 不建立完整的 ADR、独立路线图和独立技术债管理体系。
- 不把本地密码、Token、端口占用、备份路径或临时排查日志写入 Git。
- 不承诺直接修改 Codex 的主记忆文件，只通过受支持的记忆纠正说明提出瘦身要求。

## 4. 方案比较

### 4.1 双入口：`PROJECT_GUIDE.md` 与 `PROJECT_STATUS.md`（采用）

稳定信息与动态信息分开维护，文件数量少，职责清楚，适合当前 V1 阶段。后续如果技术债或决策记录明显增多，再从这两个入口拆出专用文档。

### 4.2 单文件：`PROJECT.md`

初始文件最少，但架构说明和频繁变化的项目进度会逐渐混在一起，容易形成新的大型杂项文档，因此不采用。

### 4.3 多文件：指南、状态、路线图、技术债和 ADR

边界最细，但当前维护成本高，容易出现多个文件不同步。V1 尚未稳定前不采用。

## 5. 信息架构

### 5.1 Codex Memories

只保存跨会话、跨项目仍有价值的信息：

- 用户沟通偏好和交付习惯；
- 一般技术背景；
- 跨项目可复用的工作经验；
- 不依赖当前仓库版本的长期约束。

以下内容不应继续作为长期记忆维护：

- 当前项目的提交号、PR 编号和分支状态；
- 某次测试的通过数量；
- 某个页面、接口或模块的临时完成进度；
- 当前仓库文件路径和实现状态；
- 可从 Git 历史或项目文档查到的具体决策。

实施时新增一份 Codex 记忆纠正说明，请求后续记忆整理移除上述项目状态类信息。该说明不包含密码、Token、数据库账号或其他敏感内容。

### 5.2 `AGENTS.md`

新增“项目信息分层与维护”规则，作为后续任务的固定行为约束。规则至少明确：

- 项目任务开始时，先读取 `PROJECT_GUIDE.md` 和 `PROJECT_STATUS.md`，再按需读取具体设计或实施文档；
- 当前会话只承载正在执行的细节；
- 稳定架构或数据链路变化更新 `PROJECT_GUIDE.md`；
- 项目阶段、完成项、阻塞项、技术债或下一步变化更新 `PROJECT_STATUS.md`；
- 具体任务设计和计划继续写入 `docs/superpowers`；
- 个人偏好和跨项目经验才进入 Codex Memories；
- 项目事实发生冲突时，以当前 Git 版本中的代码和项目文档为准。

该规则只负责信息路由，不复制项目当前状态，也不替代现有 Git、架构和注释规则。

### 5.3 `PROJECT_GUIDE.md`

放在仓库根目录，作为稳定项目指南。计划包含：

- 项目定位与 V1 范围；
- 系统结构和模块职责；
- 前端到后端、MySQL、TDengine、MQTT、Redis 的核心数据链路；
- 关键数据源边界；
- 主要代码入口和目录说明；
- 本地开发与验证文档入口；
- 设计冻结书、接口说明、专题设计和实施计划的索引；
- 文档维护规则。

只有架构、模块边界、核心数据流、长期运行方式或文档入口发生变化时才更新该文件。具体任务进度、短期阻塞和单次测试结果不得写入该文件。

### 5.4 `PROJECT_STATUS.md`

放在仓库根目录，作为动态项目状态入口。计划包含：

- 状态基准和更新时间；
- 当前阶段与 V1 完成边界；
- 已完成能力；
- 正在进行或尚未完成的能力；
- 当前阻塞和风险；
- 已确认技术债；
- 下一步优先级；
- 状态证据链接。

该文件描述其所在 Git 版本对应的项目状态。只有已经进入该版本且具有代码、测试或文档证据的内容才能标记为完成；计划、推测和本地未提交结果必须使用明确的未完成状态。

## 6. 后续维护流程

### 6.1 任务开始

1. 读取 `AGENTS.md`，确认固定工作规则。
2. 读取 `PROJECT_GUIDE.md`，定位模块、数据链路和详细文档。
3. 读取 `PROJECT_STATUS.md`，确认当前阶段、未完成项和风险。
4. 只在任务需要时读取对应的专题设计、实施计划和代码。

### 6.2 任务执行

- 具体命令、错误信息、临时判断和调试过程保留在当前会话。
- 新需求需要设计时，继续在 `docs/superpowers/specs` 和 `docs/superpowers/plans` 中形成任务级文档。
- 不因为执行过一次命令就修改稳定项目指南。

### 6.3 任务交付

- 架构、模块边界、数据链路或长期入口变化时，同一任务分支更新 `PROJECT_GUIDE.md`。
- 当前阶段、完成项、阻塞、技术债或下一步变化时，同一任务分支更新 `PROJECT_STATUS.md`。
- 文档与代码一起经过测试、提交和 PR 流程，合并到 `main` 后成为项目事实。
- 只有个人偏好或跨项目通用经验发生变化时，才提出 Codex Memories 更新。

## 7. 冲突与过期处理

- 代码行为与项目文档冲突时，先通过代码和测试核实事实，再修正文档，不允许静默猜测。
- `PROJECT_GUIDE.md` 与专题设计冲突时，以当前代码和最近已合并决策为核验依据，并修复失效链接或过期描述。
- `PROJECT_STATUS.md` 缺少证据或长期未更新时，明确标记“待核验”，不得直接标记为已完成。
- Memories 与仓库事实冲突时，仓库当前 `main` 的代码和项目文档优先；Memories 只用于理解用户偏好和通用背景。
- 当前会话中的结论只有进入 Git 文档或代码后，才视为可供后续任务依赖的项目事实。

## 8. 安全与内容边界

以下信息不得进入 `PROJECT_GUIDE.md`、`PROJECT_STATUS.md`、设计文档或 Codex 记忆纠正说明：

- 密码、Token、私钥和数据库凭据；
- 仅适用于个人电脑的敏感环境信息；
- 临时备份的绝对路径；
- 未脱敏的生产数据；
- 无法验证来源的完成声明。

本地开发端口只有在它们属于仓库公开配置约定时才允许记录，并应引用示例配置，不记录个人机器的临时占用情况。

## 9. 实施范围

设计获批后的实施只包含：

1. 新增根目录 `PROJECT_GUIDE.md`。
2. 新增根目录 `PROJECT_STATUS.md`。
3. 在 `AGENTS.md` 新增信息分层与维护规则。
4. 新增一份 Codex Memories 瘦身纠正说明。
5. 对新增文档执行结构、链接、敏感信息、重复职责和 Git 范围检查。

不修改其他业务、配置、数据库或运行文件。

## 10. 验收标准

- 新任务只读三个入口文件即可知道固定规则、项目结构和当前状态。
- `PROJECT_GUIDE.md` 与 `PROJECT_STATUS.md` 职责没有交叉堆叠。
- 现有专题设计和实施计划仍保留，并能从项目指南定位。
- `AGENTS.md` 明确规定任务开始、执行和交付阶段的信息维护行为。
- Codex Memories 瘦身纠正说明只处理长期记忆边界，不复制项目状态。
- 文档中没有敏感信息、临时排查日志或无证据的完成声明。
- Git diff 只包含本任务明确约定的文档与规则文件。
