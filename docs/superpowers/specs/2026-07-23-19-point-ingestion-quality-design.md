# 19 个测点数据链路验收与数据质量基础层设计

> **文档状态：历史任务设计记录**
>

> 判断当前状态前，请先查看 [历史文档目录](../README.md)、
> [项目指南](../../../PROJECT_GUIDE.md) 和 [项目状态](../../../PROJECT_STATUS.md)。

## 1. 目标

在现有 IoT 平台中完成 19 个 HVAC 核心测点的真实数据接入、数据校验、原始事件留存、事件时间分钟聚合、迟到与重复数据处理以及自动化验收，为后续 COP/效率算法提供稳定、可追溯的分钟输入。

本阶段只处理真实采集数据，所有通过校验的 MQTT 数据由平台统一标记为质量等级 0。本阶段不执行线性插值，不使用 `default_value`，不自动生成质量等级 1 或 2，不实现 COP 公式。

## 2. 范围

### 2.1 本阶段实现

- 19 个测点配置加载和有效性校验。
- MQTT HVAC 报文格式校验。
- 设备采集时间与服务器接收时间双时间记录。
- 测点、设备归属、数值和可选量程校验。
- 真实接入数据统一质量等级 0。
- TDengine 原始事件存储。
- 按设备采集时间生成分钟汇总。
- 重复、冲突和迟到数据处理。
- 原始事件保留期限配置，默认 90 天。
- 结构化拒绝日志与监控计数。
- 数据链路自动化测试和打包验证。

### 2.2 本阶段不实现

- 模拟数据生成器。
- 短期缺失线性插值和质量等级 1。
- 长期缺失 `default_value` 自动补值和质量等级 2。
- COP、冷却塔效率、水泵效率和 AHU 耗功算法。
- 历史 COP 自动补算。
- 前端页面和 WebSocket 指标推送。
- 异常数据管理页面和异常数据业务表。

## 3. 方案选择

### 3.1 备选方案

1. 保留现有内存分钟桶：实现简单，但服务重启会丢失未刷盘数据，迟到与重复处理困难。
2. 原始事件写入 TDengine，再由后端生成分钟汇总：能支持不同上报频率、重启恢复、迟到留痕和运维复审。
3. 引入 Kafka/Flink 流式窗口：扩展能力强，但对当前 19 个测点明显过重。

### 3.2 选定方案

采用方案 2。每条通过校验的真实上报写入 `st_raw_event`，分钟任务从原始事件生成 `st_raw_minute`。现有 Spring Boot 项目保持单体结构，不拆分新的 Maven 模块。

## 4. 代码职责边界

### 4.1 `iot/ingest`

- 将 MQTT JSON 转换成内部遥测命令。
- 校验必填字段和 Unix 毫秒时间戳格式。
- 由服务器生成不可伪造的 `received_time`。
- 编排校验、去重和原始事件写入。
- 返回接受、重复、拒绝或存储失败等明确结果。

### 4.2 `iot/quality`

- 加载并缓存 `biz_data_point` 有效配置。
- 校验测点状态、设备归属、有限数值和可选量程。
- 产生固定拒绝原因编码。
- 将通过校验的真实 MQTT 数据统一规范为质量等级 0。

### 4.3 `iot/temporal`

- 写入、更新和查询 `st_raw_event`。
- 查询某个设备时间分钟内的已接受事件。
- 生成并冻结 `st_raw_minute`。
- 标记并查询迟到数据。
- 清理超过配置保留期的原始事件。

### 4.4 `hvac/indicator`

本阶段只定义后续依赖的数据契约，不实现公式。后续指标计算必须保存公式版本、来源分钟、准确输入快照、结果和质量等级。

## 5. MQTT 数据契约

HVAC MQTT 报文使用以下格式：

```json
{
  "deviceId": "WCR1",
  "pointCode": "WCR1_TWin",
  "val": 12.3,
  "timestamp": 1784788220000
}
```

规则：

- `timestamp` 是设备采集时间，必须是 JSON 整数，并满足 `1_000_000_000_000 <= timestamp < 10_000_000_000_000`，即严格的 13 位 Unix 毫秒时间戳。
- 不同时接受秒级时间戳和日期字符串。
- `received_time` 由服务器收到消息时生成，不接受设备上传值。
- 设备上传的 `dataQuality` 不作为平台最终质量；真实接入校验通过后统一设为 0。

## 6. 数据校验

校验顺序如下：

1. `deviceId`、`pointCode`、`val`、`timestamp` 必须存在。
2. `timestamp` 必须是合法 Unix 毫秒时间戳。
3. `pointCode` 必须存在于 `biz_data_point`，`del_flag=0` 且 `status=ONLINE`。
4. 普通设备测点的 `deviceId` 必须与 `equip_id` 一致。
5. `DBO_TDB`、`DBO_RH` 是建筑全局测点，`equip_id` 为 NULL，不执行设备归属比较。
6. `val` 必须是有限数值，拒绝 `NaN` 和正负无穷。
7. `value_min` 或 `value_max` 未配置时不执行对应一侧校验。
8. 配置下限时拒绝低于下限的数据；配置上限时拒绝高于上限的数据。
9. 校验通过后由平台设置 `data_quality=0`。

固定拒绝原因：

- `MALFORMED_PAYLOAD`
- `INVALID_TIMESTAMP`
- `POINT_NOT_FOUND`
- `POINT_DISABLED`
- `DEVICE_MISMATCH`
- `INVALID_NUMBER`
- `BELOW_MINIMUM`
- `ABOVE_MAXIMUM`

拒绝数据不写入 TDengine 正常数据表、不进入分钟聚合、不参与后续 COP。系统输出结构化日志并按原因增加 Spring Actuator/Micrometer 计数。

## 7. TDengine 数据模型

### 7.1 原始事件 `st_raw_event`

每个测点使用独立子表，时间主键为设备采集时间。

数据列：

| 字段 | 含义 |
|---|---|
| `ts` | 设备采集时间 `event_time` |
| `received_time` | 服务器最后接收时间 |
| `val` | 通过校验的真实值 |
| `data_quality` | 本阶段固定为 0 |
| `late_flag` | 是否在所属分钟冻结后到达 |

标签：`point_code`、`building_id`、`equip_id`、`suffix_code`、`is_for_calc`。

原始事件默认保留 90 天。配置形式：

```yaml
data-retention:
  raw-event-days: 90
  cleanup-enabled: true
```

配置可以调整。延长保留期不能恢复已经清理的数据；缩短后，下次清理会删除新期限以前的事件。该策略只清理原始事件，不清理分钟汇总和指标结果。

### 7.2 分钟汇总 `st_raw_minute`

| 字段 | 含义 |
|---|---|
| `ts` | 设备时间分钟开始时刻 |
| `avg_val` | 分钟平均值 |
| `min_val` | 分钟最小值 |
| `max_val` | 分钟最大值 |
| `sample_count` | 有效且去重后的样本数 |
| `data_quality` | 窗口内最差质量；本阶段为 0 |
| `first_received_time` | 第一条样本到达服务器的时间 |
| `last_received_time` | 最后一条样本到达服务器的时间 |
| `finalized_at` | 分钟正式冻结时间 |

分钟汇总长期保留。

## 8. 时间窗口与迟到数据

- 所有窗口划分和后续 COP 输入选择均以设备采集时间 `event_time` 为准。
- 服务器接收时间只用于网络延迟、迟到判断和审计。
- 计算窗口固定为一个事件时间自然分钟，例如 `[14:30:00, 14:31:00)`。
- 默认在窗口结束后等待 30 秒冻结该分钟，配置项为 `aggregation.finalization-delay-seconds`。
- 等待 30 秒只增加结果发布延迟，不把 14:31 的数据混入 14:30 窗口。
- 冻结前收到且事件时间属于窗口的数据参与汇总。
- 冻结后收到的历史事件正常写入 `st_raw_event` 并标记 `late_flag=1`。
- 迟到事件不修改已经冻结的 `st_raw_minute`，也不自动重算已有指标。
- 未来历史重算必须通过显式任务同时生成新的分钟汇总和指标，不能只修改一侧。

## 9. 重复与冲突数据

- 业务唯一键是 `pointCode + event_time`。
- 相同键且值相同是完全重复，只保留一次，不增加分钟样本数。
- 相同键但值不同是数据冲突，最后收到的值作为原始事件当前值。
- 冲突产生结构化警告和监控计数。
- 冻结后发生冲突时，只更新原始事件审计层，不修改正式分钟汇总和指标。

## 10. MQTT 可靠性

现有订阅继续使用 QoS 1，并为 Paho 客户端启用手动确认 `setManualAcks(true)`。确认原则：

- 确定无效的数据在记录拒绝后确认，避免毒消息无限重投。
- 完全重复的数据确认，不重复处理。
- 合法数据成功写入 `st_raw_event` 后确认。
- TDengine 临时失败时最多重试 3 次；仍失败则不调用 `messageArrivedComplete(messageId, qos)`，记录存储失败指标，由 QoS 1 会话保留未确认消息并在重投或重连后再次处理。
- 重投通过业务唯一键实现幂等。

实现时必须把 MQTT 协议连接职责与 HVAC 数据质量职责分离，避免继续扩大 `MqttConfig`。

## 11. 运维复审和后续计算追溯

数据层级必须明确区分：

1. `st_raw_event`：设备逐条真实上报。
2. `st_raw_minute`：正式用于计算的分钟聚合输入。
3. `st_indicator_minute`：后续 COP/效率结果。

运维复审 COP 时，首先把指标输入快照与同一分钟的 `st_raw_minute` 对比，再从分钟汇总下钻到 `st_raw_event` 核对平均值、最小值、最大值和样本数。不能把任意一条原始事件直接当成分钟平均值代入公式。

后续每次指标计算必须持久化：

- `formula_version`
- `source_minute`
- 每个输入测点的准确分钟值
- 输入快照
- 指标结果
- 数据质量
- 计算时间

该规则保证原始样本、分钟输入和指标结果可以逐层复算。本阶段只保证分钟输入层具备这些后续能力，不实现指标存储扩展。

## 12. 配置缓存

- 启动时加载有效的 `biz_data_point` 配置。
- 定时刷新测点配置，避免每条消息查询 MySQL。
- 平台管理员新增、修改或删除测点后立即清理或刷新对应缓存。
- 缓存失效时回退 MySQL，不能因为缓存异常接受未知测点。

## 13. 测试与验收

### 13.1 测点校验

- 19 个合法配置测点全部通过。
- 未知或停用测点拒绝。
- 普通测点设备归属不匹配时拒绝。
- DBO 全局测点不执行设备归属比较。
- 非有限数值拒绝。
- 未配置量程时不拦截有限值。
- 单侧或双侧量程配置正确生效。
- 设备上传的质量 1/2 不进入平台，真实接入统一为 0。

### 13.2 时间与幂等

- Unix 毫秒时间戳正确解析。
- 设备时间和服务器接收时间分别记录。
- 完全重复事件只保留一次。
- 同时间不同值最后值生效且产生冲突记录。
- 迟到事件保留并标记，不修改冻结分钟。

### 13.3 分钟聚合

- 一分钟一个样本时，平均值、最小值和最大值等于该值，样本数为 1。
- 一分钟多个样本时，平均值、最小值、最大值和样本数正确。
- 下一分钟样本不进入上一分钟。
- 聚合窗口严格使用设备采集时间。
- 后端重启后可以从原始事件重新生成尚未冻结的分钟。

### 13.4 完整链路

- 固定测试报文经过解析、校验、原始事件写入和分钟聚合后结果可核对。
- 测试数据只存在于自动化测试环境，不是运行时模拟器，不生成质量等级 2。
- TDengine 写入失败路径可测试且不会产生虚假的成功状态。
- 完整 Maven 测试通过。
- Maven 打包成功。

## 14. 完成标准

满足以下条件才算本阶段完成：

1. 19 个配置测点均通过验收测试。
2. 非法数据不会进入 TDengine 正常数据表。
3. 原始事件同时保存设备时间和服务器接收时间。
4. 重复消息不会改变分钟样本数和平均值。
5. 分钟汇总能从原始事件复算得到。
6. 迟到数据有留痕且不会静默改变正式分钟数据。
7. 原始事件 90 天保留期限可以通过配置调整。
8. 自动化测试、编译和打包全部通过。
9. 运行时没有启用插值、默认值或模拟数据。
