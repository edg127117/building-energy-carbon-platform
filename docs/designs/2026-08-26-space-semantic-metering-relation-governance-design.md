# 空间—系统—设备—测点—计量边界关系治理闭环设计

> **文档状态：活动候选设计，方向、范围、数据模型、权限、生命周期、接口边界和软件验收规则已经用户确认；尚未实现、尚未验证、尚未批准为当前正式基线。**
>
> 当前权威基线仍以 [`PROJECT_STATUS.md`](../../PROJECT_STATUS.md)、当前代码和自动化测试为准。
> 本候选只有在完成实现、范围匹配的自动化验证、独立验收并经用户批准后，才能转为正式版本能力。

## 1. 结论

阶段一后续后台闭环锁定为“空间—系统—设备—测点—计量边界关系治理闭环”。首版采用：

```text
建筑级原子关系版本
→ 物理结构与显式语义关系分层
→ 单建筑单活动草稿
→ 校验、提交、审核和立即生效
→ 当前有效版本分层查询
→ 复制历史版本形成新版本式回滚
→ 全过程追加式审计
```

关系版本统一管理一栋建筑内的空间父子关系、设备与测点结构归属、显式语义关系、计量边界和
未分配事实；建筑、空间、系统、设备和测点的名称、编码、厂家等普通档案属性不纳入关系版本。

首版只启用 `BUILDING` 作用域。跨建筑共享能源站、总表、管网和设备不在本候选中实现；模型预留
`CAMPUS` 作用域扩展点，但运行时必须拒绝使用。多建筑查询、比较、汇总和导出不等于跨建筑关系，
继续通过建筑范围过滤后的查询聚合完成。

研发阶段允许同一开发账号完成“提交后批准”，但不能跳过提交和审核状态。生产环境强制禁止
自审；如果生产配置允许自审，应用必须拒绝启动。自审是研发例外，不是正式业务权限规则。

当前缺少能源专家确认的计量边界、分摊规则和真实现场映射。因此本候选可以实现软件框架、明确
事实迁移和安全拒绝路径，但不推断 `SERVES`、`SUPPLIES`、`RETURNS` 等业务关系，不实现分摊公式，
也不宣称真实业务、硬件或现场验收完成。

## 2. 背景与当前证据

当前仓库已经具备：

- 建筑、空间、系统分组、设备、标准测点和设备身份档案；
- 以 `parent_space_id` 表达的建筑内物理空间树；
- 设备到空间、设备到系统、测点到设备和系统的直接结构归属；
- 空间父节点、设备、系统和测点的同建筑数据库约束与服务校验；
- 新资产管理 API 的深层空间循环检查、引用计数和受保护删除；
- 正式角色、用户建筑授权、建筑范围缓存和后端范围校验；
- 数据源、质量使用策略和设备参数候选中的版本、审核、审计和回退实现，可作为工程模式参考。

主要证据入口：

- [`V03__init_hvac_schema.sql`](../../src/env/init/V03__init_hvac_schema.sql)：建筑、空间、系统、设备和测点表及同建筑复合外键；
- [`AssetManagementController.java`](../../src/main/java/com/platform/hvac/asset/api/AssetManagementController.java)：当前 `/v1/assets` 管理契约；
- [`AssetManagementService.java`](../../src/main/java/com/platform/hvac/asset/service/AssetManagementService.java)：当前空间循环、引用保护和资产聚合；
- [`BizEquipmentServiceImpl.java`](../../src/main/java/com/platform/hvac/service/impl/BizEquipmentServiceImpl.java)：设备与空间、系统的同建筑校验；
- [`BizDataPointServiceImpl.java`](../../src/main/java/com/platform/hvac/service/impl/BizDataPointServiceImpl.java)：测点与设备、系统、建筑的一致性校验；
- [`BuildingScopeServiceImpl.java`](../../src/main/java/com/platform/system/service/impl/BuildingScopeServiceImpl.java)：建筑范围安全边界；

当前主要缺口是：

- 物理关系仍由当前表直接修改，没有关系草稿和有效版本；
- 没有独立的显式语义关系表、关系类型约束、来源证据和关系有效期；
- 没有计量边界、未分配状态或待专家确认状态；
- 没有关系模型审核、生效、回滚、差异、审计和运行指针；
- `/v1/assets` 只允许平台管理员，未把建筑范围用于关系治理；
- 旧资产 Controller 仍可直接调用旧 Service，约束和删除保护与新管理 API 不完全一致；
- 现有资产状态主要按 `ACTIVE` 返回，不能表达治理版本、冲突、未分配或待确认；
- 没有空间树、语义图、计量边界和版本证据分层查询契约。

## 3. 目标与非目标

### 3.1 目标

1. 保留建筑、楼层、区域和房间的物理空间树，不把全部业务关系压成一棵树；
2. 将空间父子、设备空间/系统归属、测点设备/系统归属纳入建筑级原子关系版本；
3. 在物理结构之上建立空间、系统、设备、测点和计量边界的可追溯多对多语义关系；
4. 显式表达计量边界、已分配、未分配和待专家确认状态，不用空值或虚构对象隐藏缺口；
5. 支持草稿、校验、提交、撤回、批准、拒绝、立即生效、历史查询和新版本式回滚；
6. 通过建筑范围、角色、事务、修订号、审核快照和审计防止越权、部分生效和并发覆盖；
7. 对物理循环、跨建筑、失效引用、自关联、重复关系和待专业确认关系提供安全拒绝路径；
8. 当前生效关系同步到既有资产字段作为兼容投影，保证继承 HVAC 查询不出现双重权威；
9. 建筑进入治理模式后，阻止旧写入口直接修改关系字段；
10. 提供当前有效、指定历史版本、空间树、节点上下文、计量边界和未分配统计的分层查询；
11. 为未来园区级共享系统预留作用域扩展点，但首版保持建筑间严格隔离；
12. 使用合成事实验证软件闭环，并如实区分软件验证、专业确认和现场验收。

### 3.2 非目标

- 不开发或修改 Vue 页面、组件、状态和样式；
- 不建设 BIM、三维空间、设备拓扑叠加或热力图；
- 不实现能耗、碳排、能效、费用或损耗计算；
- 不实现比例、权重、公式、规则表达式或自动分摊；
- 不根据名称、设备类型、测点编码或现有指标猜测服务、连接、供回和计量关系；
- 不实现跨建筑或园区级关系发布；
- 不实现预约生效、追溯生效或历史日期回填；
- 不实现多草稿合并、跨建筑事务或跨实例配置广播；
- 不新增 Modbus、BACnet、NB-IoT 等南向协议；
- 不改变 Q0/Q1/Q2、设备参数、采集策略或公式的业务口径；
- 不把自动化测试描述为能源专家确认、真实设备验证或现场验收；
- 不修改冻结历史设计和计划来制造完成状态。

## 4. 已确认决策

| 决策点 | 首版结论 |
|---|---|
| 版本作用域 | 每栋建筑一个独立关系模型；首版只启用 `BUILDING` |
| 原子范围 | 物理空间、设备/测点结构归属、语义关系和计量边界统一版本生效 |
| 普通档案属性 | 名称、编码、面积、厂家等不纳入关系版本 |
| 草稿并发 | 每栋建筑同时只允许一个活动草稿；不同建筑可并行 |
| 生效时间 | 审核后显式立即生效；不支持预约和追溯生效 |
| 回滚 | 复制历史版本生成更高版本草稿，重新校验、审核和生效 |
| 现有数据接管 | 只复制当前明确外键事实，不推断业务语义或计量边界 |
| 旧接口 | 普通属性兼容；关系字段在治理模式下禁止直接修改 |
| 未分配 | 显式保存 `UNASSIGNED` 或 `PENDING_EXPERT`，不伪造占位对象 |
| 研发审核 | 研发配置可允许同一账号提交后批准，必须完整审计 |
| 生产审核 | 创建人或提交人不得批准自己的版本；错误自审配置拒绝启动 |
| 前端 | 首版只实现后端、MySQL、OpenAPI 和自动化测试 |
| 跨建筑 | 首版拒绝；只预留 `CAMPUS` 扩展值，不实现园区功能 |

## 6. 核心术语与事实边界

### 6.1 关系模型

关系模型是一个作用域内关系事实的稳定聚合头。首版每栋建筑最多有一个模型头，保存当前生效版本
指针、治理模式和并发修订号。模型头不是业务关系明细，也不直接保存空间树。

### 6.2 关系版本

关系版本是一栋建筑全部受治理关系的完整快照，不是局部补丁。版本包括：

- 全部空间父子关系；
- 全部设备空间和系统归属；
- 全部测点设备和系统归属；
- 全部显式语义关系；
- 全部计量边界及分配、未分配状态。

提交审核时冻结版本修订号和内容校验和。已提交内容不能继续编辑；修改必须撤回或创建新的草稿。

### 6.3 物理结构关系

物理结构关系回答“对象在哪里、属于哪个结构”。它们来自明确档案关系：

```text
空间 → 父空间
设备 → 所在空间
设备 → 所属系统
测点 → 所属设备
测点 → 所属系统
```

查询层可把这些事实投影为 `LOCATED_IN` 和 `PART_OF`，但显式语义关系表不重复保存相同事实。

### 6.4 显式语义关系

显式语义关系回答“对象业务上如何服务、测量、连接或传递能源”。首版登记以下稳定代码：

- `SERVES`；
- `MEASURES`；
- `CONNECTED_TO`；
- `SUPPLIES`；
- `RETURNS`。

关系代码可被软件识别，不代表端点类型、方向或现场事实已经专业确认。每种关系必须关联已批准的
关系类型配置，明确允许的源节点、目标节点、方向性、循环规则和专业依据。配置未确认时状态为
`PENDING_EXPERT`，包含该关系的版本不得生效。

### 6.5 计量边界

计量边界是能源计量责任范围，不等同于物理空间边界。它可以关联计量测点和覆盖对象，但首版不保存
分摊比例、权重或计算表达式。

计量分配状态固定为：

| 状态 | 语义 |
|---|---|
| `ASSIGNED` | 对象、计量点和边界关系已经由有效证据确认 |
| `UNASSIGNED` | 已知存在待分配事实，但当前没有可确认目标 |
| `PENDING_EXPERT` | 需要能源专家或硬件方确认边界、方向或对象 |
| `INVALID` | 引用失效、跨建筑或违反结构约束，不允许生效 |

`UNASSIGNED` 和 `PENDING_EXPERT` 必须保存原因码、说明和来源证据。缺少分配不能被自动解释为零能耗、
整栋建筑归属或平均分摊。

### 6.6 表计层级与计量方向

表计结构与“表计覆盖对象”分开建模。一块表可以覆盖多个空间、系统或设备，但在同一关系版本中只能
有一条结构事实，固定记录 `MAIN`、`SUB`、`INDEPENDENT`、`UNKNOWN` 角色、直接上级表计和
`INBOUND`、`OUTBOUND`、`BIDIRECTIONAL`、`UNKNOWN` 方向。

- `SUB` 必须引用同建筑、同版本中存在的上级表计；其他明确角色禁止填写上级；
- 自关联、直接或间接循环、同版本重复表计结构和跨建筑引用均拒绝；
- `UNKNOWN` 角色或方向只能以 `PENDING_EXPERT` 保存草稿，并阻止批准和生效；
- 软件不根据名称、能源类型或覆盖对象推断角色、方向和上下级关系；
- 结构事实进入版本复制、差异、校验、审核快照、生效、回滚、审计和当前/历史查询。

### 6.7 当前有效与兼容投影

新模型的当前生效版本是关系事实的权威来源。既有 `biz_space.parent_space_id`、
`biz_equipment.space_id/system_group_id` 和 `biz_data_point.equip_id/system_group_id` 在建筑进入治理模式后
只作为当前有效版本的兼容投影。投影更新与版本指针切换必须位于同一个 MySQL 事务。

## 7. 总体架构与数据流

```text
现有资产主档
  → 按建筑初始化明确关系草稿
  → 能源管理员或研发账号编辑草稿
       ├─ 物理结构关系
       ├─ 显式语义关系
       ├─ 计量边界、表计结构与未分配项
       └─ 平台 V1 Excel → 无写预检 → 确认后单事务写入指定草稿
  → 完整校验和影响摘要
  → 提交审核并冻结修订与校验和
  → 平台管理员批准或研发自审例外
  → 显式立即生效事务
       ├─ 再次校验基础版本和资产引用
       ├─ 写入审核与审计事实
       ├─ 更新兼容投影
       ├─ 退役旧有效版本
       └─ 切换当前有效版本指针
  → 当前/历史分层查询
```

任何校验、审计或投影步骤失败时，事务整体回滚，旧有效版本继续保持权威。

## 8. 数据模型

### 8.1 `biz_relation_model`

每个作用域的稳定模型头。

| 字段 | 约束与语义 |
|---|---|
| `model_id` | 主键，平台内部稳定 ID |
| `scope_type` | `BUILDING` 或预留 `CAMPUS`；首版运行时只接受 `BUILDING` |
| `scope_id` | 首版等于建筑 ID |
| `building_id` | 首版非空，参与组合外键和建筑权限校验 |
| `governance_mode` | `LEGACY` 或 `GOVERNED` |
| `active_version_id` | 当前有效版本，可空 |
| `draft_version_id` | 当前唯一活动草稿，可空 |
| `config_revision` | 模型并发修订号 |
| 创建、更新字段 | 操作人和 MySQL 时间事实 |

关键约束：

- `UNIQUE(scope_type, scope_id)`；
- 首版要求 `scope_type=BUILDING AND scope_id=building_id`；
- `CAMPUS` 请求统一返回“不支持的作用域”，不能静默降级为建筑；
- 同一模型最多一个活动草稿和一个当前有效版本。

### 8.2 `biz_relation_version`

建筑关系完整快照的版本头。

| 字段 | 约束与语义 |
|---|---|
| `version_id` | 主键 |
| `model_id`、`building_id` | 归属模型和建筑 |
| `version_no` | 模型内单调递增版本号 |
| `base_version_id` | 创建草稿时的当前有效版本，可空 |
| `copied_from_version_id` | 回滚或复制来源，可空 |
| `status` | `DRAFT`、`PENDING_REVIEW`、`APPROVED`、`EFFECTIVE`、`SUPERSEDED`、`REJECTED`、`WITHDRAWN` |
| `config_revision` | 草稿乐观锁修订号 |
| `submitted_revision` | 提交时冻结的修订号 |
| `snapshot_sha256` | 提交审核时的规范化快照校验和 |
| `change_reason` | 创建和提交必须提供的变更原因 |
| `effective_at` | 实际生效时间；首版只由立即生效事务写入 |
| 创建、提交、批准、生效字段 | 操作人和时间事实 |

关键约束：

- `UNIQUE(model_id, version_no)`；
- 版本内容在 `PENDING_REVIEW` 后不可修改；
- `EFFECTIVE` 和 `SUPERSEDED` 版本不可删除；
- 生效时 `base_version_id` 必须仍等于模型当前有效版本，否则返回版本冲突；
- 回滚版本必须使用新的 `version_no`，不能恢复旧版本状态。

### 8.3 `biz_relation_node`

统一登记可参与关系的业务对象，避免语义边直接使用无约束的多态字符串。

| 字段 | 约束与语义 |
|---|---|
| `node_id` | 主键 |
| `building_id` | 真实归属建筑 |
| `node_type` | `SPACE`、`SYSTEM`、`EQUIPMENT`、`POINT`、`METERING_BOUNDARY` |
| `business_object_id` | 对应主档或计量边界稳定 ID |
| `status` | `ACTIVE` 或 `RETIRED` |
| 创建、更新字段 | 操作人和时间事实 |

关键约束：

- `UNIQUE(building_id, node_type, business_object_id)`；
- 创建节点前必须验证原业务对象存在、未逻辑删除且属于同一建筑；
- 节点被有效版本引用时不得退役；
- 请求中的 `buildingId` 不能覆盖节点从数据库解析出的真实归属。

### 8.4 `biz_space_parent_version_item`

保存版本内完整空间树快照：`version_id`、`building_id`、`space_id`、`parent_space_id` 和排序值。

关键约束：

- 一个版本内每个空间最多一条父级记录；
- 顶级空间的 `parent_space_id` 为 `NULL`，建筑是隐式根；
- 父子空间必须属于同一建筑；
- 全图必须无自环和深层循环；
- 多个顶级空间允许存在，均挂在隐式建筑根下；
- 版本必须覆盖该建筑所有未删除空间，不能通过遗漏制造孤立空间。

### 8.5 `biz_asset_assignment_version_item`

保存设备和测点的结构归属快照。

| 对象 | 必需归属 |
|---|---|
| 设备 | 一个空间、一个系统 |
| 普通设备测点 | 一个设备、一个系统；必须与设备系统一致 |
| 建筑环境测点 | 不绑定设备；系统是否为空沿用当前明确档案事实 |

设备不能借计量 `UNASSIGNED` 状态绕过现有空间和系统完整性。任何结构关系都必须使用同建筑活动节点。

### 8.6 `biz_semantic_relation_version_item`

| 字段 | 约束与语义 |
|---|---|
| `relation_item_id` | 主键 |
| `version_id`、`building_id` | 所属版本和建筑 |
| `relation_type` | 已登记关系代码 |
| `source_node_id`、`target_node_id` | 同建筑节点 |
| `source_type` | `MANUAL`、`IMPORT`、`SYSTEM_MIGRATION` |
| `evidence_reference` | 脱敏证据引用；不保存凭据或个人路径 |
| `confirmation_status` | `CONFIRMED` 或 `PENDING_EXPERT` |
| `description` | 可空业务说明 |

关键约束：

- 禁止源节点等于目标节点；
- 禁止同版本内完全重复的关系；
- 源、目标、版本必须属于同一建筑；
- `PENDING_EXPERT` 关系允许保存在草稿，但阻止版本批准和生效；
- `CONNECTED_TO` 可以形成网络环；其他关系的循环规则由已确认的关系类型配置决定；
- 物理结构已经投影出的 `LOCATED_IN` 和 `PART_OF` 不在本表重复保存。

首版关系项不单独配置预约或追溯有效期。关系有效区间统一由所属版本的 `effective_at` 和被下一版本
替代的时间确定，避免版本时间与单条关系时间形成双重权威。

### 8.7 `biz_metering_boundary`

保存建筑内稳定计量边界身份：边界 ID、建筑 ID、边界编码、名称、能源类型、状态和普通审计字段。
能源类型和业务定义必须有专业依据；未确认时边界可以作为草稿对象存在，但不能进入有效版本。

### 8.8 `biz_metering_assignment_version_item`

保存版本内计量边界、计量点和覆盖节点的显式分配事实。

| 字段 | 约束与语义 |
|---|---|
| `assignment_item_id` | 主键 |
| `version_id`、`building_id` | 所属版本和建筑 |
| `metering_boundary_id` | 可空；未分配时为空 |
| `meter_point_node_id` | 计量测点，可空但必须显式说明原因 |
| `target_node_id` | 被计量或覆盖对象，可空 |
| `allocation_status` | `ASSIGNED`、`UNASSIGNED`、`PENDING_EXPERT`、`INVALID` |
| `reason_code`、`reason_text` | 未分配、待确认或非法原因 |
| `evidence_reference` | 脱敏专业或现场证据引用 |

首版不提供 `ratio`、`weight`、`formula` 或 `rule_expression` 字段。需要分摊时必须在后续独立设计中
由能源专家确认语义、精度、总和约束、损耗和历史重算边界。

### 8.9 `biz_meter_structure_version_item`

保存版本内独立的表计结构事实：关系版本、建筑、计量边界、表计测点、角色、上级表计测点、计量
方向、确认状态、原因、证据、说明、来源和审计字段。同一版本的同一表计测点只能登记一次；数据库
外键保证表计、上级表计、计量边界与版本归属，领域校验补充角色、方向、循环和待专家确认规则。

### 8.10 `biz_relation_review_request`

审核申请保存版本 ID、建筑 ID、请求序号、提交修订号、快照校验和、状态、提交人、审核人、审核
理由和时间。审核状态固定为 `PENDING`、`APPROVED`、`REJECTED`、`WITHDRAWN`。

普通生产规则要求创建人和提交人均不能审核自己的版本。研发自审例外仍必须生成独立审核申请，
记录同一提交人和审核人，并在审计中写入 `SELF_APPROVAL_DEV_MODE`。

### 8.11 `biz_relation_validation_issue`

保存最近一次显式校验发现的问题，至少包含版本、问题级别、问题代码、对象、消息和检测时间。

| 级别 | 行为 |
|---|---|
| `ERROR` | 阻止提交、批准和生效 |
| `PENDING_EXPERT` | 允许保存草稿，阻止批准和生效 |
| `WARNING` | 可提交，但审核必须填写处理理由 |

每次草稿修改后旧校验结果失效；提交时必须重新生成完整校验结果和快照校验和。

### 8.12 `biz_relation_audit_log`

追加式记录模型、版本、关系、边界、审核和生效操作。至少保存：审计 ID、建筑 ID、操作人、操作、
对象类型和 ID、前后状态、版本 ID、关联请求 ID、原因、结果、时间和脱敏摘要。

审计写入与治理操作位于同一事务。审计失败时业务操作整体失败；审计记录不提供普通删除或修改入口。

## 9. 生命周期与并发

### 9.1 状态机

```text
DRAFT → PENDING_REVIEW → APPROVED → EFFECTIVE → SUPERSEDED
   │           ├→ REJECTED
   └───────────└→ WITHDRAWN
```

- `DRAFT`：创建人可在授权建筑内修改；
- `PENDING_REVIEW`：内容冻结，等待审核；
- `APPROVED`：审核通过但尚未显式生效；
- `EFFECTIVE`：当前权威关系版本；
- `SUPERSEDED`：被新版本替代，历史只读；
- `REJECTED`、`WITHDRAWN`：历史保留，不进入运行查询。

### 9.2 并发规则

- 草稿修改必须提交 `expectedRevision`；不匹配返回 409；
- 同一建筑只能有一个活动草稿和一个待处理审核申请；
- 提交冻结 `submittedRevision` 和 `snapshotSha256`；
- 审核和生效必须再次比较冻结修订、校验和及基础有效版本；
- 资产在草稿期间被停用、删除或改变归属时，生效前重新校验并拒绝过期草稿；
- 幂等键只能复用同一用户、同一建筑和完全相同的规范化请求，不能越过草稿可见性和审核边界。

### 9.3 生效事务

生效必须在一个 MySQL 事务内：

1. 锁定模型头、目标版本、审核申请和当前有效版本；
2. 校验版本状态、基础版本、修订号、快照校验和和建筑范围；
3. 重新验证全部资产引用和阻塞问题；
4. 更新既有关系字段兼容投影；
5. 将旧有效版本改为 `SUPERSEDED`；
6. 将目标版本改为 `EFFECTIVE`；
7. 切换 `active_version_id`、清空草稿指针并递增模型修订；
8. 写入审核和生效审计。

任一步失败都必须回滚，不能出现“部分关系已更新、版本指针未切换”的混合状态。

### 9.4 回滚

回滚入口接收目标历史版本、变更原因和 `expectedModelRevision`，复制目标版本形成新的 `DRAFT`。
新草稿继续经过完整校验、审核和生效。历史版本 ID、版本号、审核和审计均不修改。

## 10. 角色、建筑范围与研发自审

### 10.1 角色矩阵

| 操作 | BUILDING_OWNER | ENERGY_MANAGER | PLATFORM_ADMIN | THIRD_PARTY |
|---|---:|---:|---:|---:|
| 读取授权建筑当前有效模型 | 是 | 是 | 是 | 否 |
| 读取授权建筑历史和差异 | 否 | 是 | 是 | 否 |
| 创建、编辑和校验草稿 | 否 | 是 | 否 | 否 |
| 提交、撤回草稿 | 否 | 是 | 否 | 否 |
| 批准、拒绝和执行生效 | 否 | 否 | 是 | 否 |
| 创建回滚草稿 | 否 | 是 | 否 | 否 |
| 读取审核与审计 | 否 | 是 | 是 | 否 |

`PLATFORM_ADMIN` 拥有全建筑读取、审核和生效范围，但不参与普通草稿编辑，且仍不能批准自己创建
或提交的版本。普通角色必须同时通过角色校验和 `BuildingScopeService` 建筑范围校验。

### 10.2 防越权规则

- 列表查询必须以服务端可访问建筑集合过滤；
- 单资源查询先从数据库解析真实建筑，再执行范围校验；
- 越权资源不能通过请求中的 `buildingId`、节点 ID 或版本 ID 绕过检查；
- 关系两端必须属于版本建筑，即使操作者同时拥有两栋建筑权限也不能建立跨建筑边；
- `THIRD_PARTY` 只保留现有 `/open-api/**` 范围，不进入治理 API。

### 10.3 研发自审例外

模块提供默认关闭的研发自审配置。启用时：

- 仍必须先提交，再调用批准和生效入口；
- 同一账号可以作为提交人和审核人；
- 批准理由必填；
- 审计追加 `SELF_APPROVAL_DEV_MODE`，查询响应返回研发例外标记；
- 自动化测试必须同时覆盖研发允许和生产拒绝路径。

生产环境强制执行提交人与审核人分离。部署环境分类必须由显式配置提供；当环境为生产且研发自审
开关为真时，应用启动校验必须失败。不能依赖操作人员上线前手工记忆关闭，也不能通过角色叠加绕过。

## 11. 校验规则

### 11.1 结构硬校验

- 建筑、空间、系统、设备、测点和边界存在且未逻辑删除；
- 所有版本项、节点和关系属于同一建筑；
- 空间不能以自身或后代为父节点；
- 所有空间从隐式建筑根可达，允许多个顶级空间；
- 设备必须有且只有一个空间和一个系统；
- 普通设备测点必须绑定同建筑、同系统设备；
- 环境测点继续遵守现有无设备绑定规则；
- 同版本语义边不能自关联或完全重复；
- 已批准关系类型配置必须匹配源、目标节点类型和方向规则；
- 有效版本或待审核版本引用的对象不能通过资产接口删除。

### 11.2 专业阻塞校验

以下内容没有确认依据时保存为 `PENDING_EXPERT`，阻止批准和生效：

- 服务范围和服务方向；
- 设备、系统和管网连接关系；
- 供水、回水、供电等流向；
- 计量边界能源类型和覆盖对象；
- 计量点方向、总分表关系和未分配处理；
- 任何比例、权重、损耗、分摊或归因规则。

### 11.3 跨建筑和循环

- 首版任何跨建筑结构或显式语义关系均返回稳定错误码并阻止保存；
- 层级型结构必须全图无环；
- `CONNECTED_TO` 可以形成网络环，只拒绝自环和重复边；
- `SUPPLIES`、`RETURNS` 可能表示闭式系统，不在缺少专业规则时硬编码全图无环；
- 关系类型配置可在专业确认后增加类型特定循环约束，但不能改变既有有效版本语义。

## 12. 现有数据接管与旧接口收口

### 12.1 分建筑受控初始化

Flyway 只创建结构，不在数据库迁移中自动猜测或发布业务关系。能源管理员通过幂等初始化入口按已授权建筑
生成首个草稿，复制以下明确事实：

- `biz_space.parent_space_id`；
- `biz_equipment.space_id` 和 `system_group_id`；
- `biz_data_point.equip_id` 和 `system_group_id`；
- 对应主档和逻辑删除状态。

迁移来源统一标记为 `SYSTEM_MIGRATION` 或 `LEGACY_PROJECTION`。不生成 `SERVES`、`MEASURES`、
`CONNECTED_TO`、`SUPPLIES`、`RETURNS`、计量边界或分摊关系。

初始化发现循环、跨建筑、孤立引用或删除对象时，问题进入校验结果，草稿不能提交或生效；不得静默
修正、删除或重挂关系。

### 12.2 治理模式切换

- 没有有效关系版本时，建筑保持 `LEGACY`，现有关系字段继续作为当前事实；
- 首个版本生效事务完成后，建筑切换为 `GOVERNED`；
- 切换后新关系版本成为权威，旧字段只作当前投影；
- 不支持从 `GOVERNED` 自动退回 `LEGACY`；灾难恢复必须使用受控备份或新版本回滚。

### 12.3 旧接口收口

现有资产 API 和旧 Controller 最终必须共享同一应用服务边界：

- 普通档案属性仍按当前权限修改；
- 空间父级、设备空间/系统、测点设备/系统等关系字段在 `GOVERNED` 模式下拒绝直接变化；
- 请求值与当前投影相同可按未变化处理；
- 实际关系变化返回 `RELATION_GOVERNANCE_REQUIRED`；
- 有效版本或活动草稿引用的资产不能删除；
- 不能只封堵 `/v1/assets` 而遗漏旧 `/space`、`/equipment`、`/datapoint` 等入口。

## 13. API 契约

### 13.1 管理入口

新接口统一位于 `/v1/relation-models`，使用 DTO，不直接暴露实体。

| 用途 | 建议契约 |
|---|---|
| 查询建筑模型和状态摘要 | `GET /v1/relation-models?buildingId=...` |
| 分建筑初始化明确关系草稿 | `POST /v1/relation-models/{buildingId}/initialize` |
| 创建普通或回滚草稿 | `POST /v1/relation-models/{buildingId}/versions` |
| 查询版本和差异 | `GET /v1/relation-models/{buildingId}/versions/**` |
| 编辑空间父级和结构归属 | `PUT /v1/relation-models/versions/{versionId}/structure/**` |
| 编辑显式语义关系 | `POST/PUT/DELETE /v1/relation-models/versions/{versionId}/relations/**` |
| 编辑计量边界和分配状态 | `POST/PUT/DELETE /v1/relation-models/versions/{versionId}/metering/**` |
| 编辑表计结构 | `POST/PUT/DELETE /v1/relation-models/versions/{versionId}/metering/structures/**` |
| 执行完整校验 | `POST /v1/relation-models/versions/{versionId}/validate` |
| 提交或撤回 | `POST /v1/relation-models/versions/{versionId}/submit|withdraw` |
| 审核 | `POST /v1/relation-models/review-requests/{requestId}/approve|reject` |
| 显式立即生效 | `POST /v1/relation-models/versions/{versionId}/activate` |
| 查询审核和审计 | `GET /v1/relation-models/reviews`、`GET /v1/relation-models/audits` |

写请求必须携带 `expectedRevision` 或 `expectedModelRevision`；具有重试风险的创建、提交、批准、生效和
回滚入口必须接受幂等键。

### 13.2 分层查询入口

| 用途 | 建议契约 |
|---|---|
| 当前空间树 | `GET /v1/relation-models/{buildingId}/effective/space-tree` |
| 节点上下文 | `GET /v1/relation-models/{buildingId}/effective/nodes/{nodeType}/{nodeId}/context` |
| 当前计量边界 | `GET /v1/relation-models/{buildingId}/effective/metering-boundaries` |
| 当前或历史表计结构 | `GET /v1/relation-models/{buildingId}/effective/metering-structures`、`GET /v1/relation-models/{buildingId}/versions/{versionId}/query/metering-structures` |
| 表计直接上下级 | `GET /v1/relation-models/{buildingId}/effective/meters/{meterPointNodeId}/hierarchy` 及对应历史版本入口 |
| 未分配和待确认项 | `GET /v1/relation-models/{buildingId}/effective/issues` |
| 历史版本空间树或节点上下文 | `GET /v1/relation-models/{buildingId}/versions/{versionId}/query/**` |

所有查询响应必须携带：

- `buildingId`；
- `versionId`、`versionNo`；
- `effectiveAt`；
- `modelRevision`；
- 查询层级和截断信息；
- 未分配、待确认、错误和警告摘要。

空间树和语义图分开返回。节点上下文默认深度为 1，允许的最大深度由配置限制；边列表必须分页，
禁止无界递归和一次返回整栋建筑所有语义关系。

### 13.3 平台标准 Excel 导入

首版只接受平台发布的 `templateVersion=V1` 标准模板，按表头名称解析，不按列序号绑定。模板包含
`填写说明` 和 `计量关系`，模板不预置真实业务数据；任何测试示例均明确标记为合成数据。

| 用途 | 契约 |
|---|---|
| 下载模板 | `GET /v1/relation-models/metering-import/template?templateVersion=V1` |
| 无写预检 | `POST /v1/relation-models/metering-import/preflight`，multipart 携带建筑、目标草稿、预期修订和文件 |
| 确认导入 | `POST /v1/relation-models/metering-import/confirm`，在预检参数基础上必须携带 `Idempotency-Key` |

解析适配器只处理模板契约和标准化映射；对象归属、表计结构、计量分配、待确认和循环规则复用关系
领域校验。预检不创建版本、不修改草稿；确认导入重新解析和校验，任一错误整体回滚，只新增或更新
指定 `DRAFT`，一次批次只递增一次修订，不自动提交、审核或生效。宏、公式、外部链接、重复或缺失
表头、不支持版本、超限文件/行/文本均明确拒绝。V1 发布后保持兼容，核心字段语义变化通过新的版本
适配器演进，不静默改变 V1。

### 13.4 稳定错误码

首版至少提供：

- `RELATION_UNAUTHORIZED`；
- `RELATION_FORBIDDEN`；
- `RELATION_NOT_FOUND`；
- `RELATION_VALIDATION_FAILED`；
- `RELATION_VERSION_CONFLICT`；
- `RELATION_REVIEW_CONFLICT`；
- `RELATION_CROSS_BUILDING`；
- `RELATION_CYCLE_DETECTED`；
- `RELATION_PENDING_EXPERT`；
- `RELATION_REFERENCE_CONFLICT`；
- `RELATION_GOVERNANCE_REQUIRED`；
- `RELATION_SCOPE_UNSUPPORTED`。

## 14. 整体空间状态呈现契约

首版不开发页面，但后端查询必须支持后续以“物理空间树为主、语义关系和计量状态为侧面信息”的
方式呈现，不能把全部关系混为一棵树。

```text
建筑
├─ 楼层 / 区域 / 房间
│  ├─ 所在设备
│  ├─ 所属与服务系统
│  ├─ 测点及完整度
│  └─ 计量边界、未分配和待确认摘要
└─ 问题汇总
   ├─ 未分配计量项
   ├─ 待专家确认关系
   └─ 结构或引用冲突
```

默认只返回当前有效版本。草稿、待审核和历史版本必须通过明确的版本入口查询，不能把未生效内容
混入当前空间状态。关系治理状态与设备实时运行状态分开；`DRAFT`、`PENDING_REVIEW`、
`PENDING_EXPERT` 不代表设备离线、故障或能耗异常。

## 15. 跨建筑与未来园区级关系

### 15.1 首版边界

首版建筑之间严格隔离：

- 每栋建筑独立草稿、审核、生效和回滚；
- 建筑 A 的事务失败或回滚不影响建筑 B；
- 同时拥有多栋建筑权限也不能建立跨建筑关系；
- 多建筑统计通过查询聚合完成，不创建虚假共享节点。

### 15.2 未来适用条件

只有出现真实共享对象或计量责任时，才适合独立设计 `CAMPUS` 关系版本，例如：

- 集中能源站服务多栋建筑；
- 园区总电表、光伏、储能或变配电系统覆盖多栋建筑；
- 供回水或能源管网跨越多栋建筑；
- 能耗、碳排或费用需要正式跨建筑归属或分摊。

启用前至少需要：

1. 相关建筑均已完成单建筑关系闭环并有有效版本；
2. 共享资产、系统和计量点身份明确；
3. 取得真实系统图、计量图、点表或现场核查证据；
4. 能源专家确认边界、方向、损耗和分摊规则；
5. 明确园区编辑、审核和全部关联建筑授权责任；
6. 具备跨建筑影响分析、原子发布和回滚设计。

`CAMPUS` 不是首版已实现能力。当前只预留枚举和模型扩展位置，不能创建园区模型、节点或关系。

## 16. 外部输入与阻塞项

| 来源 | 后续必须提供或确认的内容 | 当前处理 |
|---|---|---|
| 能源专家 | 计量边界、能源类型、总分表、服务范围、供回方向、损耗和分摊规则 | 保持 `PENDING_EXPERT`，不允许生效 |
| 硬件/现场人员 | 设备清单、系统图、点表、计量图、连接和方向证据 | 只接受明确证据，不按名称推断 |
| 产品/业务方 | 单建筑最大空间、设备、测点、边界和关系规模 | 性能验收数值暂不冻结 |
| 部署负责人 | 研发、测试、生产环境分类及生产自审禁用配置 | 生产错误配置拒绝启动 |
| 软件开发 | 模型、事务、权限、接口、兼容投影、审计和测试 | 按本文实现安全软件闭环 |

这些外部输入不阻塞表结构、状态机、权限框架和安全拒绝路径开发，但阻塞专业关系发布、数值化性能
验收、真实业务验收和现场验收。

## 17. 风险与应对

| 风险 | 应对 |
|---|---|
| 新旧两套资产写入口绕过治理 | 在共享应用服务层封堵关系字段变化，并逐个覆盖新旧 Controller 测试 |
| 兼容投影和版本指针不一致 | 同一 MySQL 事务锁定、更新和审计，失败保持旧版本 |
| 草稿期间资产被删除或改变 | 提交和生效两次全量校验，活动引用阻止删除 |
| 语义关系被软件猜测 | 类型配置和证据门禁；`PENDING_EXPERT` 阻止生效 |
| 空值被误认为无能耗或默认归属 | 显式 `UNASSIGNED/PENDING_EXPERT`，查询返回原因和数量 |
| 跨建筑越权或信息泄露 | 资源真实归属校验；首版所有跨建筑边统一拒绝 |
| 图查询规模失控 | 树与图分离、默认一层、最大深度、分页和索引 |
| 单活动草稿阻塞长期编辑 | 提供撤回、复制和差异；首版不承担复杂合并风险 |
| 研发自审配置带入生产 | 默认关闭、生产启动拒绝、审计标记和自动化门禁 |
| 初始化数据已有脏关系 | 生成不可生效草稿和问题清单，不自动纠正或删除 |
| 园区预留被误报为已实现 | API 首版拒绝 `CAMPUS`，状态和文档明确标记计划中 |
| Excel 被误作专业事实 | 只发布平台 V1 输入契约，预检不写库，未知项保持 `PENDING_EXPERT` |
| 恶意或超大工作簿消耗资源 | 限制格式、字节、行数和文本长度，拒绝宏、公式、外部链接和异常单元格 |

## 18. 验收标准

### 18.1 自动化软件验收

1. Flyway 新迁移可从空库完整执行，并在隔离 MySQL 8 上验证结构、外键、索引和约束；
2. 能源管理员只能在已授权建筑执行初始化；初始化只复制明确外键，重复调用幂等，不生成专业语义或计量边界；
3. 单建筑单草稿约束、乐观锁、审核快照和幂等键能够阻止并发覆盖；
4. 草稿、提交、撤回、批准、拒绝、生效、退役和新版本式回滚状态转换正确；
5. 研发配置允许同账号提交后批准，生产配置禁止自审且错误配置拒绝启动；
6. 普通角色、建筑业主、能源管理员、平台管理员和第三方接口账号均符合角色矩阵；
7. 越权、跨建筑、循环、自关联、重复边、孤立引用和删除对象均返回稳定错误；
8. `PENDING_EXPERT` 可以留在草稿，但不能批准或生效；
9. `UNASSIGNED` 和待确认项能够查询、统计并返回原因，不被解释为默认分配；
10. 生效事务失败、审计失败或兼容投影失败时，旧有效版本和旧投影保持不变；
11. 当前有效、历史版本、空间树、节点上下文、边界、问题和差异查询携带完整版本证据；
12. 建筑进入 `GOVERNED` 后，新旧资产写入口均不能直接改变关系字段；
13. 既有 HVAC 查询仍能读取与当前有效版本一致的兼容投影；
14. `CAMPUS` 请求被稳定拒绝，不能建立跨建筑关系；
15. 表计角色、直接上下级和计量方向参与版本差异、审核快照、回滚、审计和分层查询；
16. 表计自关联、多级循环、跨建筑、重复结构和不合法角色/方向稳定拒绝；
17. V1 模板可下载且列顺序调整后仍按表头识别，宏、公式、不支持版本、缺失表头和超限输入稳定拒绝；
18. 预检不写业务数据，确认导入复用相同校验、校验预期修订与幂等键并保持单事务原子性；
19. OpenAPI、DTO、状态码和错误码契约有自动化测试。

### 18.2 文档与质量门禁

- 核对本文、`PROJECT_GUIDE.md`、`PROJECT_STATUS.md` 与当前代码状态边界；
- 生产 Java 代码实现时使用代码注释质量规则；
- 按仓库验证矩阵运行相关单元、集成、API 契约、完整 Maven 和必要的 MySQL 迁移验证；
- 运行 `git diff --check`、Markdown 链接检查和仓库 Guardrail；
- 不用历史测试结果代替本次验证。

### 18.3 不属于软件自动验收的内容

- 能源专家对计量边界、关系方向和分摊规则的确认；
- 真实设备、系统、点表和计量图映射；
- 真实建筑或园区业务验收；
- 现场网络、硬件、长期运行和数据完整性验收；
- 园区级跨建筑关系；
- 缺少规模输入时的数值化性能 SLA。

## 19. 实施顺序

设计批准后的实现顺序固定为：

1. 新建独立任务分支并通过仓库预检；
2. 建立关系模型、版本、节点、结构、语义、计量、审核、校验和审计表；
3. 实现领域模型、状态机、建筑权限、并发和研发自审启动门禁；
4. 实现分建筑受控初始化和完整校验；
5. 实现审核、生效事务、兼容投影和新版本式回滚；
6. 收口新旧资产关系写入口；
7. 实现管理 API、分层查询和 OpenAPI；
8. 完成 H2/Mock/Stub 隔离测试和 MySQL 8 迁移验证；
9. 更新当前项目状态，明确软件候选与专业、现场未验证边界；
10. 在干净任务中基于固定基线和原始证据进行独立候选验收。

## 20. 完成定义

只有同时满足以下条件，才能称为“关系治理软件活动候选实现完成”：

- 本文范围内的数据模型、状态机、权限、校验、生效、回滚、审计、兼容投影和查询均已实现；
- 所有范围匹配自动化门禁和隔离 MySQL 8 迁移验证通过；
- 旧接口无法绕过关系治理；
- 未确认关系和计量项保持安全拒绝或显式未分配；
- 当前状态文档已经同步；
- 完成独立候选验收。

即使达到以上条件，也只能声明软件候选闭环完成。没有能源专家资料和真实现场映射时，不能声明
专业关系、计量分摊、真实业务或现场验收完成；没有独立的未来设计和验证时，不能声明跨建筑园区
关系已经实现。
