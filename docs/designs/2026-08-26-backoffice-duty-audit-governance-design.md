# 后台职责分离与统一审计证据治理设计

> **文档状态：活动候选设计，方向、范围、职责边界、审批规则、审计契约、查询、导出、保留与清理机制已经用户确认；公共职责、敏感申请及首批系统管理操作已形成候选实现，整体设计尚未实现完成、尚未独立验证、尚未批准为当前正式基线。**
>
> 当前权威基线仍以 [`PROJECT_STATUS.md`](../../PROJECT_STATUS.md)、当前代码和自动化测试为准。
> 本候选只有在完成实现、范围匹配的自动化验证、独立验收并经用户批准后，才能转为正式版本能力。

## 1. 结论

阶段一采用“业务角色、后台职责、建筑范围、领域状态”四个相互独立的授权维度：

```text
四类正式业务角色
+ 独立后台职责
+ 服务端建筑范围
+ 领域对象状态与归属
→ 是否允许执行具体操作
```

四类正式角色保持不变，不通过新增第五、第六类角色承载审核、审计或导出职责。后台职责按用户独立
授予，且不写入 JWT；所有敏感写操作必须经过“提交—审核”两步，关闭普通直接发布。研发阶段因只有
一名开发人员，允许同一账号先提交再批准，但不能跳过任一步骤；生产环境强制禁止自审，错误配置时
应用拒绝启动。

公共机制只统一以下基础边界：

- 后台职责授权与动态撤销；
- 服务端建筑范围校验；
- 敏感系统操作的通用提交与审核外壳；
- 审计证据公共字段、追踪标识、拒绝原因和查询契约；
- 导出权限、脱敏、保留策略、证据保全与自动到期清理。

领域模块继续拥有自己的草稿、版本、差异、专业校验、生效、回滚和事务。公共机制不替代领域审核
状态机，不复制领域完整快照，也不建设集中采集全部应用日志的大一统日志平台。

## 2. 背景与当前证据

当前仓库已经具备：

- JWT 登录、Redis Token 状态、四类正式角色和方法级角色鉴权；
- 用户建筑授权、平台管理员全建筑范围和服务层建筑范围校验；
- 角色、菜单、用户与建筑访问申请的后台管理基础；
- 采集策略、质量使用策略、设备参数和设备接入的模块内审计表；
- 采集策略、质量使用策略和设备参数的领域审核状态机；
- 统一的基础 HTTP 状态、脱敏异常响应和部分模块机器错误码。

主要证据入口：

- [`FormalRole.java`](../../src/main/java/com/platform/security/FormalRole.java)：四类正式业务角色；
- [`JwtService.java`](../../src/main/java/com/platform/security/JwtService.java)：JWT 只保存身份和角色；
- [`JwtAuthenticationFilter.java`](../../src/main/java/com/platform/security/JwtAuthenticationFilter.java)：Token、正式角色和 Redis 登录态校验；
- [`BuildingScopeServiceImpl.java`](../../src/main/java/com/platform/system/service/impl/BuildingScopeServiceImpl.java)：后端建筑范围边界；
- [`BuildingAccessServiceImpl.java`](../../src/main/java/com/platform/system/service/impl/BuildingAccessServiceImpl.java)：当前建筑授权申请与审核；
- [`GlobalExceptionHandler.java`](../../src/main/java/com/platform/framework/exception/GlobalExceptionHandler.java)：当前脱敏异常响应；
- [`V17__mysql_collection_policy_governance.sql`](../../src/env/init/V17__mysql_collection_policy_governance.sql)、
  [`V18__mysql_quality_usage_policy_governance.sql`](../../src/env/init/V18__mysql_quality_usage_policy_governance.sql)、
  [`V20__mysql_device_parameter_governance.sql`](../../src/env/init/V20__mysql_device_parameter_governance.sql)：现有领域审核与审计表。

当前主要缺口是：

- `PLATFORM_ADMIN` 同时承载人员、角色、菜单、建筑授权和部分领域发布，缺少独立后台职责；
- 角色、菜单、职责分配和部分系统敏感操作没有统一提交、审核和审计证据；
- 采集策略和质量使用策略仍存在管理员直接发布入口，与本次确认的统一双步骤规则冲突；
- 各审计表字段、结果枚举、索引和查询权限不一致；
- 采集和质量审计查询存在全表加载后在内存过滤、排序和分页的实现，不适合作为统一查询基础；
- 设备接入审计缺少建筑、行为主体类型、拒绝原因和追踪标识；
- 当前没有覆盖模块、建筑、操作者、对象、时间和结果的统一审计查询；
- 当前 HTTP 响应没有统一 `traceId`，401/403 的内部拒绝原因也没有形成可检索安全证据；
- 当前没有审计导出、证据保全、保留策略版本和统一审计到期清理机制。

## 3. 目标与非目标

### 3.1 目标

1. 保持四类正式业务角色稳定，建立按用户独立授予的后台职责；
2. 让角色、职责、建筑范围和领域状态共同决定操作权限，任何一层都不能替代其他层；
3. 关闭普通直接发布，统一执行提交后审核；
4. 研发环境允许同账号完成两步操作，生产环境强制提交人与审核人分离；
5. 为角色、菜单、建筑授权、职责分配、保留策略和例外删除建立系统敏感操作闭环；
6. 为领域模块提供公共职责校验、审计证据字段、追踪和查询接入规范；
7. 支持按模块、建筑、操作者、对象、时间和结果检索审计证据；
8. 对认证失败、角色不足、职责不足、建筑越权、状态冲突和自审拒绝保留稳定内部原因；
9. 建立受控导出、字段脱敏、保留策略审批、证据保全和自动到期清理；
10. 保持领域业务状态机和业务事务的所有权，不重复保存领域完整事实；
11. 使用增量迁移接管已有审计，不删除或改写历史证据；
12. 为后续模块提供可复用接口，同时控制首版复杂度和存储重复。

### 3.2 非目标

- 不开发或修改 Vue3 页面、组件、路由、状态和样式；
- 不设计告警业务阈值、告警聚合、处置工单或外部消息推送；
- 不做日志聚类、异常行为分析、用户画像、威胁评分或机器学习；
- 不接管普通调试日志、性能日志、设备时序或 MQTT 报文；
- 不建设 Elasticsearch、ClickHouse、Kafka 或独立日志微服务；
- 不把全部领域审核迁移到一个通用状态机；
- 不把菜单可见性当作后端授权；
- 不把平台管理员角色自动等同于审核、审计查询或导出职责；
- 不实现跨数据库全文检索、任意 JSON 条件或无限时间范围查询；
- 不在软件中推断上线主体的等保、行业监管、合同和档案制度；
- 不把软件自动化测试描述为法律合规、渗透测试或生产审计验收。

## 4. 已确认决策

| 决策点 | 首版结论 |
|---|---|
| 正式角色 | 保留 `BUILDING_OWNER`、`ENERGY_MANAGER`、`THIRD_PARTY`、`PLATFORM_ADMIN` 四类角色 |
| 后台职责 | 使用独立用户职责，不扩充四类业务角色 |
| JWT | 继续只保存用户身份和正式角色；职责与建筑范围不写入 JWT |
| 普通发布 | 关闭管理员直接发布，所有敏感发布统一先提交、后审核 |
| 研发审核 | 允许同一账号提交后批准，必须保留完整两步状态与 `SELF_APPROVAL_DEV_MODE` 证据 |
| 生产审核 | 提交人不得审核自己的申请；生产开启自审时应用拒绝启动 |
| 公共审批 | 只承载系统级敏感命令；领域模块保留自己的审核状态机 |
| 审计存储 | 保留领域审计表，通过公共字段和查询适配器统一检索；不新建重复的全量中央审计副本 |
| 审计查询 | 统一按模块、建筑、操作者、对象、时间和结果过滤，使用游标分页 |
| 安全拒绝 | 客户端只收到稳定脱敏机器码；内部审计保存细分原因和 `traceId` |
| 导出 | 独立导出职责、继承建筑范围、默认脱敏、完整审计；首版不提供未脱敏导出 |
| 保留策略 | 新增、修改、启停必须提交审核；策略生效后到期批次自动执行，无需逐批审批 |
| 例外删除 | 提前删除、强制删除和手工指定范围删除必须单独审核 |
| 证据保全 | 保全中的记录不自动清理；设置和解除保全均受控，解除必须审核 |
| 研发清理 | 仅使用虚拟或脱敏数据时默认关闭自动清理；接入真实数据后不得继续无限保留 |
| 生产候选期限 | 安全相关网络日志不少于六个自然月；治理和导出审计候选为一年 |
| 清理证据 | 清理批次证据不随被清理审计删除，长期保留；需要时去标识化人员信息 |
| 首版容量基线 | 全系统审计事件每日不超过 10 万条；该数值是设计与验收基线，不是达到后丢弃日志的限流阈值 |
| 后期扩展 | 预留审计写入、查询和保留处理接口；超过容量基线时可替换高频安全审计存储，不改领域状态机 |

| 已发布版本和审计不可由业务删除 | 保留 | 到期清理由独立保留策略执行，不开放领域普通删除入口 |
| 审计与业务写入同事务 | 保留 | 领域表继续作为本领域权威审计事实 |
| 历史设计保持冻结 | 保留 | 不回写旧设计；由本文显式记录替代关系 |
| MySQL 保存结构化业务事实 | 保留 | 职责、系统审核、审计索引字段、保留和清理证据位于 MySQL |
| TDengine 保存时序事实 | 保留 | 公共审计不写入 TDengine，也不负责时序保留 |

## 6. 四维授权模型

### 6.1 正式角色

正式角色继续表达用户在产品中的业务身份：

- `BUILDING_OWNER`：已授权建筑的业务查看；
- `ENERGY_MANAGER`：已授权建筑的能源和配置治理；
- `THIRD_PARTY`：受限开放接口；
- `PLATFORM_ADMIN`：平台系统管理身份和全建筑数据范围。

角色只提供进入某类业务的资格。`PLATFORM_ADMIN` 可以拥有全建筑范围，但不能仅凭角色执行审核、
审计导出、保留策略变更或例外删除。

### 6.2 后台职责

首版职责键固定为：

| 职责键 | 允许能力 |
|---|---|
| `BACKOFFICE_CHANGE_SUBMITTER` | 提交系统级敏感变更申请 |
| `BACKOFFICE_CHANGE_REVIEWER` | 批准或拒绝系统级敏感变更 |
| `AUDIT_EVIDENCE_VIEWER` | 查询授权范围内审计证据 |
| `AUDIT_EVIDENCE_EXPORTER` | 创建和下载默认脱敏审计导出 |
| `AUDIT_RETENTION_MANAGER` | 创建、修改、启停保留策略草稿 |
| `AUDIT_EVIDENCE_HOLD_MANAGER` | 设置证据保全、提交解除保全或例外删除申请 |

职责键是安全能力，不是第五类角色，也不用于决定菜单和业务数据归属。职责通过
`sys_user_backend_duty` 直接授予用户；同一用户可以拥有多个职责，但生产环境的自审规则仍按申请
提交人和审核人 ID 判断，不能通过职责叠加绕过。

### 6.3 建筑范围

- `PLATFORM_ADMIN` 继续由现有 `BuildingScopeService` 表达全建筑范围；
- 其他角色只能访问 `sys_user_building` 明确授权的建筑；
- 审计查询和导出必须把请求条件与服务端建筑范围取交集；
- 单对象操作先查数据库真实 `building_id`，再校验范围；
- 全局系统对象允许 `building_id=NULL`，但只有具备对应职责且业务角色允许的用户可访问；
- 同时拥有多栋建筑权限不允许把两个建筑对象放进同一个领域事务。

### 6.4 领域状态和归属

角色、职责和建筑范围全部通过后，领域模块仍必须校验：

- 对象是否属于当前用户、当前草稿或当前申请；
- 当前状态是否允许编辑、提交、撤回、审核或生效；
- 版本、修订号、快照摘要和幂等键是否匹配；
- 专业输入、引用、并发和事务约束是否满足。

公共职责不能把 `DRAFT` 直接变成 `EFFECTIVE`，也不能替代能源规则、设备事实或领域事务。

## 7. 职责数据模型与动态授权

### 7.1 `sys_backend_duty`

保存职责目录：职责键、名称、说明、状态、风险等级和版本。职责目录由 Flyway 初始化，不提供普通
在线新增任意职责键，避免运行时创造无法审计的安全能力。

### 7.2 `sys_user_backend_duty`

保存用户职责授权：用户 ID、职责键、状态、生效时间、失效时间、来源申请 ID、创建和撤销证据。
关键约束：

- 用户与职责唯一；
- 禁止数据库级联删除；
- 撤销使用状态和失效时间，不覆盖历史来源；
- 职责分配和撤销自身属于敏感系统操作，必须提交审核；
- 生产初始化不能把全部职责自动授予所有平台管理员。

### 7.3 `BackendDutyService`

公共授权组件提供：

- `requireDuty(userId, dutyKey)`；
- `hasDuty(userId, dutyKey)`；
- `evict(userId)`；
- `requireSeparation(submitterId, reviewerId, environment)`。

职责从 MySQL 读取，可使用 Redis 旁路缓存；缓存损坏或不可用时回源 MySQL，不能因缓存故障放宽权限。
职责分配、撤销或到期后立即清理缓存。职责不写入 JWT，因此无需等待 Token 过期才能撤权。

## 8. 敏感系统操作闭环

### 8.1 公共闭环适用范围

通用 `sys_sensitive_change_request` 只用于没有自身完整审核状态机的系统级命令和少量已登记敏感领域命令：

- 正式角色授予和撤销；
- 用户后台职责授予和撤销；
- 建筑访问批准、撤销和范围调整；
- 菜单定义、菜单状态和角色菜单关系变化；
- 账号开通、停用、恢复和管理员密码重置；
- 设备产品启停、待认领设备正式绑定和设备身份启停；
- 审计保留策略新增、修改、启停；
- 证据保全解除、提前删除、强制删除和手工范围删除。

登录、普通查询、用户修改自己的非安全资料和系统自动到期清理不进入该审批状态机。

#### 8.1.1 账号开通申请包与凭据交付

后台创建账号不拆成“创建账号、授予角色、授予建筑”三次申请。一个账号开通申请包一次填写账号
基础信息、正式角色和建筑范围，一次提交、一次审核；审批执行在一个事务中创建账号并写入全部角色、
建筑授权，任一环节失败都整体回滚。审计仍分别记录账号创建、角色授予和逐建筑授权三个安全事实，
但不重复创建三套审批。

初始密码和管理员重置后的新密码都不进入申请载荷、命令哈希或审计摘要。审批执行仅签发一次性令牌：

- 原始令牌只随本次执行响应返回一次，MySQL 只保存 SHA-256；
- 默认有效期为 15 分钟，允许通过部署配置缩短或调整；
- 新账号在令牌消费前保持停用且待激活，消费成功后才设置 BCrypt 密码并启用；
- 密码重置令牌消费后只更新密码和撤销旧登录态，不改变既有停用状态；
- 令牌只可消费一次，重新签发会撤销同账号尚未消费的旧令牌；
- 后续增加角色、扩大建筑范围、停用、恢复或重置密码均重新申请审核；昵称、电话等普通资料仍可直接修改。

公开自助注册若继续保留，只能创建无建筑范围的最低权限账号，不能替代后台账号开通申请包，也不能
通过请求字段取得其他角色或建筑权限。

每种通用申请必须关联代码内显式登记的 `SensitiveOperationHandler`。处理器负责解析白名单 DTO、重新
查询对象真实归属、校验影响范围并执行领域 Service；禁止保存任意类名、SQL、脚本或反射调用作为
可执行命令。拥有完整草稿和审核状态机的采集策略、质量使用策略、设备参数和关系治理不登记此处理器。

### 8.2 状态机

```text
DRAFT → PENDING_REVIEW → APPROVED → EXECUTED
   │            ├→ REJECTED
   └────────────└→ WITHDRAWN
                        APPROVED → EXECUTION_FAILED
```

- `DRAFT`：提交人准备规范化命令；
- `PENDING_REVIEW`：命令、目标、影响摘要和请求哈希冻结；
- `APPROVED`：审核通过，等待同事务或受控执行器执行；
- `EXECUTED`：命令成功并留下结果证据；
- `EXECUTION_FAILED`：审核已通过但执行失败，不得伪装为成功；
- `REJECTED/WITHDRAWN`：历史只读。

执行失败不能修改原申请命令或自动换成新目标。重试只允许同一申请、同一请求哈希和幂等键；需要修改
输入时创建新申请。

### 8.3 审核规则

- 提交需要 `BACKOFFICE_CHANGE_SUBMITTER`；
- 审核需要 `BACKOFFICE_CHANGE_REVIEWER`；
- 保留策略提交还需要 `AUDIT_RETENTION_MANAGER`；
- 保全解除和例外删除提交还需要 `AUDIT_EVIDENCE_HOLD_MANAGER`；
- 生产环境 `submitter_id == reviewer_id` 一律拒绝；
- 研发环境显式开启后允许同账号审核，但仍需两次 API 调用和两条审计事件；
- 审核意见必填；批准时重新计算规范化请求 SHA-256；
- 审核通过不能覆盖领域模块自己的专业校验、版本锁和生效事务。

### 8.4 领域模块接入

采集策略、质量使用策略、设备参数和关系治理继续使用各自审核表。它们只复用：

- 后台职责校验；
- 研发/生产自审策略；
- 统一追踪标识；
- 公共审计字段；
- 统一查询适配器；
- 保留、保全和清理契约。

领域模块不得把完整草稿 JSON 复制到 `sys_sensitive_change_request`，也不得同时维护两套审核状态。

## 9. 公共审计证据契约

### 9.1 必填字段

所有接入统一查询的审计源至少提供：

| 字段 | 语义 |
|---|---|
| `auditId` | 审计源内稳定唯一 ID |
| `sourceModule` | 稳定模块键，如 `SYSTEM_SECURITY`、`COLLECTION`、`QUALITY_USAGE` |
| `buildingId` | 真实建筑归属；全局系统对象可空 |
| `actorType` | `USER`、`SYSTEM`、`DEVICE` 或 `MIGRATION` |
| `operatorId` | 用户操作人；系统行为可空 |
| `actionType` | 稳定动作键 |
| `objectType` | 稳定对象类型 |
| `objectId` | 对象稳定 ID；不能保存密码、Token 或原始报文 |
| `versionId` | 关联版本，可空 |
| `reviewRequestId` | 关联审核申请，可空 |
| `beforeSummary` | 脱敏前摘要，可空 |
| `afterSummary` | 脱敏后摘要，可空 |
| `result` | `SUCCESS`、`REJECTED`、`DENIED` 或 `FAILED` |
| `reasonCode` | 稳定内部原因码；成功可空 |
| `traceId` | 服务端生成的请求追踪标识 |
| `operationTime` | MySQL 记录的操作时间 |
| `environmentMode` | `DEVELOPMENT`、`TEST` 或 `PRODUCTION` |
| `selfApprovalDevMode` | 是否使用研发自审例外 |

模块可以继续保存幂等键、请求摘要、配置修订、专业证据和领域差异，但统一查询默认不暴露这些内部
字段。

### 9.2 结果语义

- `SUCCESS`：业务事务或系统命令已经成功；
- `REJECTED`：审核人明确拒绝，或领域校验形成可追溯拒绝；
- `DENIED`：认证、角色、职责、建筑范围或生产自审边界拒绝；
- `FAILED`：已授权执行开始后因并发、依赖或系统错误失败。

不能把“提交成功”记录成“发布成功”，也不能把 Broker、缓存或运行时刷新成功替代数据库业务成功。

### 9.3 事务与失败

- 领域状态变化和领域审计继续在同一 MySQL 事务提交；
- 系统敏感命令、申请状态和系统审计在同一事务提交；
- 审计写入失败时，敏感业务操作整体回滚；
- 500 等事务外异常至少写安全事件和服务日志，不能再尝试伪造已回滚的业务成功审计；
- 审计表不对可删除草稿建立级联外键；
- 审计只追加，不提供普通更新和删除 Repository。

### 9.4 摘要脱敏

审计摘要禁止保存：

- 密码、JWT、Cookie、私钥、证书私钥和连接凭据；
- 完整手机号、邮箱、身份证号和个人地址；
- 原始设备报文、完整 Excel 内容或未脱敏外部响应；
- SQL、堆栈、文件系统个人路径和内部网络凭据。

摘要优先保存状态、版本、数量、字段名、稳定对象 ID 和规范化差异。需要核查原始证据时只保存受控
证据引用和校验值，不把原文复制进审计表。

## 10. 追踪标识与安全拒绝

### 10.1 `traceId`

- 每个 HTTP 请求由服务端生成不可预测的 `traceId`；
- 客户端提供的请求 ID只能作为单独的外部关联值，不能覆盖服务端主追踪 ID；
- `traceId` 写入 MDC、响应头 `X-Trace-Id`、错误响应和审计证据；
- 同一业务事务内的审核、执行和审计使用同一 `traceId`；
- 异步任务创建新执行追踪 ID，并保留父追踪 ID。

### 10.2 错误响应

新版本接口的失败响应统一为：

```json
{
  "code": 403,
  "errorCode": "BACKOFFICE_OPERATION_FORBIDDEN",
  "msg": "无权限执行该操作",
  "traceId": "服务端追踪标识",
  "success": false
}
```

客户端不得收到“该对象属于另一栋建筑”“缺少某具体高权限职责”或 JWT 解析细节。内部安全审计可以
记录 `ROLE_DENIED`、`DUTY_DENIED`、`BUILDING_SCOPE_DENIED`、`SELF_APPROVAL_PRODUCTION_DENIED`、
`EVIDENCE_HOLD_BLOCKED` 等细分原因，并通过 `traceId` 与脱敏响应关联。

### 10.3 安全事件范围

以下事件进入 `sys_security_audit_event`：

- 登录成功、登录失败、Token 明确撤销或角色快照非法；
- 敏感操作角色不足、职责不足、建筑越权和生产自审拒绝；
- 审计查询、导出、下载、保全、清理策略和例外删除；
- 未分类系统异常与敏感操作执行失败的关联证据。

普通 404、公开接口无 Token 和高频正常业务读取不逐条写安全审计，避免制造无收益的海量日志。
登录失败等可被攻击者放大的事件必须限长、限字段并具备容量监控。

普通页面浏览、实时卡片刷新、趋势查询、WebSocket 发布、MQTT 报文、时序写入和指标读取不属于本
公共审计事件。禁止为了“全量留痕”给每个 Controller 或普通 GET 请求统一追加数据库审计，否则用户
和设备增长会把业务 MySQL 变成无边界访问日志库。

## 11. 统一查询架构与契约

### 11.1 不建设中央全量副本

领域审计表继续作为权威事实，公共查询通过 `AuditEvidenceProvider` 适配：

```text
AuditQueryController
→ AuditQueryService
→ BuildingScopeService + BackendDutyService
→ AuditEvidenceProvider[]
   ├─ SystemSecurityAuditProvider
   ├─ CollectionAuditProvider
   ├─ QualityUsageAuditProvider
   ├─ DeviceParameterAuditProvider
   └─ OnboardingAuditProvider
→ 按统一游标合并结果
```

每个 Provider 必须把建筑、操作者、对象、时间、结果和游标条件下推到 SQL。禁止先读取整张表再在
Java 内存过滤、排序和分页。

公共边界同时定义 `AuditEvidenceWriter`、`AuditEvidenceProvider` 和 `AuditRetentionHandler`：

- `AuditEvidenceWriter` 只负责追加规范化审计证据，不暴露任意表名或 SQL；
- `AuditEvidenceProvider` 负责条件下推、游标查询和统一视图映射；
- `AuditRetentionHandler` 负责按审计源计算候选、执行保全过滤和分批清理；
- 领域审计实现继续与领域事务绑定；高频 `SYSTEM_SECURITY` 实现可以在后续独立替换；
- 首版不实现双写、消息队列、外部搜索引擎或独立日志微服务。

接口预留不等于当前已有第二套存储。只有实际事件量、写入延迟、表规模或清理追赶能力证明 MySQL
达到扩容门禁时，才启动独立架构评估。

### 11.2 查询 API

```text
GET /v1/audit-events
```

支持条件：

- `sourceModule`；
- `buildingId`；
- `operatorId`；
- `actorType`；
- `actionType`；
- `objectType`、`objectId`；
- `result`、`reasonCode`；
- `from`、`to`；
- `traceId`；
- `cursor`、`size`。

查询规则：

- 默认按 `operationTime DESC, auditId DESC, sourceModule DESC` 排序；
- 使用不透明游标，不使用跨源深页码偏移；
- 未提供时间时使用受配置限制的近期窗口；具体默认窗口、单次最大时间窗和页大小上线前确认；
- 时间使用带时区的 ISO-8601 输入，响应返回明确偏移或统一 UTC；
- 查询必须具有 `AUDIT_EVIDENCE_VIEWER`；
- 查询条件自动与服务端建筑范围取交集；
- 全局审计只对具有全局范围和相应职责的用户可见；
- 查无权限对象时返回统一脱敏结果，不暴露对象是否存在；
- 查询审计本身进入安全审计，但不递归进入业务审计。

### 11.3 查询响应

响应返回公共字段、脱敏摘要和来源模块，不返回请求哈希、幂等键、原始载荷、密码学校验细节、完整
IP 地址或堆栈。操作者展示名按当前用户目录解析；删除或停用账号仍保留稳定 `operatorId`，不能因为
账号变化改写历史审计。

## 12. 导出权限与脱敏边界

### 12.1 权限

- 创建和下载导出同时需要 `AUDIT_EVIDENCE_VIEWER` 和 `AUDIT_EVIDENCE_EXPORTER`；
- 导出职责不自动包含查询职责，两项职责必须分别显式授予；
- 导出沿用与在线查询完全相同的建筑范围和过滤器；
- 首版只提供默认脱敏导出，不提供“管理员一键取消脱敏”；
- 跨全部建筑、超出配置时间窗或超出行数上限的请求直接拒绝；
- 未来如需未脱敏导出，必须独立设计、单独审核和确认合规依据。

### 12.2 导出流程

```text
提交导出条件和用途说明
→ 校验职责、建筑范围、时间窗和数量上限
→ 生成不可变条件摘要
→ 异步生成默认脱敏文件
→ 有限有效期下载
→ 到期删除文件
→ 保留导出申请、结果、数量、校验值和下载审计
```

导出文件不能放入仓库、静态资源目录或公开对象存储。文件名不得包含用户名、手机号或建筑敏感名称。
下载使用一次性或短时授权；导出文件到期删除不删除导出审计。

### 12.3 默认脱敏

- 保留稳定用户 ID，昵称和用户名按权限显示或遮蔽；
- IP 地址默认掩码，User-Agent 截断并去除可疑控制字符；
- 前后摘要继续执行字段级脱敏；
- 不导出请求哈希、Token、Cookie、密码、凭据、完整原始载荷和堆栈；
- 导出用途、条件、记录数、文件 SHA-256、创建人和下载人进入安全审计。

## 13. 保留策略与自动清理

### 13.1 确定原则

保留期限取适用法律法规、等保或合同最低要求，安全调查周期，业务争议与审计周期，以及个人信息
最短必要原则中的有效边界。软件不以数据库容量单独决定合规期限。

当前候选：

| 数据类别 | 起算点 | 生产候选期限 | 说明 |
|---|---|---|---|
| 登录、鉴权拒绝和相关网络安全事件 | `operationTime` | 不少于 `P6M` | 使用六个自然月，不写死为 180 天 |
| 治理、系统敏感操作和审核审计 | `operationTime` | `P1Y` | 覆盖年度治理和争议追溯的产品决策 |
| 审计导出及下载审计 | 导出完成或下载时间 | `P1Y` | 文件本身使用更短到期时间 |
| 普通应用调试日志 | 日志时间 | 30～90 天 | 由部署日志策略管理，不进入本审计清理表 |
| 清理批次证据 | 清理完成时间 | 长期保留 | 不由同一清理作业删除，必要时去标识化人员字段 |

《中华人民共和国网络安全法》要求相关网络日志留存不少于六个月，具体适用范围仍需上线主体确认：
[国家保密局发布文本](https://www.gjbmj.gov.cn/n1/2026/0421/c409088-40705863.html)。涉及个人信息的
保留还需遵守实现处理目的所需的最短时间原则：[工业和信息化部发布文本](https://www.miit.gov.cn/jgsj/zfs/fl/art/2022/art_515a4b20c12f430eab54bb4f56d89f56.html)。

GB/T 47474—2026 是本项目需求依据，但公开标准目录不能单独证明某个审计保留期限；在逐条取得正式
条文和验收证据前，不据此宣称本机制已经满足标准。

### 13.2 `sys_audit_retention_policy`

策略至少保存：策略 ID、数据类别、适用审计源、期限表达式、启用状态、生效时间、策略版本、变更
原因、申请 ID、批准人和批准时间。

- 使用 `P6M`、`P1Y` 等日历期限，不把六个月错误折算为固定 180 天；
- 策略新增、修改和启停必须走系统敏感操作审核；
- 已批准策略不可原地改写，调整时创建更高版本；
- 研发阶段默认不启用自动清理的前提是只使用虚拟或脱敏数据；
- 一旦研发或测试环境接入真实账号、个人信息或生产复制数据，必须启用适用期限和脱敏规则。

### 13.3 自动清理流程

策略审核通过后，定时任务自动执行，不需要每批再由人工批准：

```text
读取当前已批准策略版本
→ 计算自然月/自然年截止时间
→ 生成待清理批次和预览数量
→ 排除证据保全、未决调查和未完成审批
→ 按主键与时间游标分批物理删除
→ 记录批次范围、数量、结果和校验摘要
→ 失败告警并从安全游标重试
```

自动清理使用系统身份，不冒充用户。每批限制行数、事务时长和运行窗口；失败不得跳过范围继续标记
整体成功。清理作业不得删除自己的清理批次证据。

### 13.4 `sys_audit_cleanup_run`

每次清理至少保存：

- 清理批次 ID和 `traceId`；
- 策略 ID、版本和数据类别；
- 审计源、建筑范围和截止时间；
- 候选数量、实际删除数量和跳过保全数量；
- 最早、最晚被清理操作时间；
- 开始、结束时间、结果和失败原因；
- 系统执行身份、人工触发申请 ID；
- 清理清单摘要或校验值。

清理证据不保存每条已删除记录的完整内容，否则会变相绕过到期删除。长期保留时可以保留系统身份、
数量和校验事实；人员身份到期后按适用制度去标识化。

### 13.5 证据保全

`sys_audit_evidence_hold` 保存保全范围、原因、依据、开始时间、预计复核时间、提交人、审核人和状态。

- 保全可以按审计 ID、对象、建筑、时间范围、事件或调查编号设置；
- 设置保全需要保全管理职责并写审计；
- 解除保全必须提交审核；
- 保全中的记录即使到期也不参与自动清理；
- 保全不能无理由永久延长，必须定期复核；
- 查询和导出保全记录仍受原建筑范围和职责限制。

### 13.6 例外删除

提前删除、强制删除或手工指定范围删除只能通过系统敏感操作申请：

- 必须填写原因、依据、范围、预计数量和影响摘要；
- 必须排除仍在保全、调查或未完成审批中的记录；
- 生产环境提交人与审核人分离；
- 执行前再次计算范围和数量，超过审核快照容差时拒绝并重新申请；
- 不提供 Controller 直接调用 Repository 删除的入口；
- 不允许运维脚本绕过证据和审批作为正常业务流程。

### 13.7 备份与恢复

主库删除不等于备份已经删除。生产上线前必须由部署负责人确认：

- 数据库备份和导出文件的保留期限；
- 备份加密、访问、销毁和介质覆盖方式；
- 从旧备份恢复后重新执行到期清理的流程；
- 证据保全对备份淘汰的适用边界；
- 灾难恢复演练如何证明已到期数据不会无期限重新出现。

具体备份天数属于上线制度和基础设施输入，本设计不猜测固定值。

## 14. 数据模型与索引边界

### 14.1 首版容量冻结

首版按“全系统审计事件每日不超过 10 万条”设计和验收。事件总量包括系统安全事件、系统敏感操作、
领域治理状态变化、审计查询、导出、保全和清理证据，不包括普通业务读取、设备遥测和时序数据。

该数值是容量假设和扩容触发线，不是写入硬上限：

- 未达到 10 万条时，仍需监控实际行大小、索引大小、写入延迟和清理耗时；
- 接近基线时发出容量预警并评估趋势；
- 超过基线时不能停止写入、静默丢弃、随机采样或降低治理审计完整性；
- 超过基线后应优先把高频安全事件切换到独立实现，领域治理审计仍保持事务原子性；
- 扩容方案可以是独立 MySQL 实例、按时间分区或专用审计存储，但必须依据实测另行选择。

按每条事件连同索引约 2 KB 的粗略规划值，10 万条/天约对应每年 7300 万 KB，即约 73 GB；这只是
容量预算输入，不是最终表大小证据。实现后必须在隔离 MySQL 8 测量真实平均行大小、索引放大、压缩、
备份和清理空间回收，再确定生产磁盘冗余。

相同账号、来源和原因在短时间内重复触发的限流型安全拒绝可以形成带 `firstAt`、`lastAt` 和
`attemptCount` 的有界汇总证据，但登录成功、职责变更、审核、发布、导出、保全和清理等关键事件不得
合并。汇总规则必须可配置、可测试，不能把真实业务失败静默吞掉。

### 14.2 表与索引

首版新增系统表：

- `sys_backend_duty`；
- `sys_user_backend_duty`；
- `sys_sensitive_change_request`；
- `sys_security_audit_event`；
- `sys_audit_retention_policy`；
- `sys_audit_evidence_hold`；
- `sys_audit_cleanup_run`；
- `sys_audit_export_job`。

已有领域审计表继续保留，通过增量迁移补齐缺失的公共字段和索引。至少建立：

- `(building_id, operation_time, audit_id)`；
- `(operator_id, operation_time, audit_id)`；
- `(object_type, object_id, operation_time, audit_id)`；
- `(result, operation_time, audit_id)`；
- `trace_id` 索引；
- 保留作业使用的 `(operation_time, audit_id)` 索引。

索引必须按实际查询计划在隔离 MySQL 8 验证，不能只凭表结构宣称性能满足生产要求。禁止为统一查询
把全部审计再复制到一张中央宽表；只有后续真实数据量证明联邦查询无法满足 SLA，才另行评估投影库。

## 15. 现有模块迁移

### 15.1 采集策略

- 删除 `DIRECT_ADMIN_PUBLISH` 普通入口和允许动作；
- 平台管理员创建的配置也必须提交审核；
- 复用领域审核表，不迁移到系统通用申请表；
- 审计补齐 `reasonCode`、`traceId`、审核申请 ID和研发自审标记；
- 查询改为 SQL 条件下推和统一 Provider。

### 15.2 质量使用策略

- 删除 `DIRECT_PUBLISH` 审核模式和管理员直接发布例外；
- 保留变更集、快照 SHA-256、修订号、冲突和发布事务；
- 复用公共自审策略：研发允许完整两步，生产禁止；
- 审计查询由内存过滤改为 SQL 条件下推。

### 15.3 设备参数

- 保留当前无直接发布的职责分离规则；
- 把现有审核人角色检查迁移为角色、后台职责和建筑范围组合校验；
- 审计补齐 `traceId`、审核申请 ID和研发自审标记；
- 继续保留参数版本、双时间、专业证据和重算语义，不放进公共审计表。

### 15.4 设备接入

- 审计补齐建筑 ID、主体类型、原因码、追踪标识和公共索引；
- 从设备、身份或待认领对象真实归属解析建筑，不能信任请求建筑 ID；
- 设备产品启停、待认领设备正式绑定和设备身份启停登记为敏感操作，统一提交审核；
- 产品草稿创建和编辑、待认领列表查询及正式设备只读查询不进入审批；
- 设备接入领域 Service 继续负责产品、设备、身份、测点和建筑一致性事务，通用申请不复制其状态机。

### 15.5 系统管理

- 角色、职责、建筑授权、菜单和账号敏感变化进入通用系统申请；
- 现有建筑访问申请迁移时保留历史 ID和审核事实，不覆盖旧记录；
- 菜单继续只影响导航和可见性，不能授权 API；
- 普通管理员直接写角色、职责和建筑授权的旧入口在迁移后拒绝或改为创建申请。

### 15.6 关系治理候选

- 后续实现直接复用本设计的职责和研发/生产审核策略；
- 保留建筑级关系版本、专业校验、兼容投影和生效事务；
- 关系审计实现公共证据字段和 Provider，不复制关系完整快照。

## 17. 风险与应对

| 风险 | 应对 |
|---|---|
| 独立职责被误做成新角色 | 数据模型和授权 API 分离；正式角色枚举保持四类 |
| 平台管理员仍可绕过审核 | 旧直接写和直接发布入口收口；Service 强制职责和申请状态 |
| 研发自审配置带入生产 | 默认关闭、生产启动拒绝、自动化门禁和审计标记 |
| 通用审批与领域审批重复 | 系统命令用通用申请；有完整领域状态机的模块只复用公共策略和证据 |
| 统一审计成为重复中央库 | 保留领域权威表，使用 Provider 联邦查询，不创建全量副本 |
| 跨源查询内存或数据库压力过大 | SQL 条件下推、时间窗、游标、页大小和索引验证 |
| 用户或攻击流量推高安全事件写入 | 普通读取不入库、拒绝事件有界汇总、每日容量监控和高频安全存储可替换接口 |
| 达到 10 万条后直接丢日志 | 10 万条是扩容触发线而非硬限流；禁止丢弃治理和关键安全证据 |
| 安全拒绝泄露对象或权限结构 | 外部统一脱敏码，内部原因只在受控审计中可见 |
| 审计摘要泄露凭据或个人信息 | 字段白名单、长度限制、脱敏测试和禁止原始载荷 |
| 到期自动清理误删调查证据 | 证据保全、预览批次、范围快照、分批删除和清理证据 |
| 每批都人工审核导致积压 | 只审核策略和例外删除；正常到期批次自动执行 |
| 清理证据重新保存被删内容 | 只保存范围、数量和校验摘要，不保存逐条完整副本 |
| 主库删除但备份长期保留 | 上线前确定备份制度，恢复后重新执行到期清理 |
| 法定期限被错误写死为 180 天 | 使用自然月 `P6M`，上线前核对适用制度 |
| 导出成为数据外流入口 | 独立职责、范围继承、默认脱敏、数量限制、短时下载和全程审计 |

## 18. 验收标准

### 18.1 授权与审批

1. 四类正式角色保持不变，未知职责不能被当作正式角色；
2. 后台职责不写入 JWT，分配或撤销后清理缓存即可动态生效；
3. 平台管理员没有相应职责时不能审核、查询审计、导出或修改保留策略；
4. 角色、职责、建筑范围和领域状态任一不满足时操作被拒绝；
5. 系统敏感操作完整覆盖提交、撤回、批准、拒绝、执行成功和执行失败；
6. 研发配置允许同账号先提交再批准，并明确记录研发例外；
7. 生产配置禁止自审，生产开启自审时应用拒绝启动；
8. 采集和质量使用策略不再存在管理员普通直接发布路径；
9. 设备参数和关系治理继续保留自己的状态机，不出现重复审核申请。

### 18.2 审计与追踪

1. 所有敏感成功、拒绝、越权和失败事件包含公共必填字段；
2. `traceId` 同时出现在响应头、错误响应、服务日志和相关审计；
3. 客户端看不到内部建筑归属、具体职责缺失、Token 解析或堆栈细节；
4. 审计写入失败使对应敏感业务事务回滚；
5. 摘要和导出不包含密码、Token、Cookie、私钥、完整个人信息和原始载荷；
6. 历史账号停用或改名不会改写历史操作人 ID；
7. 查询审计和导出审计不会递归制造无界业务审计。

### 18.3 查询与导出

1. 可以按模块、建筑、操作者、对象、时间、结果、原因和 `traceId` 组合过滤；
2. 所有 Provider 把条件和游标下推到 SQL，不读取全表后内存分页；
3. 跨模块结果按稳定游标排序，无重复、漏项或越权建筑；
4. 普通无建筑范围用户返回空结果，不能看到全局系统审计；
5. 导出严格继承在线查询范围，默认脱敏并限制时间和数量；
6. 导出文件到期删除，导出申请、数量、校验和下载事实仍可追溯；
7. 首版不存在未脱敏导出开关或绕过职责的下载地址。

### 18.4 保留与清理

1. 保留策略只能通过提交审核产生新版本或启停；
2. `P6M` 按自然月计算，不能用固定 180 天替代；
3. 策略生效后正常到期清理自动执行，不需要逐批人工审核；
4. 保全记录、未完成审批和调查范围不会被自动清理；
5. 提前、强制和手工范围删除没有审核时被拒绝；
6. 清理按批次、游标和事务上限执行，失败可安全重试；
7. 每批记录策略版本、范围、数量、结果、追踪标识和校验摘要；
8. 清理证据不保存被删记录的完整副本，也不被同一作业删除；
9. 研发默认关闭清理只在虚拟或脱敏数据前提下通过；
10. 恢复旧备份后能够重新执行适用到期清理。

### 18.5 验证层级

- H2、Mock 和 Stub 验证授权、状态机、脱敏、错误和事务失败路径；
- 隔离 MySQL 8 验证迁移、约束、索引、并发、游标查询和分批清理；
- 使用合成审计数据验证每日 10 万条容量基线对应的写入、查询、存储和清理行为，不连接生产资源；
- 验证普通业务读取、设备遥测和 WebSocket/MQTT 高频链路不会写入公共审计表；
- 验证超过容量预警值不会丢弃关键审计，并能通过接口替换测试证明高频安全存储边界可演进；
- API 契约测试验证状态码、机器码、`traceId`、查询和导出范围；
- 自动化测试不得连接生产数据库、真实账号、现场设备或真实外部存储；
- 生产容量、备份销毁、渗透测试、等保和法律适用性必须独立验收。

## 19. 上线前外部确认项

以下事项不改变本设计架构，但在生产启用前必须由对应负责人确认：

| 来源 | 必须确认的内容 |
|---|---|
| 运营与合规负责人 | 适用法律、等保等级、合同、档案制度及超过候选期限的要求 |
| 组织负责人 | 生产提交人、审核人、审计查看和导出职责的实际账号名单 |
| 基础设施负责人 | 满足每日 10 万条基线的 MySQL 磁盘与备份容量、备份周期、销毁方式、恢复后清理和导出文件存储 |
| 产品负责人 | 单次查询时间窗、页大小、导出最大行数和下载有效期 |
| 安全负责人 | IP 脱敏级别、登录失败容量、防滥用、渗透测试和审计抽查 |

这些数值和人员名单没有当前证据，本设计不自行填写占位值，也不把候选默认解释为最终生产制度。

## 20. 实施顺序

设计批准后的实现顺序固定为：

1. 建立职责目录、用户职责、公共环境和职责分离策略；
2. 建立服务端 `traceId`、统一错误附加字段和安全拒绝事件；
3. 实现系统敏感操作申请、审核和执行器注册；
4. 把角色、职责、建筑授权、菜单和账号敏感操作接入通用闭环；
5. 关闭采集和质量使用策略直接发布，并让领域模块复用公共职责和自审策略；
6. 为现有审计表补齐公共字段、索引和 SQL 查询 Provider；
7. 落实写入、查询和保留处理接口，并为高频安全审计提供可替换实现边界；
8. 实现统一游标查询和默认脱敏导出；
9. 实现保留策略、证据保全、自动清理和清理批次证据；
10. 完成每日 10 万条合成容量验证、H2/Mock/Stub、MySQL 8、API 契约和范围匹配的完整 Maven 验证；
11. 更新项目指南和状态，明确软件候选、外部制度和生产未验证边界；
12. 在干净任务中基于固定基线和原始证据进行独立候选验收。

实施必须按可独立回滚的小批次完成，不能在一个 PR 中同时重写所有领域状态机。优先建立公共职责、
追踪和系统敏感操作，再逐个模块迁移；每个旧直接入口只有在新入口和自动化验证就绪后才关闭。

## 21. 完成定义

只有同时满足以下条件，才能称为“后台职责分离与统一审计治理软件活动候选实现完成”：

- 四类正式角色保持稳定，后台职责和建筑范围可以动态授权与撤销；
- 生产敏感操作无法自审，研发自审仍完整经过提交和批准；
- 普通直接发布入口全部关闭，领域状态机没有被公共机制重复实现；
- 系统敏感操作、领域审计、安全拒绝和追踪标识形成一致证据链；
- 统一查询、默认脱敏导出、保全、策略审批和自动清理均已实现；
- 现有模块审计完成增量接管，没有删除、覆盖或无依据补造历史证据；
- 范围匹配自动化门禁和隔离 MySQL 8 验证通过；
- 当前项目状态与稳定架构入口已经同步；
- 完成独立候选验收。

即使达到以上条件，也只能声明软件候选机制完成。没有上线主体制度、生产账号分工、备份与恢复验证、
安全测试和必要的合规验收时，不能声明生产职责分离或法律合规已经完成。
