# Modbus 只读边缘适配器设计

> **文档状态：已确认方向的活动候选设计；软件实现与隔离模拟验证随本分支交付，现场验收未完成。**

## 1. 目标

在厂家寄存器点表尚未取得时，先形成不依赖具体厂家的通用 Modbus 采集骨架。厂家资料到位后
通过部署配置补充真实连接和点位，不修改平台 V2 持久化契约，不把南向驱动装入云端适配器。

```text
设备 Modbus TCP/RTU
→ 独立 modbus-edge-adapter
→ V2 MQTT QoS 1/TLS
→ 平台身份、幂等、迟到和持久化处理
→ 可信绑定指定的代理 ACK Topic
```

## 2. 已批准边界

纳入：

- 独立 Java 21 JAR/进程；
- Modbus TCP、串口 RTU，只读 01/02/03/04；
- 外部 YAML 配置设备身份、连接、点位、类型、端序、倍率、单位和周期；
- 完整批次读取后生成现有 V2 多测点报文；
- MQTT QoS 1、TLS、主机名校验、有限重试、分类日志与指标；
- 平台代理 ACK 的关联和超时观测；
- 进程内模拟从站和自动化验证。

不纳入：

- 厂家专有寄存器点表、默认地址或单位；
- Modbus 写操作、参数下发和设备控制；
- 配置中心、配置页面或远程点表下发；
- 本地持久化缓存、容量/淘汰、断电保留、补传和限速；
- 真实设备、真串口、生产 Broker/TLS、现场网络和长期运行验收。

## 3. 模块职责

`modbus-edge-adapter` 负责南向通信、点值解释和北向报文生成；云端
`telemetry-adapter` 继续负责已有 MQTT JSON 厂商报文适配。二者是并列入口，不互相调用。
平台核心仍是身份可信绑定、去重/冲突、迟到处理、原始持久化和应用 ACK 的唯一权威方。

模块按设备固定延迟调度。每轮先依据点表合并连续且同功能码的地址，再用单次会话读取所有
块。任一连接、协议或解码错误都会放弃整批，避免把缺点半包伪装成完整采样。

## 4. 配置契约

设备配置必须包含：

- 稳定设备身份、协议模板编号与版本；
- TCP 的主机/端口，或 RTU 的串口参数；
- Modbus Unit ID、超时和采样周期；
- 每个点的标准点码、功能码、零基地址、数据类型、字节序、字序、倍率、偏移和单位。

启动时拒绝空身份、重复身份/点码、地址越界或重叠、位功能码与数据类型不匹配、TLS 信任库
缺失，以及未显式标记为测试的明文 MQTT。仓库只提供关闭状态的虚构结构示例。

## 5. 身份与时间

Modbus 本身通常不提供消息编号或采集时间。适配器不把这些缺失字段猜成设备原始事实：

- 进程启动生成 `bootId`；
- 每个稳定设备身份维护进程内单调 `sourceSeq`；
- 二者共同支持 `BOOT_ID_AND_SEQ` 去重关联并派生 `canonicalMessageId`；
- `collectedAt` 保持空，`adapterReceivedAt` 使用边缘 UTC 时钟；
- 时间来源明确为 `ADAPTER_RECEIVED`。

因此重试同一生成报文时消息编号不变；下一轮重新采样生成新序号。进程重启更换 `bootId`，
避免序号从 1 重新开始造成静默覆盖。

## 6. ACK 和失败语义

Broker `PUBACK` 只证明 Broker 接收 QoS 1 PUBLISH。平台完成全部原始测点及轻量消息账
持久化后，才可产生 `PLATFORM_PERSISTED` 应用 ACK。适配器声明 `ADAPTER_PROXY`，但平台
仍依据可信身份绑定、关联策略和 ACK Topic 决定实际模式，载荷不能自行提升权限。

当前模块在内存中关联应用 ACK，并分别记录收到、无法关联、格式无效和超时。应用 ACK
不是本地持久化队列：超时只留下运行证据，不承诺断网后恢复。读取或发布的有限重试耗尽后，
日志和指标保留失败分类，但该采样批次无法在进程重启后补发。

## 7. 验收分层

软件候选验收：配置校验、功能码读取计划、端序/倍率解码、完整批次、重试、V2 字段、TLS
信任库、QoS 1 与应用 ACK 分离，以及进程内 Modbus TCP 从站读取均通过自动化。

厂家联调前置：正式协议文档、寄存器点表、设备型号/固件、TCP 或串口参数、地址基准、类型、
端序、倍率、单位、有效范围和异常码。

现场验收：真实设备与真串口/网络、生产证书和 ACL、平台预注册、长期稳定性，以及若未来
新增网关持久化能力后的真实断网补传，必须另行验证。
