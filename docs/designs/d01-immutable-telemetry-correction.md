# D01 原始遥测保全与冲突更正

> 状态：已批准实施的活动候选；不表示已经部署、成为正式基线或完成现场验收。
> 当前状态以 [PROJECT_STATUS](../../PROJECT_STATUS.md) 为准。

## 取值边界

原始契约采用已校验 DOUBLE 数值；标准/V2 十进制不能往返该类型时明确拒绝，不宣称保存任意精度十进制。

同一物理测点和设备采集毫秒构成原始事实身份。MySQL 唯一意图先独立提交完整快照，所有 MQTT、HTTP、标准批次和 V2 原始入口仅向 TDengine 回放此快照。TDengine 的同时间戳覆盖能力不再承担业务仲裁。DOUBLE 使用可往返字符串，时间写入使用毫秒数值。

相同语义的重传忽略接收时间和迟到标志变化，保留首次元数据。不同数值或身份内容作为冲突证据持久化；重复冲突合并次数，不反复创建待办。到达晚、普通序号大或更换消息 ID 均不证明数据正确。旧库已经存在的行先被接管；切换前已经遭覆盖的值无法由本改动恢复，不追认历史回执证明原始正确性。

例如先收到 100、后收到 120：原始证据仍为 100。核实 120 正确后追加处置版本，业务查询和分钟计算采用 120。审计详情仍能看到原值、候选、当前有效值与处置依据。设备/建筑/来源/质量身份发生变化的候选不能作为单纯数值更正采用。

## 人员与权限

- 复用现有 `BUILDING_OWNER`、`ENERGY_MANAGER`、`PLATFORM_ADMIN` 与建筑范围，不增加角色。
- 平台管理员为每栋建筑指定一个已有有效账号。普通冲突由该账号核实、选择候选或保留原值，并填写原因和依据；管理员身份本身不等于可代替指定负责人处置。
- 无法判断时再联系硬件方核对报文、能源专业人员解释业务，不逐条要求会签。
- 能源专业档案或已有能源更正管理的点，采用不同值必须通过现有能源更正版本 API、维护职责、审核职责和生产职责分离。负责人需具有现有维护权限才能提交；不新增 D01 审核组织。当前前端只显示待审核版本 ID，能源审核继续使用既有 API，未新增能源审核页面。
- 新候选或其他处置会改变冲突修订号。旧页面处置和已被新冲突取代的能源更正提交不能直接通过审核。

## 查询、计算与核算

普通监测点的处置只保存选择版本，不写回 TDengine 原始行。历史、最新、趋势及分钟取样读取有效选择；趋势由引擎样本均值、样本数和稀疏更正差值组合，不把全量原始历史拉入 JVM。原采集时间、首次接收时间和质量保持不变。

能源活动原始读取契约继续读取原始事实，由现有能源聚合核心消费更正一次；按 `calculationAsOf` 选择当时已批准的版本，被后续版本取代的审批历史仍可追溯，未来批准不会倒灌历史计算。待审核值不生效；既有 DECIMAL(30,12) 无法精确表示的值明确拒绝，不静默舍入。

普通测点后来纳入能源治理时，已有普通选择在待审期间继续有效，证据仍指向原普通处置版本。现有能源审核批准时，在同一事务内清除普通取值指针、启用批准值并登记派生任务；普通处置历史不删除，审计或容量失败整体回滚。两类有效来源使用同一 SQL 快照读取，避免交接期间读到两份值；没有新增免审核能源更正入口。

选择版本或能源审核成功时，同事务写持久派生任务。后台复用现有 Q0 分钟重聚合、公式通知和插值修正；明确确认的更正不受设备迟到自动窗口限制。已存在 Q1 的左右相邻缺口按现有线性算法重算，以端点数值及持久化修订时间构造新补全任务，并显式替代原 Q1 任务；保留旧端点证据，不覆盖 Q0，不恢复已作废任务。幂等重试仍补发 READY，避免落盘后通知中断。更正、能源批准和派生任务共用 MySQL 点级锁，跨实例不会由较旧任务覆盖较新选择。缺失原始证据、测点被迁移或下游不可用时保留失败任务，不假装完成。

自动插值最大缺口缩小后，已存在 Q1 的依赖不能按新配置被遗漏。明确更正先检查相邻 Q1，必要时按原任务冻结端点扩大回读范围，使用现存 Q0 数值重算原缺口；该处理不扩大普通自动补点的范围。每侧最多处理 5,000 个缺失分钟，证据缺失、损坏、端点已清理或仍有关联 Q1 而测点不再适用时明确失败，不能把旧 Q1 未处理的任务收为完成。累计量等本来不参与插值且没有遗留 Q1 的测点正常完成 Q0 更正，不因此产生失败任务。

累计量/积分锚点的影响范围由前后真实样本限定，缺少一侧时保守检查该点已有周期。受影响能源周期标为待重算；正式快照不直接改写，继续使用现有重算审核，发布新能源快照后沿用既有碳依赖变更链。不会冻结整栋建筑。

## 消息与恢复

V2 在 TDengine 写入前冻结规范化多点批次、身份绑定、ACK 模式和首次接收时间。恢复使用冻结映射，不重新解析已变化的别名。原始意图独立于消息回执事务；同一消息跨实例由持久键和行锁串行收口。终态回执和消息完成状态同事务提交。

标准 V1 同样先整批预检并冻结映射，再写入；遇首个冲突后继续为后续已有事实留证，不为已拒绝批次创建后续未知事实。任何留证失败均不确认消息，保留重投。

相同 canonical ID 的不同有效载荷另存完整冲突，后台按首次冻结映射转成可处置的测点冲突；管理员可通过 `GET /v1/telemetry-conflicts/messages/{id}` 查看消息冲突原文和次数；不适用于原事实身份的变化只能留证，不能强行换成原点数值。后台有界补齐中断批次与回执，不依赖 Broker 恰好再次投递。`PLATFORM_PERSISTED` 仍只证明原始持久化与终态回执，不代表数值经确认、业务更正已经采用或现场验收。

消息冲突物化与原始清理交错时，在测点退役锁内区分“原始意图暂缺”和“原始事实已退役”。暂缺继续有界重试；已退役的变体进入 `materialized=3` 归档状态，原因 `ORIGINAL_RETIRED_USE_HISTORICAL_REVIEW` 可从原消息证据接口查询，明确转既有历史导入和核算审核。归档保留完整报文至证据期限，不补造原始行、不宣称候选已生效；同批尚未退役的测点仍逐项留证。归档状态不进入无效重试，到期清理后释放消息证据配额；其他 PENDING/FAILED 不因超时被误删。

## 积压与保留

冲突负载不保存在无限内存队列中。每个事实最多 16 种冲突内容。消息证据与测点候选分别使用有界配额，各默认最多 50,000 条、合计最多 100,000 条负载，避免消息自身占满候选物化空间；这替代原共享 50,000 条预算。未完成原始意图和消息意图各默认最多 50,000 条。派生任务按同一测点和采集时间合并，待处理及失败任务合计默认最多 50,000 条，由 `max-pending-derived-tasks` 配置；FAILED 不自动重新排队、不释放额度，满额时回滚业务选择或能源批准。只有完成任务释放额度，重复入队及人工重试不得重复占用。重复冲突只增加次数。达到容量后拒绝新增证据写入、保留消息重试，不能先确认后丢弃。原始意图、消息和派生恢复每轮分别最多 50、20、50 项；查询和过期清理有固定上限。高负载部署需独立核验新增 MySQL 意图、网络往返、保留期及恢复吞吐，旧 V2 热路径的单次写入预算不再适用，未以 Mock 速度证明 200 条/秒。

默认 7 天未处置标记为 `EXPIRED`（待核实过期），不自动采用候选，不把过期描述为正确。已处置/过期内容重传不重新打开待办，新的不同内容需要重新核实。未引用的冲突负载保留 180 天后压缩为内容指纹；处置引用的证据受保护，未完成恢复意图不因超时丢弃。原始、消息、派生和消息冲突物化连续 10 次恢复失败转入持久 `FAILED`（消息冲突表内部以 `materialized=-1` 表示），通过 `GET /v1/telemetry-conflicts/recovery?buildingId=...` 查看；指定负责人或管理员核实依赖恢复后，调用 `POST /v1/telemetry-conflicts/recovery/retry`（`kind=RAW|MESSAGE|MESSAGE_CONFLICT|DERIVED`、列表返回的 `id`）重新排队，并保留审计。关闭 HVAC 质量组件时，能源周期脏标记仍执行，分钟任务显示失败而不是假完成。成功消息快照沿用 24 小时热回执期限。TDengine 原始清理前推进持久测点退役水位，未完成原始意图阻止越过其时间；退役键不能因重传重新出现。已退役事实的处置不能显示为业务更正成功；超出原始保留期的正式历史更正须使用既有历史导入和核算审核，不根据留存摘要补造 TDengine 原始行。

证据容量耗尽、恢复失败或重算滞留必须作为运维异常处理；增加内存或让未知值自动生效不能替代处置。测试发布切换候选后若启动或验收失败，脚本停止候选服务、保留候选目录和迁移数据，不自动恢复可能覆盖原始值的旧包；停止失败须明确报错。切换前失败不停止当前运行服务。回退须另行核验旧包的 D01 写入兼容性、停止覆盖写入者并保留迁移数据，不能把制品没有能力标识视为兼容。

```powershell
.\mvnw.cmd -DskipTests test-compile
.\mvnw.cmd dependency:build-classpath -Dmdep.outputFile=target/d01-classpath.txt -Dmdep.includeScope=test
python scripts/Verify-D01Isolated.py
```
