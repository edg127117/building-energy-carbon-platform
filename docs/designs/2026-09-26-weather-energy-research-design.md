# 天气数据板块与日用电量对照首期实施设计

状态：首期后端为活动候选，前端未实施。本文记录设计及分阶段联调过程；2026-09-28 本轮测试环境功能与历史完整性验收已通过，最新证据和未验证项以 [PROJECT_STATUS.md](../../PROJECT_STATUS.md#3-能力状态矩阵) 为准。下文早期失败和待办为过程记录，不代表当前结果；长期稳定性及正式上线仍未验收。

## 1. 产品目标与范围

目标是先建立可靠天气数据，再方便地与中央空调电耗对照。首期建设“天气数据板块＋简单日用电量对照”，不建设独立用电研究管理体系。

| 保留的能力 | 首期交付 |
|---|---|
| 天气概览 | 建筑所在地当前天气、今天及未来六天预报、小时天气曲线 |
| 历史天气 | 从 2024-01-01 起的可用历史天气，含温湿度、降水、辐射和风 |
| 简单电耗对照 | 天气页面内的对照视图，选择系统、内机计量组或外机、日期；展示日用电量与日均温，可切换日均湿度 |
| 数据说明 | 来源、实际时间、建筑/行政区覆盖、更新状态、缺失原因，以及电量近似和计量范围标记 |

用户无需选择天气供应商，也无需逐测点配置。管理员维护建筑位置和已确认计量关系，所属系统自动继承。没有电表仍能独立使用天气功能。

### 1.1 本次范围收缩及既有约束处理

| 原方案 | 处理 |
|---|---|
| Open-Meteo＋中国天气网；不依赖 tianqi.com、Chromium | 保留 |
| 建筑坐标、区县概览、Best Match、历史/预报分离 | 保留 |
| 六分钟日界容差、质量校验、换表/复位治理、一表多机 | 保留，它们是日用电量正确性的必要条件 |
| 独立用电研究页面、项目/配置/运行版本管理 | 暂缓；替代为历史天气页内的简单对照视图 |
| 小时功率联合分析及 90%/390 秒/两端 360 秒门槛 | 暂缓，不创建相应计算任务、结果表和 API；天气小时曲线保留 |
| 散点图、内外机占比、系统合计及联合分析 | 暂缓；内机组、外机分别查看，不自动合计 |
| 专用研究证据快照、清理前保护接口、研究归档 | 暂缓；不修改既有电表原始数据保留天数和清理行为 |
| 长期研究结果完整复现承诺 | 取消首期承诺；仅保留必要日结果与计算摘要，原始输入清理后的限制明确展示 |
| 天气历史积累、预报批次和来源追溯 | 保留，属于天气基础能力，不建立研究引用/归档管理系统 |

不自建天气或电耗预测模型，不做远程控制，不分摊单台内机电耗，不计算 COP/EER、节能量或因果结论，不增加回归模型和专门辐射电耗分析。后续按实际研究问题另行设计。

本文件整理现有活动草案，不改动其他冻结设计。[项目指南](../../PROJECT_GUIDE.md)与[当前状态](../../PROJECT_STATUS.md)仍是项目权威入口，本文不是已实现能力声明。

## 2. 数据来源与空间时间口径

| 来源 | 职责 |
|---|---|
| Open-Meteo | 当前天气、小时及七日日预报、全部历史天气；所有电耗对照天气数值 |
| 中国天气网 weather.com.cn | 城市/区县七天日级预报概览 |

首批城市南京，按建筑真实坐标请求模型数据，历史起点 2024-01-01；只补取实际可用日期。Best Match 为默认历史方案，不固定指定 ERA5，也不排除默认产品内部可能使用 ERA5。不假设统一五天延迟，不把模型值标为现场观测。

一个建筑维护一套有生效时间的位置配置：建筑经纬度、时区、来源区县代码、覆盖层级。Open-Meteo 保存请求坐标和响应网格；中国天气网优先实际支持的区县，只有无该区县产品且已明确配置时才采用城市级并标明范围。请求失败不能自动改用其他区县。未配置建筑时可以预览南京市天气，但不得将市中心坐标自动作为建筑对照输入。

地点、测点、报文语义和计量覆盖变更沿用版本与生效区间，不回写旧结果的说明。跨建筑系统分别展示，不平均不同位置天气。业务日按 Asia/Shanghai，存储时点统一 UTC；保存有效时间、获取时间、明确存在的源发布时间，三者不可互换。

“七天”为今天加未来六天；历史不等于当时发布的历史预报。预报批次从实际采集时开始留存，不能倒造。天气与电量只比较两者实际重叠期间，2024 年有天气不表示该年有电表数据。

### 3.2 来源入口与字段契约

| 产品 | 受控入口 | 请求与规范字段 |
|---|---|---|
| Open-Meteo 当前 | `https://api.open-meteo.com/v1/forecast` | `current=temperature_2m,relative_humidity_2m,weather_code,wind_speed_10m,wind_direction_10m` |
| Open-Meteo 小时预报 | 同上，`forecast_days=7` | `hourly=temperature_2m,relative_humidity_2m,precipitation,weather_code,wind_speed_10m,wind_direction_10m,shortwave_radiation` |
| Open-Meteo 七日日预报备用 | 同上，`forecast_days=7` | `daily=temperature_2m_max,temperature_2m_min,weather_code,wind_speed_10m_max,wind_direction_10m_dominant`；备用组合已通过本次南京 Java 只读获取验证；目标服务器持续运行未验证 |
| Open-Meteo 历史 | `https://archive-api.open-meteo.com/v1/archive` | 上述七个小时字段；日字段只取 `temperature_2m_max,temperature_2m_min,weather_code`，不使用供应商日均值代替研究小时统计；按月指定起止日，不指定固定 ERA5 |
| 中国天气网七日 | `https://www.weather.com.cn/weather/{cityCode}.shtml` | 已验证南京代码 `101190101`；读取 `#7d ul.t > li` 中日期、`p.wea`、`p.tem` 和 `p.win`，正式解析需对保存样本验证选择器 |

Open-Meteo 显式设置 `timezone=Asia/Shanghai`、`wind_speed_unit=ms`、`temperature_unit=celsius`、`precipitation_unit=mm`。小时温度 °C、湿度 %、风速 m/s、风向 °为对应时刻值；降水 mm 为前一小时累计，短波辐射 W/m² 为前一小时平均，按真实期间对齐。依据[历史 API 文档](https://open-meteo.com/en/docs/historical-weather-api)及[预报 API 文档](https://open-meteo.com/en/docs)。保存请求参数、返回单位/时区/网格；未返回的逐小时模型身份和起报时间保持空，`generationtime_ms` 不是发布时间。

中国天气网[南京七天页面](https://www.weather.com.cn/weather/101190101.shtml)采用日列表，不使用原脚本的“分时”命名。高温读取 `p.tem span`，低温读取 `p.tem i`；移除单位符号后分别解析，不能用首个正则数字同时充当两者。夜间缺少今日最高温时置空，不能以最低温补造。风向从风向元素的 `title` 提取，保留白天/夜间多个方向；风力原文保留，不换算为精确 m/s。

日期用已验证的页面当前完整日期作为锚点，结合各行日号与顺序推导完整日期，跨月/跨年递进并保存 `PAGE_DATE_DERIVED`；若页面日期仅由客户端动态生成、缺失、与抓取北京时间不符或七日不连续，不用采集日猜测为最新，标 `DATE_AMBIGUOUS` 或 `STALE_CONTENT`。源端明确发布时间才写入 `sourcePublishedAt`，网站文章发布时间不能代替预报发布时间。来源日天气编码按后端有版本的映射转展示文本，保留原编码；未知编码显示“未知天气代码”，不臆测。

### 3.3 已知条件和上线验证

- 用户已选择免费接口开展企业公开研究。保留来源署名及用途条件：[Open-Meteo 条款](https://open-meteo.com/en/terms)与[套餐](https://open-meteo.com/en/pricing)。当前企业公开研究资格尚未由来源方确认，不把免费 API 决定写成已获商业服务授权。
- 中国天气网存在 [SmartWeatherAPI 申请说明](https://www.weather.com.cn/wzfw/smart/weatherapi.shtml)，当前申请可用性、费用、配额未核实；首期不依赖申请成功，不把网页入口包装为官方免费开放 API。网页持续使用条件保留为上线风险，不扩大为新的来源选型讨论。
- 编码期间完成独立源站验证：正式区县代码、完整备用日字段、跨日/夜间响应、目标服务器 TLS/网络及按计划重复抓取。普通自动化测试只使用脱敏保存样本和替身。
- 数据源选型到此结束；未验证项目进入实施验收，不宣称一次成功证明长期稳定，也不要求全量历史和电表现场验收先完成才能建设独立天气能力。

### 3.4 用电侧已核对依据

通过用户终端回传核对 TDengine 3.2.3.0：原始事件有事件时间、接收时间、数值、质量/迟到标记及建筑、系统、设备、测点标签；分钟表含样本数及均值。近期两侧功率样本间隔约三分钟。七天外机每字段 3361 条、内机 3317 条，条数差不能直接推断连续断报时长。午夜前后样本支持存在六分钟内的近似边界，但不等于整日计算验收。

数据库 KEEP 显示约 3650 天，不等于应用不会按默认 90 天清理，也不证明已有十年数据。已有累计量核心要求真实精确锚点；第 6 节通过包装实际期间接入，保留其约束。原始时间来源、现场方向、覆盖关系、缺测事件和服务器实际清理配置仍需独立确认；无需继续让用户逐条查询数据库才能编写本设计。

## 4. 字段与页面

### 4.1 字段用途

| 字段 | 展示与统计口径 |
|---|---|
| 温度 °C | 当前/小时/来源日高低温；24 个合格历史小时值计算日均温，用于日电量对照 |
| 相对湿度 % | 当前/小时；24 个合格历史小时值计算日均湿度，可切换对照 |
| 降水 mm | 历史与预报小时曲线，表示前一小时累计降水；首期不新增电耗归因计算 |
| 太阳短波辐射 W/m² | 历史与预报小时曲线，表示前一小时平均辐照度，不冒充每日辐射能量 |
| 风速 m/s、风向 ° | Open-Meteo 当前/小时展示；日预报备用用最大风速、主导风向并标明口径 |
| 天气代码/文本 | 概览及历史日说明，保留原代码与有版本的文本映射 |
| 中国天气网风向/风力 | 保留日预报原文，不换算精确数值风速 |

按字段记录缺失，缺一个字段不丢弃其他字段。日均温与日均湿度分别要求北京时间自然日 24 个唯一、有效小时值；不足则日均值留空，仍显示已有小时曲线及覆盖数。不能用日最高/最低温平均代替日均温。历史只使用 Open-Meteo，来源日极值与小时采样极值不假定相等。

### 4.2 页面布局

仅两个页面：`/weather/overview` 和 `/weather/history`。概览提供当前卡片、七日概览、温湿度小时曲线；降水、辐射、风可展开。历史页提供日期范围、日概况和小时曲线，并内嵌“电耗对照”视图，不创建 `/weather/research`。

电耗对照选择建筑、系统、实际内机计量组或外机及日期。默认日用电量柱形＋日均温折线，标明两轴单位，可切换日均湿度；不默认同时叠加多个气象变量。内机/外机分别选择查看，不显示系统合计与占比，不新增散点图、小时功率对照或导出功能。

每个日期保留时间槽；电量缺失只断开电量，天气缺失只断开天气，不填零、不连接缺口。近似日量明确标注，提示实际计量起止时刻、偏差及覆盖对象。只对已结束日展示完整日量；今天可看天气，但电耗对照标“本日未结束”，不新增实时累计用电计算。

### 4.3 七日预报整批回退

中国天气网批次必须覆盖今天至未来六天，日期连续、高低温及天气有效，最近成功获取不超过六小时，且最近更新未失败，才优先整组展示。风字段可单独缺失。夜间今日高温缺失不补造，视为七日必要字段不完整。

优先源不满足条件时，选择满足上述覆盖和字段要求的已存储 Open-Meteo 日预报；不拼接两源日期或单个字段。返回选中来源、批次、回退原因和空间范围。恢复后自动选择合格中国天气网新批次；用户无需切源，历史对照来源不改变。

两源均无合格批次时，显示优先来源最近批次中仍覆盖目标日期的值并标明过期/失败，其余留空；没有该批次才显示 Open-Meteo 的旧批次。不把旧日期重标为今天，不因 HTTP 200 就把旧内容当成最新。

## 5. 更新频率、状态与留存

| 数据/任务 | 首期默认值 |
|---|---|
| Open-Meteo 当前 | 每 15 分钟采集 |
| 两源日预报、Open-Meteo 小时预报 | 每 3 小时；来源独立调度 |
| Open-Meteo 历史 | 首次按月回填，每日补缺并复查最近 7 天 |
| 日用电量最小补齐 | 已确认计量对象次日 00:15 生成/检查，每日复查最近 7 天；已有合格结果优先复用 |
| 对照视图 | 读取已保存的天气与日量按日对齐，不持久化另一套研究配对结果 |

当前天气有效时间超过 60 分钟标过期；预报超过六小时未成功获取标更新超时；历史计划检查超过 36 小时未成功标任务异常，不使已有历史值失效。来源未发布必须有来源可用范围等依据，网络/解析失败不能当作未发布。

天气历史及其当前日统计在本模块使用期间持续保留，支持已有平台备份；预报批次一年，普通当前抓取和日志 90 天。天气版本修订保留批次/解析版本及变更时间；不新增研究引用保护表和专门归档流程。清理不得删除当前查询指针所需内容及在途写入意图；天气存储必须配置匹配的保留期并定期检查，不能依赖 TDengine 默认 KEEP 假定永久保存。

既有电表原始数据默认 90 天保持不变，服务器可覆盖，需部署核查。不增加清理拦截接口或长期全量输入快照。最小日量结果保留数值、状态和必要计算摘要；原始输入已清理时旧结果只能展示，不能承诺重新计算或完整复现。尚未算过且原始数据已清理的日期显示不可计算，不用天气、平均功率或零值补量。未来恢复同日期有效原始数据才可重新计算。

原独立研究项目结束、归档、研究证据删除规则随研究管理能力一起暂缓；不再作为首期页面/任务。用户明确授权删除已存储数据前，不新增批量历史删除功能。

## 6. 日用电量的最小接入

### 6.1 复用优先与计量范围

先复用平台已有已发布且可验证语义的日用电量结果：必须是同一实际计量对象、方向、日期、单位和关系版本，并携带质量/近似说明。已有趋势 AVG、累计电能原值或标为模拟的结果不能充当日用电量。

已有[累计量服务](../../src/main/java/com/platform/energy/aggregation/NativeQuantityAggregationService.java)和[计算核心](../../src/main/java/com/platform/energy/aggregation/EnergyAggregationCore.java)可复用，但尚不等于完整的现场近似自然日量能力。只补充 `DailyElectricityAdapter`：读取必要原始记录、选日界、调用既有治理和核心、保存轻量日结果。缺少同口径结果时用该适配器补齐，不在天气模块另写一套电量公式。

对象按[有效计量关系](../../src/main/java/com/platform/relation/api/RelationGovernanceController.java)解析。一块内机表覆盖多台内机即一个计量组，不分摊、不重复求和。首期逐计量组或外机对象查看；多块表不自动汇总。同一系统/厂家是背景信息，不能代替覆盖配置。

单位、方向、倍率、设备身份和时间来源须明确。外机已应用 PT/CT 倍率的报文不能再次乘倍率；EPP/EPN 固定采用已确认方向，不能沿用前端看板自动切向。改名、换表、周期或覆盖变化按生效关系分段。

### 6.2 必须保留的正确性规则

1. 北京时间自然日两端优先使用精确零点合格读数。“精确”指时刻，不是小数位数。
2. 当前三分钟上报表缺少零点读数时，选零点之前六分钟内（含）的最近合格读数；任一端超限不可计算，不向零点之后取值。任一端不精确则标近似，保存实际时刻和偏差。
3. 同一计算批次内相邻日期共用一次选定的日界；迟到读数改变日界时同时复核两侧日期并原子更新轻量结果，失败则保留旧结果。边界处理不混用不同配置版本。
4. 以实际选中的起止时刻调用原生核心，保持精确锚点约束，不把时间改写成零点。原始读数查询包含终点；治理事件按核心要求 `(起点,终点]` 归属。
5. 读取期间必要累计记录，检查身份、质量、下降和治理事件；仅两端递增不足以证明无复位。未解决复位/换表暂停受影响日期，不取绝对值、不自行修正。证据完整且范围一致才允许分段计算，范围变化时留空并说明。
6. 日内漏报不必然使累计量丢失，但必须通过同表连续计数及事件校验；不能用这点豁免质量要求。质量复用已发布场景策略，不统一硬编码 Q0。
7. 缺失、未配置、质量拒绝、事件未解决、原始数据不可用分别返回原因；后续有效日期可恢复，不因一次异常永久停用。

六分钟是用户确认的本批研究/对照配置，不是行业计量标准。上报周期和设备改变后需重新确认，不自动套用旧参数。普通用户只查看对照，不承担边界参数配置。

### 6.3 轻量日结果而非研究快照

只保存业务日、对象/测点、kWh、状态、方向/单位、起止实际时刻及读数、偏差、关系/质量/计算政策版本、治理事件引用、计算时间和输入摘要哈希。它用于解释结果，不包含期间全部原始读数，也不保证历史任意版本复现。

若已有同语义结果仓储可直接复用则不新增表；否则使用第 8 节单一日量结果表，不引入运行版本、证据分片、引用保护、项目生命周期或研究归档表。重算更新当前日结果并遵循现有操作审计，不构建研究版本浏览功能。

对照只使用合格已结束日电量及对应字段完整的历史天气日均值。近似量可展示并标记；某侧缺失不隐藏另一侧。首期不新增散点样本筛选、纳入/排除统计或近似排除开关。

## 7. 后端模块、HTTP 与任务

沿用 Java/Spring Boot、MySQL、TDengine；不新增服务、运行时或浏览器。Python 原文件仅参考/独立验证，删除模拟兜底思路，日/小时解析分开。

`com.platform.weather.source` 下两个适配器输出统一 `WeatherFetchResult`，包括来源、产品、位置版本、字段/单位、有效时刻/期间、抓取/发布时间、规范数据、字段缺失与解析版本。Java HTTP＋现有 JSON 库，HTML 使用单一 DOM 解析库；如需新增依赖在编码时锁定版本。不执行网页 JavaScript。

职责：`WeatherAcquisitionService` 调度和发布，`WeatherForecastSelectionService` 整批回退，`WeatherHistoryStatisticsService` 日均温湿度，`WeatherQueryService` 查询，`WeatherEnergyComparisonService` 只按日连接已有天气与日电量，`DailyElectricityAdapter` 归用电侧。Controller 不访问源站，前端不重算指标。

来源地址使用第 3.2 节常量及验证过的地区代码，只允许三个来源域名，拒绝任意 URL、未批准跳转及内网目标。TLS 正常校验；管理员不配置任意抓取地址。每来源并发 1、全局最小间隔两秒、有界执行器；连接 10 秒、请求总时限 30 秒、响应上限 2 MiB。遇登录/验证码/禁止访问/结构变化可见失败，不绕过。

任务状态 `QUEUED/RUNNING/RETRY_WAIT/SUCCEEDED/FAILED/BLOCKED/CANCELLED`；HTTP 429/5xx/超时最多三次尝试，30/120 秒退避，遵守 Retry-After。租约 180 秒、每 30 秒续租，栅栏版本防旧 worker 发布。来源未更新为明确成功检查，内容部分缺失标 PARTIAL，不能以网络失败冒充无新数据。

天气和日量任务分别启用，默认关闭，只有位置或计量配置合格才启用。日量自动任务使用明确配置的执行责任账号，每次校验现有 `ENERGY_CALCULATION_RUN` 职责和建筑权限；撤销后暂停，不伪造管理员身份。复用现有任务授权路径，仅增加必要部署配置，不做研究项目配置页面。

幂等键包含任务类型、来源/对象、位置/计算政策、日期范围和计划时槽。首次天气回填按月，优先当前/预报、近期缺口、旧月份。天气每日复查最近七天，日量同样复查近期；更早变更支持管理员指定范围补算，不暗示能恢复已经清理的原始记录。

跨库：先持久化规范载荷和固定写入身份，再幂等写 TDengine、核验行数/内容，最后在 MySQL 事务发布指针并完成任务。失败从同一载荷重放，不能重抓后冒充旧批次；未发布时序对查询不可见。任务状态与内容完整性分开，字段部分缺失可带说明发布，不能覆盖完整旧版冒称更完整。

## 8. 最小数据结构

不预占迁移编号；业务 ID、审计列沿用项目约定，时点 UTC 毫秒、业务日 DATE，来源与产品枚举，坐标 DECIMAL(10,7)，电量 BigDecimal/DECIMAL，源数值时序用 DOUBLE，必要精确边界读数用十进制字符串。

| MySQL 对象 | 最小字段与约束 |
|---|---|
| `biz_weather_location` | 稳定地点身份、城市/区县、坐标、时区、启停；不以可变名称作主键 |
| `biz_weather_binding_version` | 建筑、地点与坐标快照、来源地区代码及层级、生效区间/版本；唯一建筑＋版本，锁内检查区间不重叠 |
| `biz_weather_job` | 类型、来源/对象、范围、配置版本、幂等键、状态、游标、重试、租约/栅栏；唯一幂等键，状态＋下次执行时间索引 |
| `biz_weather_batch` | 每次获取/检查、任务/尝试、来源性质、请求/位置、抓取/发布时间、数据集、状态与错误；保留无变化检查 |
| `biz_weather_dataset` | 不可变身份、来源/产品/位置版本、范围、哈希、解析版、规范压缩载荷、行数/字段覆盖、子表清单、发布状态；同身份重放载荷必须一致 |
| `biz_weather_dataset_head` | 来源＋位置版本＋产品＋业务日唯一，指向已发布数据集；旧 worker 不得回退指针 |
| `biz_energy_daily_comparison_result`（仅现有仓储不足时新增） | 对象、建筑、业务日、计算政策与关系版本、方向、日电量、锚点摘要、状态/原因、计算时间；对象＋业务日＋政策/关系版本唯一，不存完整原始输入，不建研究运行表 |

数据集载荷是天气跨库重放依据，不是研究证据系统；单批压缩后上限 1 MiB、解压后上限 4 MiB，超限分小范围任务，单行不无限增长。相同规范内容及解析版可共享载荷，但获取批次独立记录。日量字段/精度沿用现有能源类型，迁移前校验范围，不静默截断。

| TDengine 超级表 | 隔离与字段 |
|---|---|
| `st_weather_current_v1` | 主时间为固定抓取时刻，按来源/位置版本/月分子表；另存天气有效时刻、五个当前字段、批次 |
| `st_weather_hourly_v1` | 天气有效时间为主时间，每不可变数据集一个子表；七个小时字段、缺失标记；历史和预报隔离 |
| `st_weather_daily_v1` | 业务日零点为主时间，每数据集一个子表；日高低温、原天气编码/文本、来源风字段及日均温湿度/有效小时数，标明来源值或派生值 |

采用当前 TDengine 3.2.3.0 的基础时间主键能力，不假设新版复合主键；不同预报批次不能写同一子表同一有效时刻，不加假毫秒。日派生值保存所用小时数据集身份。首期不新增日电量或小时功率研究时序表。

按一个地点估算每年小时预报 490560 行，两个日预报产品各 20440 行；三类预报最多约 8760 个数据集子表/年（去重前）。部署验收测容量、查询性能与过期清理；历史保留和批次上限不能仅凭行数推断容量。数据集发布/指针/清理共用锁，查询中的数据有短期租约或读取快照保障，清理不能删除在途读写；不实现长期研究引用锁。

Controller 使用 `/v1`，既有 context-path `/api`；复用 `Result<T>`、`PageResponse<T>`，不直接输出实体。天气与对照读取只查平台已保存数据，不触发源站请求或批量计算。

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/weather/locations` | 权限内地点分页，最多 100 |

| `POST /api/v1/weather/buildings/{buildingId}/energy-comparison/jobs` | 已获计算权限人员按范围补齐日量，复用用电服务；202＋jobId，不触发源站抓取 |

管理提交携带 Idempotency-Key，同键不同内容 409。超范围 400；不存在/越权遵循现有统一规范，不泄露其他建筑存在性。业务缺失为可解释状态，不用 500 或零值替代。

读权限复用 `BUILDING_OWNER/ENERGY_MANAGER/PLATFORM_ADMIN` 与 `BuildingScopeService`，管理员 null 全范围与空集合无权限必须区分；计量对象必须再次验证属于该建筑/系统。天气配置和天气任务仅管理员；日量计算保持现有管理角色、动态计算职责与建筑范围，不因天气读权限而允许计算/计量修正。治理事件仍走既有审批。

`DailyEnergyComparisonDto` 每个日期包含 `energyKwh/energyStatus/weatherValue/weatherUnit/weatherStatus`、实际计量范围、近似标记、锚点偏差、来源/数据集身份、计算时间和原因列表。空值可独立存在。页面没有独立“研究运行”、归档或项目配置。日均值后端计算，显示精度与计算精度分离。

天气 DTO 保留 `source/product/dataKind/validTime/fetchedAt/sourcePublishedAt/batchId/datasetId/locationVersion/coverage`，七日增加 selectedSource/fallbackReason；可用性 `READY/PARTIAL/MISSING/NOT_CONFIGURED` 与更新状态 `FRESH/OVERDUE/FAILED/NOT_CHECKED` 分开。模型天气不伪造设备 Q0/Q1/Q2。

**本次用户只授权后端编码；以下前端内容留待另行讨论，不属于本次实现或验收。**

前端模块 `web/src/modules/weather` 使用 api、models、composables、components、pages、routes 与语言文件；接入 `web/src/app/router/index.ts`。天气概览、历史页及其电耗对照共用权限内建筑选择；普通用户不看到来源开关或计算参数。切换条件取消旧请求，防慢响应覆盖新选择；前端只渲染后端结果。

## 11. 本次后端落地与启用边界

本次只实施后端，保持当前权威基线不变。正式入口为 `WeatherController`，`WeatherService` 负责授权及入队，`WeatherQueryService` 集中负责只读查询、整批预报选择、历史日均值和日电量按日对齐，`WeatherWorker`/`WeatherScheduler` 负责后台执行。相关职责合并在同一模块，不拆新服务；前端、菜单、路由和交互尚未实现。

### 11.1 存储细化

- MySQL 迁移为 `V64__mysql_weather_backend.sql`。除第 8 节对象外，增加 `biz_weather_lane` 三条共享通道记录，用于多实例来源串行、退避和租约；`biz_weather_command` 记录整段补采请求的幂等身份，拆月不能绕过同键内容冲突。
- TDengine 发布前必须读回比对。小时/日产品按不可变数据集子表隔离；当前产品按位置版本/月共享子表，以固定抓取时刻定位批次，清理仅删除该批次行。
- 公共查询从 MySQL 已发布数据集的规范载荷读取，避免双库读取中间状态。该载荷同时是跨库重放依据，历史载荷持续保留；不能把 TDengine 全库默认 KEEP 当作永久保存保证。TDengine 物理留存、容量和恢复仍需部署验收。
- 日均温湿度查询时从已发布历史小时载荷分别统计，各自要求 24 个不同整点有效值，并返回小时数据集身份；不新增研究结果快照或另一套日均版本仓储。
- 日用电量只保存每个建筑/系统/测点/日期的当前轻量结果，版本及锚点摘要放入结果中；没有历史版本浏览。原始输入不可用时保留已有结果，并追加 `RECALCULATION_RAW_HISTORY_UNAVAILABLE`，不承诺复现。
- 天气配置变更和后台执行结果写入既有公共审计。历史天气不自动删除；当前批次 90 天、预报一年后分批清理，但保留最近版本和活动任务所需内容。

### 11.2 启用配置

`weather.enabled`、`open-meteo-enabled`、`china-weather-enabled`、`energy-enabled` 默认均为 `false`。公共读取不触发外部请求；管理员即使提交了队列任务，仍须启用对应后台执行开关。

1. 先通过建筑位置版本接口配置已核对坐标、天气网九位地区代码及区县/城市覆盖层级；首次有效时间明确填写北京时间业务日零点，例如已确认历史位置自 2024-01-01 开始有效。不会自动把南京市中心坐标写成真实建筑坐标。
2. 配置 `WEATHER_TASK_ACTOR_ID` 为真实可用管理员账号，再启用 `WEATHER_ENABLED` 及对应来源开关。首次历史按有效位置版本和月份入队；近期修订与旧月份队列分开，当前/预报优先。
3. 电量计算单独启用 `WEATHER_ENERGY_ENABLED`。通过受控部署配置填写 `weather.energy-targets` 的 `building-id/system-id/point-id/actor-id`；责任账号必须具备现有计算职责和建筑范围。列表为空时不自动计算任何电表。
4. 补采使用 `POST /api/v1/weather/jobs`，携带 `Idempotency-Key` 和 `buildingId/source/product/start/end`。历史按日闭区间；当前仅今天，预报今天至未来六天。返回任务列表，使用任务查询获取状态。一次用户提交可因月份或位置版本拆为多项后台任务。
5. 日量补算使用对应建筑的 `energy-comparison/jobs`，传 `systemId/pointId/start/end`。后台额外复核相邻已结束日期，共享本批边界并在一次 MySQL 事务更新。查询中的 `pointId` 是已确认累计电量测点，不是功率测点。

### 11.3 当前计量适配的保守边界

若补算范围外的已有相邻日结果采用不同共享日界，事务拒绝单侧更新并返回 `ADJACENT_DAY_BOUNDARY_CHANGED`，应扩大补算范围；失败时保留既有结果。

当前公共关系查询只提供当前有效计量版本。适配器使用该版本的 `effectiveAt`：更早日期、日界实际读数早于版本生效时刻，以及缺少已确认 kWh 累计属性的对象均返回不可计算原因，不把今天关系追溯套用到旧日期。已保存旧结果仍带原版本摘要；完整历史关系回放不在本次新增。

同日原始来源设备身份变化时，原生累计核心不能直接核对来源身份与物理换表身份，因此暂停该日并返回 `SOURCE_IDENTITY_CHANGED_REQUIRES_REVIEW`。同一来源身份下已审核复位/换表事件仍交由原生核心判断；不取绝对值、不自行猜测分段补量。真实电表字段、方向、倍率和覆盖关系仍需现有治理确认。
