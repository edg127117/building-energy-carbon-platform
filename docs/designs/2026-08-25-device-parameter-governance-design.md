# 设备参数读取与版本治理闭环设计

> **文档状态：活动候选设计，方向、范围和首版治理规则已经用户确认，尚未实现、尚未验证、尚未批准为当前正式基线。**
>
> 当前权威基线仍以 [`PROJECT_STATUS.md`](../../PROJECT_STATUS.md)、当前代码和自动化测试为准。
> 本候选只有在完成实现、范围匹配验证、独立验收并经用户批准后，才能转为正式版本能力。

## 1. 结论

阶段一第三个后台业务闭环锁定为“设备参数读取与版本治理闭环”。它把设备上报、人工录入、
Excel 导入和产品模板中的参数转换为平台可追溯的标准参数事实：

```text
DEVICE / MANUAL / EXCEL / TEMPLATE
→ 标准参数定义与字段映射
→ 原始来源候选与单位归一化
→ 来源一致性和冲突识别
→ 设备参数集草稿
→ 审核或平台管理员直接发布
→ 不可变有效版本
→ 按设备、参数和计算时间查询
→ 公式参数读取边界
```

本闭环只管理平台数据，不向设备下发参数。设备上报只能形成候选事实，不能自动覆盖当前有效
版本；来源之间没有硬编码优先级。回退通过复制历史版本生成更高版本的新版本，不修改历史，
也不向设备发送回滚指令。

首版保持现有 Vue 不变。旧设备档案接口中的额定容量、额定功率和设计 COP 字段由后端兼容层
转换为 `MANUAL` 参数版本，不再直接覆盖扁平参数字段。现有公式不因本候选自动改用设计值或
额定值；只有能源专家确认公式参数依赖后，公式才能通过统一读取边界显式使用有效参数版本。

## 2. 需求依据与当前证据

需求矩阵 `功能清单拆解!A32:M34` 已确认：

- 建立额定功率、容量、设计 COP 等标准设备参数模型；
- 区分 `DEVICE`、`MANUAL`、`EXCEL`、`TEMPLATE` 来源；
- 建设参数映射、来源冲突、版本、差异、生效时间、回退、审计和查询能力；
- 平台侧回退不等于设备回滚；
- 远程下发、设备端修改和设备端回滚本期不开发。

当前代码证据为：

- [`BizEquipment.java`](../../src/main/java/com/platform/hvac/model/entity/BizEquipment.java) 已直接保存
  `ratedCapacity`、`ratedPower` 和 `designCop`，但没有来源、标准参数身份、版本、生效时间或冲突状态；
- [`AssetManagementService.java`](../../src/main/java/com/platform/hvac/asset/service/AssetManagementService.java)
  在设备创建和更新时直接覆盖三个字段；
- [`AssetEquipmentDrawer.vue`](../../web/src/components/admin/AssetEquipmentDrawer.vue) 仍允许旧前端直接编辑
  三个字段，因此后端必须提供兼容路径，不能让旧页面静默失效；
- [`StandardTelemetryMessage.java`](../../src/main/java/com/platform/iot/ingest/standard/StandardTelemetryMessage.java)
  只包含时序指标，没有设备参数上行契约；
- [`JsonTelemetryAdapter.java`](../../telemetry-adapter/src/main/java/com/platform/adapter/parser/JsonTelemetryAdapter.java)
  只把原始字段映射为标准时序指标，不能把设备参数混入该热路径；
- [`ChillerCopFormula.java`](../../src/main/java/com/platform/iot/formula/ChillerCopFormula.java) 使用测点分钟值计算
  实际 COP，不读取设计 COP 或额定功率；
- 数据源与质量使用策略候选已经提供版本、审核、审计、建筑范围和回退状态机参考，但不能直接代替
  设备参数的来源候选、整组版本和单位语义。

当前主要缺口是：

- 现有三个参数是无来源、无版本的可变列；
- “容量”在不同设备类型下可能代表不同物理量，不能按列名猜测统一语义；
- 没有标准参数目录及设备类型适用范围；
- 没有设备参数报文、字段映射、Excel 导入和产品参数模板；
- 没有候选来源、一致性判断、冲突处理和选择记录；
- 没有整组差异、审核、生效、历史查询和平台侧回退；
- 没有供未来公式按计算时间读取有效参数及版本来源的统一边界。

## 3. 目标与非目标

### 3.1 目标

1. 建立按设备类型定义业务语义、物理量、标准单位和精度的标准参数目录；
2. 首版治理可标准化的十进制数值参数，其他数据类型必须后续确认后扩展；
3. 支持 `DEVICE`、`MANUAL`、`EXCEL`、`TEMPLATE` 四类来源候选；
4. 让设备参数使用独立只读上行契约，不混入时序指标报文；
5. 支持来源字段、单位、倍率和偏移的版本化映射；
6. 保存原始值、原始单位、标准值、标准单位、来源引用、来源版本和观测时间；
7. 对同一设备、同一标准参数的当前候选执行一致性和冲突识别；
8. 以“单台设备完整参数集”为版本粒度，支持草稿、审核、发布、差异和回退；
9. 通过建筑范围、角色、事务、修订号和脱敏审计保护治理过程；
10. 兼容旧设备档案字段，后端把实际变化转换为 `MANUAL` 直接发布版本；
11. 提供当前有效、指定时间有效、历史版本、差异、候选和冲突查询；
12. 提供未来公式可批量读取参数值及版本来源的后端接口，但不改变现有公式业务含义；
13. 迁移既有扁平字段时保留原值并显式暴露未映射状态，不猜测专业语义。

### 3.2 非目标

- 不向设备或网关发送参数；
- 不修改设备端配置、不请求设备执行合法性校验、不确认设备侧实际生效；
- 不实现设备端回滚、固件回滚、控制命令、安全联锁或响应执行；
- 不把 MQTT QoS/PUBACK 描述为参数已经审核或生效；
- 不新增 Modbus、BACnet、NB-IoT 等南向驱动；
- 不根据厂家名称、设备类型或字段名猜测参数业务语义、单位、边界和来源优先级；
- 不把额定容量定义成所有设备共用且含义相同的通用字段；
- 不用设计 COP 替换实际 COP，不用额定功率补齐缺失实测功率；
- 不修改现有 Q0/Q1/Q2 生成或使用策略；
- 不开发或修改 Vue 页面、组件、状态和样式；
- 不建设物理空间扩展、完整语义关系、计量边界和能源分摊；
- 不建设未来定时生效、跨实例参数缓存广播或大规模归档清理；
- 不把自动化测试描述为厂家报文、真实设备、现场网络或长期运行验收。

## 4. 既有硬约束处理

| 既有约束 | 本候选处理 | 说明 |
|---|---|---|
| 当前只建设监测、分析和展示 | 保留 | 参数只有平台侧读取、治理和消费，没有设备下行 |
| MySQL 保存结构化业务数据 | 保留 | 参数定义、候选、版本、审核、审计和导入事实全部保存于 MySQL |
| TDengine 保存时序和指标事实 | 保留 | 设备参数不是高频时序，不写入 TDengine |
| 南向协议由网关/适配层转换 | 保留并扩展 | 新增独立参数上行契约和映射，不在平台核心猜测厂家字段 |
| 建筑范围是后端安全边界 | 保留并增强 | 设备归属从 MySQL 设备身份解析，客户端不能覆盖建筑归属 |
| 专业规则由能源专家确认 | 保留 | 参数语义、适用设备、标准单位、精度和边界没有确认时拒绝发布 |
| 协议与设备能力由硬件方确认 | 保留 | 没有报文样例和字段说明时只实现映射框架和拒绝路径 |
| 已发布版本不可改写 | 落实 | 有效和退役版本不可修改或删除，回退创建新版本 |
| 旧前端暂不修改 | 保留并兼容 | 旧字段继续读写兼容，后端内部转为治理版本 |
| 当前公式口径保持不变 | 保留 | 新增读取边界，不改变现有四项公式输入和计算逻辑 |
| 历史设计保持冻结 | 保留 | 本文只承接当前设备参数缺口，不修改旧设计制造完成状态 |

## 5. 核心术语和语义边界

### 5.1 标准参数定义

标准参数定义不是一个只有名称的全局字段。其稳定身份至少由“设备类型 + 参数编码”决定，并明确：

- 业务名称与业务定义；
- 适用设备类型；
- 物理量类型；
- 标准单位；
- 数值精度；
- 可选取值上下限；
- 是否允许公式读取；
- 专业依据或确认引用；
- 启停状态。

相同的“容量”文字如果在冷水机组、水泵或空气处理机组中代表不同物理量，必须使用不同标准参数
定义。定义一旦被候选或版本引用，业务语义、物理量和标准单位不得原地修改；不兼容变化使用新的
参数编码。没有专业确认引用的定义可以保存为草稿，但不能启用或用于发布。

首版只接受可精确保存为 `DECIMAL` 的数值参数。型号、固件版本、枚举模式和复杂结构不借用本模型，
需要时另行确认数据类型和治理规则。

### 5.2 来源候选

来源候选表示“某个来源声称某台设备的某个参数是什么”，不等于平台已经认可：

| 来源 | 含义 | 首版入口 |
|---|---|---|
| `DEVICE` | 设备通过独立上行契约报告 | 协议适配器和参数接入服务 |
| `MANUAL` | 人工或管理 API 录入 | 新治理 API 和旧设备档案兼容入口 |
| `EXCEL` | 固定模板批量导入 | 单建筑 Excel 导入批次 |
| `TEMPLATE` | 已启用设备产品模板中的默认值 | 设备绑定或显式应用模板 |

候选保存来源事实、映射事实和校验结果。未映射、单位不兼容、精度非法或超出已确认范围的候选可以
用于问题查询和审计，但不能进入正式版本。

### 5.3 参数集版本

参数集版本是单台设备在某一生效区间内完整、不可变的参数快照。版本中的每个值都保存选中来源，
因此同一版本可以同时包含来自设备、人工、Excel 和模板的参数，但每个参数只能有一个正式值。

版本是完整快照，不是局部补丁。新版本从当前有效版本复制后修改；未出现在新版本中的参数表示明确
移除。允许发布空参数集以表达“当前没有平台认可参数”，但必须使用 `CLEAR` 变更类型和必填原因。

### 5.4 冲突

同一设备、同一标准参数的可用当前候选经已确认映射转换为同一标准单位后：

- 数值按标准参数声明的精度归一化后相等：`CONSISTENT`；
- 数值不同：`CONFLICTING`；
- 缺少映射：`UNMAPPED`；
- 单位、精度、类型或取值边界不合法：`INVALID`。

软件不设置 `DEVICE > MANUAL > EXCEL > TEMPLATE` 等固定优先级。冲突不会使已经发布的当前版本自动
失效，但会阻止未经选择的新版本发布。解决冲突必须选择具体候选、填写原因并进入草稿和审核记录。

### 5.5 平台侧回退与设备侧回滚

平台侧回退固定为：

```text
选择历史参数集版本
→ 复制为更高版本号草稿
→ 审核或平台管理员直接发布
→ 当前版本退役
→ 新版本立即生效
```

它只改变平台查询和未来公式读取的有效版本，不发送命令，也不证明设备实际参数已经改变。

## 6. 总体架构与数据流

```text
厂家设备报文
→ telemetry-adapter 参数字段映射
→ 标准参数上行契约
→ 设备身份解析和建筑归属校验
→ DEVICE 候选

人工/API ───────────────→ MANUAL 候选
Excel 批次 ─────────────→ EXCEL 候选
产品参数模板 ───────────→ TEMPLATE 候选

候选
→ 标准定义、单位、精度和边界校验
→ 一致性/冲突投影
→ 完整参数集草稿
→ 能源管理员提交 / 平台管理员直接发布
→ 平台管理员审核
→ MySQL 有效版本时间线
→ 管理查询 / 指定时间查询 / DeviceParameterResolver
```

模块职责建议为：

- `com.platform.iot.deviceparameter.definition`：标准参数定义和适用范围；
- `com.platform.iot.deviceparameter.mapping`：设备参数字段映射版本；
- `com.platform.iot.deviceparameter.ingest`：标准参数报文、身份解析、幂等和候选持久化；
- `com.platform.iot.deviceparameter.importing`：Excel 模板、批次校验和候选生成；
- `com.platform.iot.deviceparameter.governance`：候选、冲突、参数集版本、审核、回退和审计；
- `com.platform.iot.deviceparameter.query`：有效版本、差异和公式批量读取；
- `telemetry-adapter`：厂家报文到标准参数上行契约的转换，不管理正式版本。

Controller 只处理请求校验、认证身份和响应包装；Service 负责状态机、权限、事务和冲突；
Repository/Mapper 负责 MySQL；Adapter 负责外部报文和 Excel 边界。参数治理不进入 TDengine。

## 7. 领域模型

### 7.1 `biz_device_parameter_definition`

| 字段 | 类型 | 规则 |
|---|---|---|
| `definition_id` | `VARCHAR(32)` | 内部主键 |
| `equipment_type_code` | `VARCHAR(20)` | 外键到启用设备类型 |
| `parameter_code` | `VARCHAR(50)` | 设备类型内稳定大写编码 |
| `parameter_name` | `VARCHAR(100)` | 展示名称 |
| `business_definition` | `VARCHAR(500)` | 业务含义，启用前必填 |
| `quantity_kind` | `VARCHAR(50)` | 已确认物理量编码 |
| `value_type` | `VARCHAR(20)` | 首版固定 `DECIMAL` |
| `standard_unit` | `VARCHAR(20)` | 标准单位，启用前必填 |
| `value_scale` | `INT` | 允许精度，不能静默改变 |
| `min_value/max_value` | `DECIMAL(30,10)` | 可空；只有专业确认后填写 |
| `formula_readable` | `TINYINT` | 是否允许公式解析器读取 |
| `evidence_reference` | `VARCHAR(255)` | 专业确认或标准依据引用 |
| `status` | `VARCHAR(20)` | `DRAFT/ENABLED/DISABLED` |
| `config_revision` | `INT` | 显式并发更新修订号 |
| `create_by/update_by` | `BIGINT` | 操作者 |
| `create_time/update_time` | `DATETIME(3)` | MySQL 时间 |

唯一键为 `equipment_type_code + parameter_code`。定义被候选、模板、映射或版本引用后，不允许物理删除，
也不允许修改设备类型、参数编码、物理量、标准单位和精度；错误定义必须停用并创建新编码。

### 7.2 `biz_device_parameter_mapping` 与版本

稳定映射保存 `mapping_id`、产品/协议模板身份和当前版本指针；
`biz_device_parameter_mapping_version` 保存：

- `version_no`、`status=DRAFT/ACTIVE/RETIRED`；
- `profile_code/profile_version`；
- 原始 `source_path`；
- `definition_id`；
- `source_unit`、`scale`、`offset`；
- 是否必填；
- 基础版本、复制来源、变更原因、创建与发布时间。

设备参数映射与现有时序指标映射分开，不能用同一条字段映射同时产生时序指标和设备参数。映射发布
只影响后续报文，不重写既有候选；既有候选保留当时的 `mapping_version_id`。

映射中的倍率和偏移必须有厂家或硬件依据。转换后精度超出标准定义且未显式确认舍入规则时拒绝，
不能由 Java 默认截断或四舍五入。

### 7.3 `biz_product_parameter_template`

设备产品草稿可以包含参数模板项：

- `template_parameter_id`；
- `product_id`；
- `definition_id`；
- 原始值、原始单位和标准值；
- 依据说明、必填标志、排序和状态。

当前设备产品只有草稿且未使用时可以原地修改；启用产品或已被设备使用的产品必须复制为新产品，
因此 `product_id` 同时提供稳定模板来源版本。设备绑定或显式应用模板时只生成 `TEMPLATE` 候选，
不自动发布，不覆盖设备当前有效参数。

### 7.4 `biz_device_parameter_candidate`

| 字段 | 说明 |
|---|---|
| `candidate_id` | 候选主键 |
| `building_id/equip_id` | 可信设备归属，不能由外部载荷覆盖 |
| `definition_id` | 已映射时填写；未映射时可空 |
| `source_type` | 四类来源之一 |
| `source_reference/source_version` | 设备报告、操作者、导入批次或产品版本引用 |
| `source_slot_key` | 同一逻辑来源的稳定槽位，用于替代旧候选 |
| `source_parameter_key` | 原始字段路径、Excel 参数码或模板项 |
| `raw_value/raw_unit` | 原始来源事实 |
| `normalized_value/standard_unit` | 映射后的标准值和单位 |
| `mapping_version_id` | 使用的映射版本；人工标准录入可空 |
| `observed_at` | 来源声称参数成立或被观测的时间 |
| `validation_status` | `READY/UNMAPPED/INVALID` |
| `validation_reason` | 稳定原因码，不保存堆栈或敏感载荷 |
| `payload_hash` | 脱敏报文或文件行摘要，用于幂等和追溯 |
| `current_flag/supersedes_candidate_id` | 当前候选标记和被替代候选 |
| `first_seen_at/last_seen_at` | 重复相同报告的首次和最近时间 |

相同来源身份、来源版本、参数和内容哈希重复上报时不创建无界历史，只更新 `last_seen_at`。值或来源版本
变化必须创建新候选，并在同一事务内把相同 `source_slot_key` 的旧候选改为非当前。候选内容不允许原地
修改；错误人工录入通过新候选纠正。

冲突只比较各逻辑来源槽位的最新当前 `READY` 候选，不让全部历史候选永久参与冲突。来源槽位规则为：

- `DEVICE`：设备外部身份、协议模板、原始参数字段和标准参数共同确定；
- `MANUAL`：录入渠道和来源引用共同确定，旧资产接口使用固定 `LEGACY_ASSET_API` 槽位；
- `EXCEL`：业务来源引用和标准参数共同确定，导入批次 ID 只用于审计，不能让每次导入都变成新槽位；
- `TEMPLATE`：设备当前显式应用的产品模板槽位，新产品版本应用时替代旧模板候选。

人工和 Excel 没有稳定业务来源引用时可以保存批次问题，但不能成为当前 `READY` 候选。来源槽位只定义
“同一来源的新事实替代旧事实”，不表达来源优先级，也不删除历史候选。

### 7.5 `biz_device_parameter_conflict` 与成员

冲突头保存设备、标准参数、`OPEN/RESOLVED/OBSOLETE`、修订号、解决人、解决时间和原因；成员表保存
参与比较的候选 ID。解决记录只能选择 `READY` 成员，且不删除其他来源事实。

新候选到达后，如果与当前解决依据不同，旧冲突标记 `OBSOLETE` 并创建新的冲突投影；不能静默复用
过去的人工选择。当前有效参数版本继续服务，直到新版本正式发布。

### 7.6 `biz_device_parameter_set`

每台设备最多一个稳定参数集：

| 字段 | 说明 |
|---|---|
| `parameter_set_id` | 参数集主键 |
| `building_id/equip_id` | 设备与建筑，`equip_id` 唯一 |
| `active_version_id` | 当前有效完整版本，可空 |
| `config_revision` | 草稿、提交和并发控制 |
| `create_time/update_time` | MySQL 时间 |

建筑归属由设备档案派生。设备不能通过参数治理跨建筑移动，设备逻辑删除前需要保留参数历史和审计。

### 7.7 `biz_device_parameter_version`

| 字段 | 说明 |
|---|---|
| `version_id/parameter_set_id` | 版本身份 |
| `version_no` | 参数集内严格递增 |
| `status` | `DRAFT/ACTIVE/RETIRED` |
| `base_version_id` | 创建草稿时的有效版本，用于并发检测 |
| `copied_from_version_id` | 复制或回退来源 |
| `change_type` | `INITIAL/UPDATE/ROLLBACK/CLEAR/MIGRATION` |
| `change_reason` | 发布、回退和清空必填 |
| `owner_user_id` | 草稿归属 |
| `effective_at/retired_at` | 数据库生效区间 |
| `published_by/published_at` | 发布者和发布时间 |
| `create_time/update_time` | 草稿时间；发布后不再更新 |

`biz_device_parameter_version_value` 保存版本中的完整值集合：`definition_id`、标准值、标准单位、
选中候选 ID、来源类型、来源引用、来源版本和观测时间。唯一键为 `version_id + definition_id`。

同一参数集同一时刻只能有一个有效版本。批准或直接发布事务使用数据库当前时间让旧版本退役、新版本
生效，并更新 `active_version_id`。首版不允许回填过去生效时间，也不支持未来定时生效；系统迁移只从
迁移完成时间起生效，不能声称旧扁平值从设备创建时间起就已成立。

### 7.8 审核、审计和导入批次

`biz_device_parameter_review_request` 与业务状态分开，保存目标版本、提交修订号、审核快照摘要、
`PENDING/APPROVED/REJECTED/WITHDRAWN`、提交人、审核人和意见。待审核期间参数集草稿冻结。

`biz_device_parameter_audit_log` 保存创建候选、解决冲突、创建/修改草稿、提交、审核、直接发布、
回退、导入和迁移等脱敏前后摘要。审计表不对可删除草稿建立级联外键；审计写入失败时对应业务事务
回滚。

`biz_device_parameter_import_batch` 保存单建筑 Excel 批次、原始文件名的安全显示值、SHA-256、操作者、
行数、状态和错误摘要。文件本体不落业务数据库。行级错误保存行号、字段和稳定错误码，不保存公式、
外部链接或未脱敏整行内容。

## 8. 状态机和核心工作流

### 8.1 候选进入

所有来源统一执行：

1. 解析可信设备身份或建筑内设备编码；
2. 校验设备存在且未删除；
3. 解析设备类型对应的标准参数定义；
4. 保存原始来源、来源版本和观测时间；
5. 按发布映射执行单位转换；
6. 校验类型、精度和已确认边界；
7. 幂等保存候选；
8. 重建对应参数的当前一致性/冲突投影；
9. 不修改当前有效参数版本。

任何来源进入都只是候选。即使设备上报与当前值不同，也不能自动发布或使公式切换版本。

### 8.2 创建和修改参数集草稿

- 没有有效版本时创建 `INITIAL` 草稿；
- 有有效版本时默认复制完整有效版本创建 `UPDATE` 草稿；
- 草稿值必须选择 `READY` 候选；
- 存在冲突时必须保存解决原因；
- 同一设备只允许一个未完成草稿，避免整组版本合并歧义；
- 能源管理员只能修改自己的草稿；平台管理员可以处理全部草稿；
- 每次变化递增 `config_revision`，请求必须携带期望修订号；
- 待审核时禁止修改、删除或替换候选。

### 8.3 审核和直接发布

能源管理员提交后，平台管理员在一个 MySQL 事务内：

1. 锁定审核请求、参数集、草稿和当前有效版本；
2. 校验建筑范围、角色和提交修订号；
3. 重新校验全部标准定义仍启用；
4. 重新校验选中候选、单位、精度、边界和冲突解决；
5. 校验 `base_version_id` 仍是当前有效版本；
6. 退役旧版本；
7. 发布新完整版本并写数据库生效时间；
8. 更新当前版本指针和修订号；
9. 完成审核并写入审计。

任一项失败全部回滚。平台管理员自己创建的草稿可以执行相同事务直接发布，审计动作必须显式记录
`DIRECT_ADMIN_PUBLISH`，不能伪装成审核批准。

### 8.4 平台侧回退

回退复制历史版本的完整值和来源引用，生成更高版本号 `ROLLBACK` 草稿。发布前仍需重新校验定义、
建筑范围和候选是否可追溯；候选已失效不等于历史版本不可复制，但必须保留原候选引用并填写回退原因。

旧历史版本不重新激活，当前有效版本不原地覆盖。回退发布只影响平台，不触发设备操作。

### 8.5 旧设备档案接口兼容

旧 `/v1/assets/equipment` 创建和更新接口继续保留原三个字段，后端规则为：

1. 设备详情优先从当前有效参数版本映射回旧字段；
2. 没有有效版本时可以回显原扁平列，同时返回附加治理状态 `LEGACY_UNGOVERNED`；
3. 旧客户端提交值与当前显示值相同，视为没有参数变化，不重复创建版本；
4. 实际变化由 `PLATFORM_ADMIN` 兼容入口创建 `MANUAL` 候选和完整新版本；
5. 兼容版本使用固定来源引用 `LEGACY_ASSET_API`，保存前后差异并直接发布；
6. 缺少设备类型参数定义或旧字段映射时，参数变化返回稳定错误，不猜测映射；
7. 参数失败与设备档案更新使用同一事务，禁止设备名称已改但参数版本失败的半成功；
8. 新版本发布后不再同步写扁平列，避免形成两个权威来源；
9. 首个实现保留旧列作为迁移输入和未治理回显，暂不删除数据库列。

旧前端无需修改，但新治理状态、来源、历史和冲突只通过后端 API 提供，旧页面不宣称具备这些管理能力。

## 9. 来源入口设计

### 9.1 设备只读上行

设备参数使用独立标准契约，至少包含：

- `standardVersion`；
- `profileCode/profileVersion`；
- 设备外部身份；
- 幂等 `reportId` 或厂家配置版本；
- `reportedAt/receivedAt`；
- 参数项的标准参数编码、原始字段路径、原始值/单位、标准值/单位和映射版本。

建筑和平台设备 ID 不接受设备声明，必须由已启用身份绑定解析。适配器先验证完整报文，再发布完整参数
报告；平台在候选成功持久化后才返回应用处理成功。Broker PUBACK 只证明 Broker 收到消息，不代表平台
候选已经持久化，更不代表参数已经审核生效。

具体厂家字段路径、参数版本含义、Topic/路由和取值范围必须由硬件方提供。没有样例时实现合成契约、
映射框架和拒绝测试，不写任何厂家专用默认路径。

### 9.2 Excel 导入

首版固定一个建筑一个批次，工作表逻辑字段为：

| 字段 | 含义 |
|---|---|
| `equipmentCode` | 建筑内设备编码 |
| `parameterCode` | 对应设备类型的标准参数编码 |
| `value` | 十进制数值，禁止公式单元格 |
| `unit` | 来源单位 |
| `observedAt` | 可空的来源观测时间 |
| `sourceReference` | 可空的台账、厂家文档或批次引用 |

只接受无宏 `.xlsx`。拒绝加密文件、公式单元格、外部链接、重复设备参数行和跨建筑设备。文件大小、
行数和文本长度使用可配置正数上限，实施时通过安全默认和边界测试确认，不在设计中伪造业务阈值。

导入先完整解析和校验全部行；任一行失败时不生成任何候选，返回批次及行级错误。全部通过后在一个
事务内生成 `EXCEL` 候选和冲突投影，但仍不创建或发布正式版本。

### 9.3 产品模板

产品参数模板只能引用同一设备类型的启用标准定义。产品启用后模板内容不可原地修改；变化必须复制
为新产品草稿。设备绑定或显式应用模板时创建 `TEMPLATE` 候选，来源引用保存 `product_id`，不自动
发布，也不覆盖设备已有参数。

### 9.4 人工录入

新治理 API 的人工值先生成 `MANUAL` 候选，再被草稿选用。能源管理员走提交审核；平台管理员可以
直接发布自己的完整草稿。人工录入必须说明来源或变更原因，不能只保存一个没有依据的数值。

## 10. 权限和数据可见性

### 10.1 `BUILDING_OWNER`

在授权建筑内只能查看设备当前有效参数和普通查询所需的生效时间。不能查看候选、冲突、草稿、历史
版本、来源原始字段、审核、操作者和审计。

### 10.2 `ENERGY_MANAGER`

在授权建筑内可以：

- 查看正式参数和自己可见的来源候选；
- 创建 `MANUAL` 候选和完整参数集草稿；
- 选择候选并记录冲突解决原因；
- 查看和修改自己的未提交草稿；
- 提交、撤回自己的审核申请；
- 查看自己的历史版本、审核结果和相关脱敏审计；
- 导入单个授权建筑的 Excel 候选。

不能直接发布、审核、管理全局标准定义和协议映射，也不能查看他人的草稿和操作者信息。发现他人草稿
时只返回设备已有待处理草稿，不泄露所有者。

### 10.3 `PLATFORM_ADMIN`

可以管理标准定义、参数映射、产品参数模板、全部建筑的候选、冲突、版本、审核和审计；可以审核能源
管理员提交的草稿，也可以直接发布自己的草稿和兼容旧设备档案变更。首版不要求另一名管理员复核。

### 10.4 `THIRD_PARTY`

不开放参数治理和参数历史接口。未来开放公式或外部参数查询必须另行确认最小字段和建筑授权范围。

所有设备范围权限都先从 `equip_id` 查询可信 `building_id`，再调用 `BuildingScopeService`。列表请求的
建筑条件只是过滤条件，不是授权来源。

## 11. 查询、差异和公式读取

### 11.1 当前和指定时间查询

查询服务支持：

- 当前有效完整参数集；
- 指定 `at` 时间的有效完整参数集；
- 参数集历史版本分页；
- 两个版本的新增、删除、值变化、单位变化和来源变化；
- 当前候选一致性、冲突及解决状态；
- 未映射和非法候选问题清单。

指定时间使用 MySQL 生效区间：`effective_at <= at < retired_at`，`retired_at` 为空表示当前有效。没有有效
版本返回明确 `NO_EFFECTIVE_PARAMETER_VERSION`，不能回退到模板、设备最新上报或旧扁平字段供公式使用。

### 11.2 `DeviceParameterResolver`

公式侧只通过批量解析接口读取：

```text
resolve(equipmentId, calculationTime, requiredParameterCodes)
→ value + standardUnit + definitionId + versionId
  + sourceType + sourceReference + observedAt + effectiveAt
```

解析规则为：

- 设备、参数定义和版本都必须存在；
- 定义必须启用且 `formula_readable=1`；
- 只读取计算时间所在的正式版本，不读取候选；
- 缺失、停用、单位不兼容或版本不可用时返回稳定失败原因；
- 一次公式计算批量读取并固定全部版本 ID，不能在计算中途跨版本；
- 未来公式结果必须持久化实际参数版本来源，保证历史可解释。

首版没有现有公式声明设备参数依赖，因此只实现解析边界、查询和自动化测试，不修改现有 COP、泵效率、
冷却塔效率和 AHU 指标。新增公式参数依赖必须由能源专家独立确认并在对应公式 PR 接入。

首版解析器使用 MySQL 批量查询，不提前建设全量内存快照或多实例广播。只有实际公式负载证明存在性能
问题时，才基于版本时间线增加缓存和失效机制。

## 12. API 契约边界

管理 API 继续使用 `/v1`、稳定 DTO、`Result<T>` 和 `PageResponse<T>`，不暴露 MyBatis 对象。建议资源：

- `/v1/device-parameter-definitions`：标准定义草稿、启停和查询；
- `/v1/device-parameter-mappings`：映射草稿、版本、发布和回退；
- `/v1/device-parameter-imports`：Excel 批次创建和结果查询；
- `/v1/device-parameters/equipment/{equipmentId}/candidates`：候选和问题查询；
- `/v1/device-parameters/equipment/{equipmentId}/conflicts`：冲突查看和解决；
- `/v1/device-parameters/equipment/{equipmentId}/versions`：草稿、历史、差异和回退；
- `/v1/device-parameters/equipment/{equipmentId}/effective`：当前或指定时间有效参数；
- `/v1/device-parameter-reviews`：提交、撤回、批准和拒绝；
- `/v1/device-parameter-audits`：脱敏审计分页。

设备上行契约不复用管理 API；具体 MQTT/适配器路由由配置承载，不在 URL 或 Java 常量中猜测厂家路径。

响应必须显式返回 `allowedActions`、版本状态、修订号、冲突状态、生效时间和来源摘要。前端不能自行推断
角色权限、版本状态机或冲突结果。

## 13. 校验和稳定错误码

核心校验包括：

1. 设备存在且设备、类型和建筑关系一致；
2. 用户角色和建筑范围满足操作；
3. 标准定义启用、设备类型匹配且具备专业依据；
4. 来源类型只能是四个固定值；
5. 原始单位可以映射到标准单位；
6. 数值满足类型、精度和已确认边界；
7. 映射版本与协议模板匹配；
8. 选中候选属于同一设备和标准定义；
9. 冲突已经显式解决；
10. 完整版本中同一标准参数只有一个值；
11. 基础版本、修订号和当前有效版本未变化；
12. 待审核草稿未被修改；
13. 回退来源属于同一设备；
14. Excel 批次不跨建筑且没有重复行；
15. 公式只读取正式版本和允许公式读取的定义。

稳定机器错误码至少包括：

- `DEVICE_PARAMETER_VALIDATION_FAILED`；
- `DEVICE_PARAMETER_DEFINITION_NOT_FOUND`；
- `DEVICE_PARAMETER_MAPPING_NOT_FOUND`；
- `DEVICE_PARAMETER_UNIT_INCOMPATIBLE`；
- `DEVICE_PARAMETER_PRECISION_INVALID`；
- `DEVICE_PARAMETER_VALUE_OUT_OF_RANGE`；
- `DEVICE_PARAMETER_CANDIDATE_CONFLICT`；
- `DEVICE_PARAMETER_DRAFT_CONFLICT`；
- `DEVICE_PARAMETER_VERSION_CONFLICT`；
- `DEVICE_PARAMETER_REVIEW_CONFLICT`；
- `DEVICE_PARAMETER_NO_EFFECTIVE_VERSION`；
- `DEVICE_PARAMETER_IMPORT_REJECTED`；
- `DEVICE_PARAMETER_LEGACY_MAPPING_MISSING`；
- `DEVICE_PARAMETER_FORBIDDEN`；
- `DEVICE_PARAMETER_NOT_FOUND`。

HTTP 状态保持：校验失败 `400`，未登录 `401`，越权 `403`，不存在 `404`，状态/引用/并发冲突 `409`。

## 14. 事务、并发和幂等

- 候选单条写入及冲突投影在一个事务内完成；
- Excel 全批候选和冲突投影全部成功或全部回滚；
- 设备参数报告以设备身份、报告 ID/来源版本和内容哈希幂等；
- 草稿使用 `config_revision` 显式乐观并发，审核提交保存修订号；
- 审核批准、直接发布和回退发布锁定参数集及当前版本；
- 旧版本退役、新版本生效、当前指针、审核和审计同事务提交；
- 旧设备档案字段变更和参数版本直接发布同事务提交；
- 外部报文解析失败不写部分候选；
- 审计失败不允许业务发布成功；
- 不使用数据库级联删除正式版本、候选来源或审计事实。

## 15. 既有扁平字段迁移

迁移按以下顺序执行：

1. 创建标准定义、映射、候选、参数集、版本、审核、审计和导入表；
2. 扫描 `biz_equipment.rated_capacity/rated_power/design_cop` 非空值；
3. 每个旧值以 `source_type=MANUAL`、`source_reference=LEGACY_BIZ_EQUIPMENT` 保存迁移候选；
4. 只有设备类型存在已确认且唯一的旧字段到标准定义映射时才归一化；
5. 缺少映射的值标记 `UNMAPPED` 并进入迁移问题查询，不自动发布；
6. 已映射值通过校验后生成 `MIGRATION` 完整参数版本，从迁移事务完成时间起生效；
7. 保存迁移版本、旧字段摘要和系统审计；
8. 设备详情优先读取有效治理版本，无版本时继续回显旧值并标记 `LEGACY_UNGOVERNED`；
9. 新写入不再更新旧列，首版不删除旧列；
10. 迁移脚本可安全重跑，相同迁移候选和版本不得重复创建。

现有种子数据中某些“额定容量”值可能与额定功率相同，不能据此推断容量含义。专业映射未确认前必须
保持未映射状态，不能为了迁移通过而自动创建参数定义。

## 16. 验证与验收标准

### 16.1 自动化验证

#### 数据模型与迁移

- MySQL 迁移契约覆盖表、索引、唯一键、外键和可重跑检查；
- H2 测试结构覆盖参数治理表和旧字段兼容；
- 已确认旧字段映射可迁移成唯一有效版本；
- 未确认“容量”映射只形成 `UNMAPPED` 候选；
- 迁移重跑不重复候选、版本或审计。

#### 来源、映射和冲突

- 四类来源均能生成候选；
- 相同标准值形成一致状态，不同值形成冲突；
- 没有固定来源优先级；
- 映射缺失、单位不兼容、精度非法和超界均不能发布；
- 映射升级不重写历史候选；
- 重复设备报告幂等，变化报告创建新候选。

#### Excel

- 正常固定模板整批生成候选；
- 任一错误行让整批不生成候选；
- 跨建筑、重复行、公式单元格、外部链接、加密或宏文件被拒绝；
- 文件和行级错误不泄露敏感内容。

#### 状态、事务和并发

- 能源管理员草稿提交、平台管理员审核发布完整通过；
- 平台管理员直接发布有独立审计动作；
- 版本发布原子切换，任一步失败全部回滚；
- 待审核草稿冻结；
- 过期修订号和过期基础版本返回 `409`；
- 回退创建更高版本，不修改历史；
- 空参数集只能通过明确 `CLEAR` 发布；
- 审计失败使业务事务回滚。

#### 权限和建筑范围

- 建筑业主只能查看授权建筑当前有效参数；
- 能源管理员只能操作授权建筑和自己的草稿；
- 平台管理员可以管理定义、映射、审核和全部建筑；
- 第三方不能访问治理接口；
- 客户端伪造建筑 ID 不能越过设备真实归属。

#### 查询、公式和兼容

- 当前及指定时间查询命中正确版本区间；
- 差异正确区分新增、删除、值和来源变化；
- 公式解析器只返回正式、允许读取的参数并携带版本来源；
- 缺少有效版本不回退到模板、候选或旧列；
- 现有四项公式结果和输入保持不变；
- 旧设备页面契约字段保持兼容；
- 旧接口实际参数变化生成 `MANUAL` 直接发布版本且不双写旧列。

#### 测试隔离

- 普通测试使用 H2、Mock、Stub 和合成 Excel/报文；
- 不连接真实 MySQL、MQTT Broker、厂家设备、现场网络或外部文件服务；
- 自动化结果不得描述为真实设备或现场验收。

### 16.2 业务验收

1. 能源专家确认首批参数定义、设备类型适用范围、标准单位、精度和边界；
2. 硬件方提供至少一个设备参数报文样例、字段路径、单位和版本说明；
3. 四类来源可形成可查询候选，且不会自动生效；
4. 同值来源显示一致，不同值显示冲突且无默认优先级；
5. 能源管理员能够选择候选形成完整草稿并提交；
6. 平台管理员批准后整组参数立即生效，历史版本不可修改；
7. 查询能够返回当前、指定时间、来源和版本差异；
8. 平台回退生成更高版本，不向设备发送命令；
9. 旧设备页面不修改仍可读写三个兼容字段，并生成版本和审计；
10. 未声明参数依赖的现有公式结果不变化；
11. 目标 MySQL 8 迁移、真实 Excel 和厂家报文联调单独记录证据；
12. 独立验收和用户批准与代码合并保持分离。

## 17. 实施范围与顺序

本候选后续作为一个独立实现 PR 完成后端软件闭环，不与空间语义、计量分摊或前端改造混合。建议顺序：

1. MySQL 迁移、标准定义、候选、冲突、参数集版本、审核和审计模型；
2. 标准定义和映射治理 Service/API；
3. 四类来源候选入口、Excel 导入和参数报文适配；
4. 参数集草稿、审核、直接发布、差异和回退；
5. 建筑范围、角色、错误码、事务、并发和幂等；
6. 当前/指定时间查询和 `DeviceParameterResolver`；
7. 旧设备档案兼容和既有扁平字段迁移；
8. 定向测试、完整后端验证、前端兼容验证和状态文档同步。

实现 PR 必须保持一个完整闭环，不能交付“只有表没有发布状态机”“只有导入没有冲突处理”或“只有
版本 API 没有查询/公式读取”的半完成状态。具体厂家映射和专业参数定义没有输入时可以保持未映射和
拒绝路径，但不能用合成规则伪装现场能力。

## 18. 已确认事项与未解决边界

### 18.1 已确认

- 参数治理是独立于空间语义的后端闭环；
- 标准参数定义包含设备类型、语义、物理量、单位、精度、边界和公式可读性；
- 参数集以单台设备完整快照为版本粒度；
- 来源固定为 `DEVICE/MANUAL/EXCEL/TEMPLATE`，不设置自动优先级；
- 冲突必须显式选择和记录原因后才能发布；
- 能源管理员提交，平台管理员审核；平台管理员可直接发布自己的草稿；
- 批准后立即生效，首版不做未来定时生效和普通回填生效；
- 历史版本不可修改，回退创建更高版本；
- 旧前端不修改，后端把实际参数变化转换为 `MANUAL` 直接发布版本；
- 设备参数使用独立只读上行契约，不混入时序指标；
- Excel 整批校验、整批形成候选，永不直接发布；
- 产品模板只产生候选；
- 查询和公式只读取正式有效版本；
- 现有公式不自动使用设计 COP、额定功率或容量；
- 不向设备下发参数，不实现设备端修改、校验或回滚；
- 参数实现 PR 与空间语义 PR 分离。

### 18.2 外部输入未解决且不得猜测

- 首批标准参数的正式编码、业务定义、设备类型适用范围、物理量、单位、精度和边界；
- 旧 `rated_capacity` 在各设备类型下的准确业务含义；
- 厂家设备参数报文样例、字段路径、原始单位、配置版本含义和报告时机；
- 真实产品模板参数和值依据；
- 真实 Excel 台账样例和业务验收数据；
- 哪些未来公式需要哪些参数，以及参数缺失时的专业失败语义；
- 真实设备、云环境、TLS、现场网络和长期运行验收。

这些输入不阻塞通用治理框架、拒绝路径和合成自动化实现，但会阻塞对应真实映射、专业参数发布和现场
闭环声明。

### 18.3 明确延期

- 非十进制参数类型；
- 未来定时生效和历史回填生效；
- 参数缓存、多实例广播和实例状态聚合；
- 原始文件长期归档、法规保留和最终物理清理；
- 管理端 Vue 页面；
- 空间语义、计量边界、分摊和分层查询；
- 设备参数下发、生效回读、安全联锁和设备端回滚。
