# 标准设备参数读取与参数版本治理闭环设计

> **文档状态：活动候选设计，方向、范围和首版治理规则已经用户确认，尚未实现、尚未验证、尚未批准为当前正式基线。**
>
> 当前权威基线仍以 [`PROJECT_STATUS.md`](../../PROJECT_STATUS.md)、当前代码和自动化测试为准。
> 本候选只有在完成实现、范围匹配验证、独立验收并经用户批准后，才能转为正式版本能力。

## 1. 结论

阶段一第三个后台业务闭环锁定为“标准设备参数读取与参数版本治理闭环”。这里的“版本”只指
设备技术参数集版本，不包含厂家、型号的档案版本，也不包含设备投运、停用、报废及状态流转。
本闭环把设备上报、人工录入、
Excel 导入和产品模板中的参数转换为平台可追溯的标准参数事实：

```text
DEVICE / MANUAL / EXCEL / TEMPLATE
→ 标准参数定义与字段映射
→ 原始来源候选与单位归一化
→ 来源一致性和冲突识别
→ 设备参数集草稿
→ 提交人与审核人分离的审核发布
→ 不可变双时间有效版本
→ 按业务时间和平台认知时间查询
→ 公式参数版本留痕、影响分析和受控历史重算
```

本闭环只管理平台数据，不向设备下发参数。设备上报只能形成候选事实，不能自动覆盖当前有效
版本；来源之间没有硬编码优先级。回退通过复制历史版本生成更高版本的新版本，不修改历史，
也不向设备发送回滚指令。

首版保持现有 Vue 不变。旧设备档案接口提交的额定容量、额定功率和设计 COP 与当前生效值相同
时按未变更处理；实际修改必须由后端明确拒绝，不能绕过新治理入口。旧字段在生产切换后只作为
当前生效版本的只读兼容投影。现有公式不因本候选自动改用设计值或额定值；只有能源专家确认
公式参数依赖后，公式才能通过统一读取边界显式使用有效参数版本。

## 2. 需求依据与当前证据

需求矩阵 `功能清单拆解!A32:M34` 已确认：

- 建立额定功率、容量、设计 COP 等标准设备参数模型；
- 区分 `DEVICE`、`MANUAL`、`EXCEL`、`TEMPLATE` 来源；
- 建设参数映射、来源冲突、版本、差异、生效时间、回退、审计和查询能力；
- 平台侧回退不等于设备回滚；
- 远程下发、设备端修改和设备端回滚本期不开发。

当前代码证据为：

- [`BizEquipment.java`](../../src/main/java/com/platform/hvac/model/entity/BizEquipment.java) 已直接保存
  `ratedCapacity`、`ratedPower` 和 `designCop`，但没有来源、标准参数身份、版本、生效时间或冲突状态；
- [`AssetManagementService.java`](../../src/main/java/com/platform/hvac/asset/service/AssetManagementService.java)
  在设备创建和更新时直接覆盖三个字段；
- [`AssetEquipmentDrawer.vue`](../../web/src/components/admin/AssetEquipmentDrawer.vue) 仍允许旧前端直接编辑
  三个字段，因此后端必须提供兼容路径，不能让旧页面静默失效；
- [`StandardTelemetryMessage.java`](../../src/main/java/com/platform/iot/ingest/standard/StandardTelemetryMessage.java)
  只包含时序指标，没有设备参数上行契约；
- [`JsonTelemetryAdapter.java`](../../telemetry-adapter/src/main/java/com/platform/adapter/parser/JsonTelemetryAdapter.java)
  只把原始字段映射为标准时序指标，不能把设备参数混入该热路径；
- [`ChillerCopFormula.java`](../../src/main/java/com/platform/iot/formula/ChillerCopFormula.java) 使用测点分钟值计算
  实际 COP，不读取设计 COP 或额定功率；
- [`FormulaCalculationAttempt.java`](../../src/main/java/com/platform/iot/formula/model/FormulaCalculationAttempt.java)
  已保存追加式公式计算尝试、公式版本和策略证据；
- [`TdengineIndicatorMinuteRepository.java`](../../src/main/java/com/platform/iot/temporal/impl/TdengineIndicatorMinuteRepository.java)
  的现有作废流程仍会删除当前成功结果行，计算尝试也不保存成功值，因此尚不能复现追溯修正前后的
  两个结果值；
- [`DataQualityRecalculationJobService.java`](../../src/main/java/com/platform/iot/dataquality/DataQualityRecalculationJobService.java)
  已有可恢复范围重算任务，本闭环应扩展而不是另建不兼容重算体系；
- 数据源与质量使用策略候选已经提供版本、审核、审计、建筑范围和回退状态机参考，但不能直接代替
  设备参数的来源候选、整组版本和单位语义。

当前主要缺口是：

- 现有三个参数是无来源、无版本的可变列；
- “容量”在不同设备类型下可能代表不同物理量，不能按列名猜测统一语义；
- 没有标准参数目录及设备类型适用范围；
- 没有设备参数报文、字段映射、Excel 导入和产品参数模板；
- 没有候选来源、一致性判断、冲突处理和选择记录；
- 没有整组差异、审核、生效、历史查询和平台侧回退；
- 没有供未来公式按计算时间读取有效参数及版本来源的统一边界。

## 3. 目标与非目标

### 3.1 目标

1. 建立全局唯一标准参数定义，并以独立适用关系声明设备类型、必填性、专业边界和公式可读性；
2. 首版治理可标准化的十进制数值参数，其他数据类型必须后续确认后扩展；
3. 支持 `DEVICE`、`MANUAL`、`EXCEL`、`TEMPLATE` 四类来源候选；
4. 让设备参数使用独立只读上行契约，不混入时序指标报文；
5. 支持来源字段、单位、倍率和偏移的版本化映射；
6. 保存原始值、原始单位、标准值、标准单位、来源引用、来源版本和观测时间；
7. 以“设备 + 标准参数 + 来源类型”为来源槽位，对各槽位当前候选执行一致性和冲突识别；
8. 以“单台设备完整参数集”为版本粒度，支持草稿、审核、发布、差异和回退；
9. 通过建筑范围、角色、事务、修订号和脱敏审计保护治理过程；
10. 旧设备档案字段只读兼容，禁止旧接口实际参数变化绕过候选、审核和发布；
11. 提供当前有效、按业务时间有效、按平台认知时间还原、历史版本、差异、候选和冲突查询；
12. 提供公式批量读取、参数版本留痕、追溯影响分析、历史结果作废与可恢复重算边界；
13. 支持审核后立即生效和受控追溯生效，但不支持未来预约生效；
14. 迁移既有扁平字段时保留原值并显式暴露未映射、待专业确认状态，不猜测专业语义。

### 3.2 非目标

- 不向设备或网关发送参数；
- 不修改设备端配置、不请求设备执行合法性校验、不确认设备侧实际生效；
- 不实现设备端回滚、固件回滚、控制命令、安全联锁或响应执行；
- 不把 MQTT QoS/PUBACK 描述为参数已经审核或生效；
- 不新增 Modbus、BACnet、NB-IoT 等南向驱动；
- 不根据厂家名称、设备类型或字段名猜测参数业务语义、单位、边界和来源优先级；
- 不把厂家、型号当作设备参数版本项；它们只作为设备或产品档案上下文参与匹配和追溯；
- 不建设设备投运、停用、报废时间及状态流转；设备生命周期另行治理；
- 不把额定容量定义成所有设备共用且含义相同的通用字段；
- 不用设计 COP 替换实际 COP，不用额定功率补齐缺失实测功率；
- 不修改现有 Q0/Q1/Q2 生成或使用策略；
- 不开发或修改 Vue 页面、组件、状态和样式；
- 不建设物理空间扩展、完整语义关系、计量边界和能源分摊；
- 不建设未来预约生效、跨实例参数缓存广播或大规模归档清理；
- 不把自动化测试描述为厂家报文、真实设备、现场网络或长期运行验收。

## 5. 核心术语和语义边界

### 5.1 标准参数定义

标准参数定义使用全局唯一 `parameter_code` 作为稳定业务身份，并明确：

- 业务名称与业务定义；
- 物理量类型；
- 标准单位；
- 存储精度和展示精度；
- 专业依据或确认引用；
- 启停状态。

标准参数与设备类型使用独立适用关系，声明必填/可选、专业硬限制、建议范围、比较容差和公式可读性。
设备参数值的稳定身份为“设备 ID + 标准参数定义 ID”。相同的“容量”文字如果代表额定制冷量、
额定制热量、流量、风量或储能容量，必须使用不同全局参数编码，禁止建立含义模糊的通用
`RATED_CAPACITY`。系统组合或系统分组的设计参数不借用本设备参数模型。

定义一旦被候选或版本引用，业务语义、物理量和标准单位不得原地修改；不兼容变化使用新的参数编码。
没有专业确认引用的定义和适用关系可以保存为草稿，但不能用于生产发布。

首版只接受可精确保存为 `DECIMAL` 的数值参数。型号、固件版本、枚举模式和复杂结构不借用本模型，
需要时另行确认数据类型和治理规则。

### 5.2 来源候选

来源候选表示“某个来源声称某台设备的某个参数是什么”，不等于平台已经认可：

| 来源 | 含义 | 首版入口 |
|---|---|---|
| `DEVICE` | 设备通过独立上行契约报告 | 协议适配器和参数接入服务 |
| `MANUAL` | 人工或管理 API 录入 | 新治理 API；旧设备档案接口不再作为写入口 |
| `EXCEL` | 固定模板批量导入 | 单建筑 Excel 导入批次 |
| `TEMPLATE` | 已启用设备产品模板中的默认值 | 设备绑定或显式应用模板 |

候选保存来源事实、映射事实和校验结果。类型错误、单位不兼容或转换失败属于硬失败，不能进入正式
版本。专业建议范围属于警告；审核人填写理由后可以批准。专业范围未配置时必须显式返回
`RANGE_NOT_CONFIGURED`，允许进入人工审核，但不能宣称已完成专业合理性校验。

### 5.3 参数集版本

参数集版本是单台设备在某一生效区间内完整、不可变的参数快照。版本中的每个值都保存选中来源，
因此同一版本可以同时包含来自设备、人工、Excel 和模板的参数，但每个参数只能有一个正式值。

版本是完整快照，不是局部补丁。新版本从当前认知下、目标业务时间有效的完整版本复制后修改；发布
前必须展示完整差异。每个适用参数都要保存“有值”或“明确未配置”状态，缺失不等于零。必填参数
缺失时禁止发布，可选参数可以明确未配置并保存原因。

### 5.4 冲突

同一设备、同一标准参数的可用当前候选经已确认映射转换为同一标准单位后：

- 标准化后的精确十进制值相等，或在已确认比较容差内：`CONSISTENT`；
- 数值不同：`CONFLICTING`；
- 缺少映射：`UNMAPPED`；
- 单位、存储精度、类型或专业硬限制不合法：`INVALID`。

软件不设置 `DEVICE > MANUAL > EXCEL > TEMPLATE` 等固定优先级。冲突不会使已经发布的当前版本自动
失效，但会阻止未经选择的新版本发布。解决冲突必须选择具体候选、填写原因并进入草稿和审核记录。

### 5.5 平台侧回退与设备侧回滚

平台侧回退固定为：

```text
选择历史参数集版本
→ 复制为更高版本号草稿
→ 重新提交并由另一名具备审批权限的人员审核
→ 生成更高版本号的新发布事实
→ 按立即或受控追溯时间进入当前认知时间线
```

它只改变平台查询和未来公式读取的有效版本，不发送命令，也不证明设备实际参数已经改变。

## 6. 总体架构与数据流

```text
厂家设备报文
→ telemetry-adapter 参数字段映射
→ 标准参数上行契约
→ 设备身份解析和建筑归属校验
→ DEVICE 候选

人工/API ───────────────→ MANUAL 候选
Excel 批次 ─────────────→ EXCEL 候选
产品参数模板 ───────────→ TEMPLATE 候选

候选
→ 标准定义、单位、精度和边界校验
→ 一致性/冲突投影
→ 完整参数集草稿
→ 具备提交权限的人员提交
→ 另一名具备审核权限的人员批准
→ MySQL 双时间版本与不可变时间线修订
→ 当前认知 / 历史认知查询 / DeviceParameterResolver
→ 追溯影响分析 / 追加式公式尝试 / 作废与重算
```

模块职责建议为：

- `com.platform.iot.deviceparameter.definition`：标准参数定义和适用范围；
- `com.platform.iot.deviceparameter.mapping`：设备参数字段映射版本；
- `com.platform.iot.deviceparameter.ingest`：标准参数报文、身份解析、幂等和候选持久化；
- `com.platform.iot.deviceparameter.importing`：Excel 模板、批次校验和候选生成；
- `com.platform.iot.deviceparameter.governance`：候选、冲突、参数集版本、审核、回退和审计；
- `com.platform.iot.deviceparameter.query`：有效版本、差异和公式批量读取；
- `telemetry-adapter`：厂家报文到标准参数上行契约的转换，不管理正式版本。

Controller 只处理请求校验、认证身份和响应包装；Service 负责状态机、权限、事务和冲突；
Repository/Mapper 负责 MySQL；Adapter 负责外部报文和 Excel 边界。参数定义、候选和版本不写入
TDengine；公式参数版本证据、作废状态和重算尝试沿用既有 TDengine 追加事实与当前投影。

## 7. 领域模型

### 7.1 `biz_device_parameter_definition`

| 字段 | 类型 | 规则 |
|---|---|---|
| `definition_id` | `VARCHAR(32)` | 内部主键 |
| `parameter_code` | `VARCHAR(50)` | 全局唯一稳定大写编码 |
| `parameter_name` | `VARCHAR(100)` | 展示名称 |
| `business_definition` | `VARCHAR(500)` | 业务含义，启用前必填 |
| `quantity_kind` | `VARCHAR(50)` | 已确认物理量编码 |
| `value_type` | `VARCHAR(20)` | 首版固定 `DECIMAL` |
| `standard_unit` | `VARCHAR(20)` | 标准单位，启用前必填 |
| `storage_scale/display_scale` | `INT` | 存储精度与展示精度分离，不静默截断原始值 |
| `evidence_reference` | `VARCHAR(255)` | 专业确认或标准依据引用 |
| `status` | `VARCHAR(20)` | `DRAFT/ENABLED/DISABLED` |
| `config_revision` | `INT` | 显式并发更新修订号 |
| `create_by/update_by` | `BIGINT` | 操作者 |
| `create_time/update_time` | `DATETIME(3)` | MySQL 时间 |

唯一键为 `parameter_code`。定义被候选、模板、映射或版本引用后，不允许物理删除，也不允许修改参数
编码、物理量和标准单位；不兼容变更必须停用旧定义并创建新编码。

### 7.2 `biz_device_parameter_applicability`

标准定义与设备类型通过适用关系关联，唯一键为 `equipment_type_code + definition_id`。适用关系保存：

- `required_flag`：完整快照是否必须有值；
- `formula_readable`：该设备类型下是否允许公式读取；
- `hard_min/hard_max`：确认后的硬限制，违反时禁止进入版本；
- `warning_min/warning_max`：专业建议范围，超出时必须带理由审核；
- `comparison_tolerance`：来源一致性比较容差；未配置时使用标准十进制数值相等；
- `evidence_reference`、`status` 和并发修订号。

专业范围未配置不是零范围，也不阻止人工审核；接口必须显式暴露 `RANGE_NOT_CONFIGURED`。

单位必须引用受控单位目录，包含物理量、稳定单位代码、符号和是否无量纲；外部载荷不能自由创建单位。
允许的单位换算使用有依据、带修订号的线性规则：

```text
normalizedValue = rawValue * scale + offset
```

本期不执行复杂公式换算。原始值和原始单位永远保留；标准化值使用高精度十进制，展示精度不改变存储
事实，超出存储边界时拒绝而不是静默舍入。

### 7.3 `biz_device_parameter_mapping` 与版本

稳定映射保存 `mapping_id`、产品/协议模板身份和当前版本指针；
`biz_device_parameter_mapping_version` 保存：

- `version_no`、`status=DRAFT/ACTIVE/RETIRED`；
- `profile_code/profile_version`；
- 原始 `source_path`；
- `definition_id`；
- `source_unit`、`scale`、`offset`；
- 是否必填；
- 基础版本、复制来源、变更原因、创建与发布时间。

设备参数映射与现有时序指标映射分开，不能用同一条字段映射同时产生时序指标和设备参数。映射发布
只影响后续报文，不重写既有候选；既有候选保留当时的 `mapping_version_id`。

映射中的倍率和偏移必须有厂家或硬件依据。转换后精度超出标准定义且未显式确认舍入规则时拒绝，
不能由 Java 默认截断或四舍五入。

### 7.4 `biz_product_parameter_template`

设备产品草稿可以包含参数模板项：

- `template_parameter_id`；
- `product_id`；
- `definition_id`；
- 原始值、原始单位和标准值；
- 依据说明、必填标志、排序和状态。

模板使用稳定模板身份和显式修订号，可以关联产品、厂家和型号作为适用上下文。已启用或已应用的模板
修订不可原地修改；变化创建新修订。设备绑定或显式重新应用模板时只生成 `TEMPLATE` 候选，不自动
发布，不覆盖设备当前有效参数；模板升级不自动传播到既有设备。

### 7.5 `biz_device_parameter_candidate`

| 字段 | 说明 |
|---|---|
| `candidate_id` | 候选主键 |
| `building_id/equip_id` | 可信设备归属，不能由外部载荷覆盖 |
| `definition_id` | 已映射时填写；未映射时可空 |
| `source_type` | 四类来源之一 |
| `source_reference/source_version` | 设备报告、操作者、导入批次或产品版本引用 |
| `source_slot_key` | 同一逻辑来源的稳定槽位，用于替代旧候选 |
| `source_parameter_key` | 原始字段路径、Excel 参数码或模板项 |
| `raw_value/raw_unit` | 原始来源事实 |
| `normalized_value/standard_unit` | 映射后的标准值和单位 |
| `mapping_version_id` | 使用的映射版本；人工标准录入可空 |
| `observed_at` | 来源声称参数成立或被观测的时间 |
| `validation_status` | `READY/UNMAPPED/INVALID` |
| `validation_reason` | 稳定原因码，不保存堆栈或敏感载荷 |
| `payload_hash` | 脱敏报文或文件行摘要，用于幂等和追溯 |
| `current_flag/supersedes_candidate_id` | 当前候选标记和被替代候选 |
| `first_seen_at/last_seen_at` | 重复相同报告的首次和最近时间 |

相同来源身份、来源版本、参数和内容哈希重复上报时不创建无界历史，只更新 `last_seen_at`。值或来源版本
变化必须创建新候选，并在同一事务内把相同 `source_slot_key` 的旧候选改为非当前。候选内容不允许原地
修改；错误人工录入通过新候选纠正。

冲突只比较各逻辑来源槽位的最新当前 `READY` 候选，不让全部历史候选永久参与冲突。首版来源槽位固定
为“设备 ID + 标准参数定义 ID + 来源类型”。导入批次、操作者、模板版本、设备报告和映射版本都属于
来源证据，不得因为每次提交不同而制造永久并行槽位。新数据校验成功后才替代该槽位旧候选；校验失败
只保存问题事实，不替代上一个 `READY` 候选。来源槽位不表达优先级，也不删除历史候选。

### 7.6 `biz_device_parameter_conflict` 与成员

冲突头保存设备、标准参数、`OPEN/RESOLVED/OBSOLETE`、修订号、解决人、解决时间和原因；成员表保存
参与比较的候选 ID。解决记录只能选择 `READY` 成员，且不删除其他来源事实。

新候选到达后，如果与当前解决依据不同，旧冲突标记 `OBSOLETE` 并创建新的冲突投影；不能静默复用
过去的人工选择。当前有效参数版本继续服务，直到新版本正式发布。

### 7.7 `biz_device_parameter_set`

每台设备最多一个稳定参数集：

| 字段 | 说明 |
|---|---|
| `parameter_set_id` | 参数集主键 |
| `building_id/equip_id` | 设备与建筑，`equip_id` 唯一 |
| `current_timeline_revision_id` | 当前平台认知时间线，可空 |
| `config_revision` | 草稿、提交和并发控制 |
| `create_time/update_time` | MySQL 时间 |

建筑归属由设备档案派生。设备不能通过参数治理跨建筑移动，设备逻辑删除前需要保留参数历史和审计。

### 7.8 `biz_device_parameter_version`

| 字段 | 说明 |
|---|---|
| `version_id/parameter_set_id` | 版本身份 |
| `version_no` | 参数集内严格递增 |
| `status` | `DRAFT/PENDING_REVIEW/PUBLISHED/REJECTED/CANCELLED` |
| `base_version_id` | 创建草稿时复制的完整版本，用于差异和并发检测 |
| `base_timeline_revision_id` | 创建草稿和影响预览时的平台认知基线 |
| `copied_from_version_id` | 复制或回退来源 |
| `change_type` | `INITIAL/UPDATE/ROLLBACK/CLEAR/MIGRATION`；`CLEAR` 只表达一个或多个可选参数被明确清空 |
| `requested_effective_from/to` | 追溯业务区间请求；立即生效时为空 |
| `change_reason/evidence_reference` | 发布、回退、迁移和追溯必填依据 |
| `owner_user_id` | 草稿归属 |
| `create_time/update_time` | 草稿时间；发布后内容不再更新 |

`biz_device_parameter_version_value` 保存版本中的完整值集合：`definition_id`、标准值、标准单位、
选中候选 ID、来源类型、来源引用、来源版本和观测时间。唯一键为 `version_id + definition_id`。

版本只承载完整内容快照，不在原记录上改写有效区间。发布后内容、来源和审核事实都不可修改。
`EFFECTIVE/SUPERSEDED` 是版本相对于指定时间线修订和业务时间的查询状态，不作为可原地更新的版本
事实状态；同一已发布版本可以在旧认知时间线中有效、在当前认知时间线中被追溯修正替代。

### 7.9 双时间发布与时间线

`biz_device_parameter_timeline_revision` 是一次不可变发布事实，保存参数集、严格递增修订号、
`published_at`、发布人、审核请求、发布类型、追溯原因、证据和重算状态。其明细
`biz_device_parameter_timeline_segment` 保存该次发布认知下的完整业务时间线：

- `business_effective_from/business_effective_to`：业务事实有效区间；
- `version_id`：该区间使用的完整参数快照；
- 区间采用左闭右开，同一时间线修订内不得重叠；
- 当前认知选择最新已发布时间线修订；还原历史认知选择 `published_at` 不晚于认知时间的最后修订；
- 时间线修订及其区间一旦发布不可修改，新的追溯修正通过复制并调整完整时间线生成更高修订。

立即生效使用数据库发布时间作为业务生效时间。受控追溯生效允许业务生效时间早于发布时间；如果
目标时间之后已有业务版本边界，默认只替换到下一个既有边界。需要覆盖更多后续区间时必须显式选择
影响范围并重新展示差异。首版不允许业务生效时间晚于发布时间，即不支持未来预约生效。

### 7.10 审核、审计和导入批次

`biz_device_parameter_review_request` 与业务状态分开，保存目标版本、提交修订号、审核快照摘要、
`PENDING/APPROVED/REJECTED/WITHDRAWN`、提交人、审核人和意见。待审核期间参数集草稿冻结。

`biz_device_parameter_audit_log` 保存创建候选、解决冲突、创建/修改草稿、提交、审核、发布、追溯、
回退、导入和迁移等脱敏前后摘要。审计表不对可删除草稿建立级联外键；审计写入失败时对应业务事务
回滚。人工查询和导出进入访问日志；公式读取把参数版本证据写入计算尝试，不为每次读取另写业务审计。

`biz_device_parameter_import_batch` 保存单建筑 Excel 批次、原始文件名的安全显示值、SHA-256、操作者、
行数、状态和错误摘要。文件本体不落业务数据库。行级错误保存行号、字段和稳定错误码，不保存公式、
外部链接或未脱敏整行内容。

## 8. 状态机和核心工作流

### 8.1 候选进入

所有来源统一执行：

1. 解析可信设备身份或建筑内设备编码；
2. 校验设备存在且未删除；
3. 解析设备类型对应的标准参数定义；
4. 保存原始来源、来源版本和观测时间；
5. 按发布映射执行单位转换；
6. 校验类型、精度和已确认边界；
7. 幂等保存候选；
8. 重建对应参数的当前一致性/冲突投影；
9. 不修改当前有效参数版本。

任何来源进入都只是候选。即使设备上报与当前值不同，也不能自动发布或使公式切换版本。

### 8.2 创建和修改参数集草稿

- 没有有效版本时创建 `INITIAL` 草稿；
- 有有效版本时默认复制完整有效版本创建 `UPDATE` 草稿；
- 草稿值必须选择 `READY` 候选；
- 存在冲突时必须保存解决原因；
- 同一设备只允许一个未完成草稿，避免整组版本合并歧义；
- 草稿查看、修改和代办范围由现有 RBAC 能力与建筑范围共同决定，不在设计中编造角色代码；
- 每次变化递增 `config_revision`，请求必须携带期望修订号；
- 待审核时禁止修改、删除或替换候选。

### 8.3 审核和发布

提交后，另一名具备审核权限的人员在一个 MySQL 事务内：

1. 锁定审核请求、参数集、草稿和当前时间线修订；
2. 校验建筑范围、角色和提交修订号；
3. 重新校验全部标准定义仍启用；
4. 重新校验选中候选、单位、精度、边界和冲突解决；
5. 校验 `base_timeline_revision_id` 仍是当前认知基线，影响预览没有过期；
6. 根据立即生效或追溯生效生成新的完整时间线修订；
7. 发布新完整版本并写入业务有效时间和平台发布时间；
8. 更新当前时间线指针和修订号；
9. 完成审核、影响事实和审计；追溯发布同时生成可恢复重算任务。

任一项失败全部回滚。创建人、提交人或回退发起人不能批准同一版本；即使一个账号同时拥有提交和审核
能力也不能绕过职责分离。本期不提供管理员直接发布例外。

### 8.4 平台侧回退

回退复制历史版本的完整值和来源引用，生成更高版本号 `ROLLBACK` 草稿。发布前仍需重新校验定义、
建筑范围和候选是否可追溯；候选已失效不等于历史版本不可复制，但必须保留原候选引用并填写回退原因。

旧历史版本不重新激活，当前有效版本不原地覆盖。回退发布只影响平台，不触发设备操作。

### 8.5 受控追溯生效

追溯生效属于本闭环的正式能力，但不允许来源候选自行追溯，也不允许普通审核流程无提示回填历史：

1. 只有具备独立平台级“追溯生效审批”能力且不是提交人的人员可以批准；
2. 必须填写业务生效时间、追溯原因和证据来源；
3. 发布前生成新的完整时间线预览，展示被拆分或替换的区间、参数差异和后续版本边界；
4. 通过公式参数依赖声明计算受影响的指标、设备和业务时间范围；
5. 发布时写入新的不可变时间线修订，并把已保存的受影响结果投影标记为待重算；
6. 追加创建参数追溯重算任务，历史计算尝试和旧结果不删除、不覆盖；
7. 重算成功后新的结果修订成为当前投影；失败或部分失败时保留旧结果值、新尝试和失败状态；
8. 当前认知查询在重算完成前必须显式返回 `STALE/PENDING_RECALC/RECALC_FAILED`，不能无提示返回旧结果；
9. `DEVICE` 新上报值仍只形成候选，不能凭 `observed_at` 自动追溯生效；
10. 全过程不向设备下发或修改设备参数。

现有公式引擎已经保存追加式公式计算尝试、当前状态投影、公式版本和质量策略证据，也已有可恢复重算
任务。本闭环在这些既有能力上扩展参数版本证据、参数依赖和参数追溯任务。同时必须新增或扩展追加式
结果修订事实，使成功值与 `attemptId` 一起保留；现有“删除成功行再重算”不能用于参数追溯。当前投影
仍可覆盖更新，但只能指向某个不可变结果修订，不能成为唯一结果事实。

### 8.6 旧设备档案接口兼容

旧 `/v1/assets/equipment` 创建和更新接口继续保留原三个字段，后端规则为：

1. 设备详情优先从当前有效参数版本映射回旧字段；
2. 生产切换前没有有效版本时可以回显原扁平列，同时返回附加治理状态 `LEGACY_UNGOVERNED`；
3. 旧客户端提交值与当前显示值相同，视为没有参数变化，不重复创建版本；
4. 实际参数变化返回稳定错误并提示使用参数治理流程，不能转换为候选或直接发布；
5. 参数变化被拒绝时，不影响经过验证的非参数设备档案变更；接口必须避免返回参数修改成功的假象；
6. 新版本发布后同步更新旧列的只读兼容投影；投影不是输入来源，也不参与冲突和公式读取；
7. 定期对账兼容投影与当前生效版本，发现差异时告警且不得反向覆盖权威版本；
8. 首个实现保留旧列作为迁移输入和读取投影，暂不删除数据库列。

旧前端无需修改，但新治理状态、来源、历史和冲突只通过后端 API 提供，旧页面不宣称具备这些管理能力。

## 9. 来源入口设计

### 9.1 设备只读上行

设备参数使用独立标准契约，至少包含：

- `standardVersion`；
- `profileCode/profileVersion`；
- 设备外部身份；
- 幂等 `reportId` 或厂家配置版本；
- `reportedAt/receivedAt`；
- 参数项的标准参数编码、原始字段路径、原始值/单位、标准值/单位和映射版本。

建筑和平台设备 ID 不接受设备声明，必须由已启用身份绑定解析。未知设备继续进入现有待接入流程，不能
直接形成参数候选。身份、认证或报文结构失败时拒绝整份报告；全量/增量语义、单项失败是否允许其他项
进入候选，必须由硬件方契约确认，软件不预设。平台在候选成功持久化后才返回应用处理成功。
Broker PUBACK 只证明 Broker 收到消息，不代表平台候选已经持久化，更不代表参数已经审核生效。

具体厂家字段路径、参数版本含义、Topic/路由和取值范围必须由硬件方提供。没有样例时实现合成契约、
映射框架和拒绝测试，不写任何厂家专用默认路径。

### 9.2 Excel 导入

首版固定一个建筑一个批次，工作表逻辑字段为：

| 字段 | 含义 |
|---|---|
| `equipmentCode` | 建筑内设备编码 |
| `parameterCode` | 对应设备类型的标准参数编码 |
| `value` | 十进制数值，禁止公式单元格 |
| `unit` | 来源单位 |
| `observedAt` | 可空的来源观测时间 |
| `sourceReference` | 可空的台账、厂家文档或批次引用 |

只接受无宏 `.xlsx`。拒绝加密文件、公式单元格、外部链接、重复设备参数行和跨建筑设备。文件大小、
行数和文本长度使用可配置正数上限，实施时通过安全默认和边界测试确认，不在设计中伪造业务阈值。

导入采用“上传校验、返回逐行报告、明确确认导入”两阶段。任一行失败时不允许确认，也不生成任何
候选。全部通过且操作者再次确认后，才在一个事务内生成 `EXCEL` 候选和冲突投影；仍不创建或发布
正式版本。每批只允许一个建筑，权限违规拒绝整批。

### 9.3 产品模板

产品参数模板只能引用对目标设备类型已启用的标准适用关系。已启用或已应用的模板修订不可原地修改；
变化创建新模板修订。设备绑定或显式重新应用模板时创建 `TEMPLATE` 候选，来源引用保存模板身份、
模板修订和产品上下文，不自动发布，也不覆盖设备已有参数；模板升级不自动传播。

### 9.4 人工录入

新治理 API 的人工值先生成 `MANUAL` 候选，再被草稿选用。人工录入必须说明来源或变更原因，不能只
保存一个没有依据的数值；任何账号都不能直接发布自己创建或提交的完整草稿。

## 10. 权限和数据可见性

本设计只冻结业务能力，不编造新角色名称或硬编码 `PLATFORM_ADMIN`。实现时把以下能力映射到现有
RBAC 权限：

- 查看当前参数、历史版本、候选、冲突和脱敏审计；
- 人工录入、Excel 导入、模板应用和草稿编辑；
- 提交、撤回、审核、驳回和发布；
- 发起平台侧回退；
- 审批受控追溯生效；
- 管理全局标准定义、单位、适用关系、映射和模板。

全局标准定义、单位目录和映射使用平台级配置权限；拥有某建筑数据权限不等于可以修改全局定义。
设备候选、版本、导入、审核、回退、追溯和导出全部同时执行动作权限与建筑范围校验。所有设备范围
权限都先从 `equip_id` 查询可信 `building_id`，再调用 `BuildingScopeService`；客户端建筑条件只是过滤
条件，不是授权来源。

职责分离是硬约束：创建人、提交人和回退发起人不能批准同一版本；拥有多项权限也不能绕过。追溯
生效还要求独立的平台级审批能力。本期不提供紧急直发或超级管理员例外。

人工查询和导出进入访问日志，所有状态变化进入不可删改的业务审计。公式读取通过计算尝试保存参数
版本证据，不逐次写业务审计。审计保存年限由项目数据保留制度确认，软件不得自行编造。

## 11. 查询、差异和公式读取

### 11.1 双时间查询

查询服务支持：

- 当前有效完整参数集；
- 指定业务时间、按当前认知有效的完整参数集；
- 指定业务时间和认知时间，还原平台当时已知的完整参数集；
- 参数集历史版本分页；
- 两个版本的新增、删除、值变化、单位变化和来源变化；
- 当前候选一致性、冲突及解决状态；
- 未映射和非法候选问题清单。

查询先按 `knowledgeAt` 选择不晚于该认知时间的最后一个已发布时间线修订，再在该修订内按
`businessEffectiveFrom <= businessAt < businessEffectiveTo` 选择唯一完整版本。`knowledgeAt` 省略时表示
按平台当前已知事实回看；同时提供两项时间才能还原平台当时所知。没有有效版本返回明确
`NO_EFFECTIVE_PARAMETER_VERSION`，不能回退到模板、设备最新上报或旧扁平字段供公式使用。

### 11.2 `DeviceParameterResolver`

公式侧只通过批量解析接口读取：

```text
resolve(equipmentId, businessTime, knowledgeTime, requiredParameterCodes)
→ value + standardUnit + definitionId + versionId
  + timelineRevisionId + sourceType + sourceReference
  + observedAt + businessEffectiveFrom + publishedAt
```

解析规则为：

- 设备、参数定义和版本都必须存在；
- 定义必须启用且 `formula_readable=1`；
- 只读取业务时间和认知时间共同确定的正式版本，不读取候选；
- 缺失、停用、单位不兼容或版本不可用时返回稳定失败原因；
- 一次公式计算批量读取并固定全部版本 ID 和时间线修订 ID，不能在计算中途跨版本；
- 统计区间跨参数版本边界时按有效区间拆分，不能用当前版本覆盖整个区间；
- 公式计算尝试必须持久化实际参数版本来源和公式版本，保证历史可解释。

公式必须显式声明所依赖的标准参数编码；没有能源专家确认的依赖保持为空，现有 COP、泵效率、冷却塔
效率和 AHU 指标不自动读取设计值或额定值。参数依赖声明同时用于追溯发布前的影响分析。

追溯发布扩展现有追加式 `FormulaCalculationAttempt`，为每次计算保存参数版本证据，并让成功结果以
`attemptId` 关联不可变结果修订；扩展现有可恢复重算任务，按设备、受影响指标和业务时间范围将当前
投影标记为陈旧并追加重算，不删除成功事实。旧计算尝试、旧成功值和失败事实均保留。查询当前结果时
必须返回重算状态；还原平台当时所知时按认知时间选择当时已存在的结果修订。

首版解析器使用 MySQL 批量查询，不提前建设全量内存快照或多实例广播。只有实际公式负载证明存在性能
问题时，才基于版本时间线增加缓存和失效机制。

## 12. API 契约边界

管理 API 继续使用 `/v1`、稳定 DTO、`Result<T>` 和 `PageResponse<T>`，不暴露 MyBatis 对象。建议资源：

- `/v1/device-parameter-definitions`：标准定义草稿、启停和查询；
- `/v1/device-parameter-mappings`：映射草稿、版本、发布和回退；
- `/v1/device-parameter-imports`：Excel 批次创建和结果查询；
- `/v1/device-parameters/equipment/{equipmentId}/candidates`：候选和问题查询；
- `/v1/device-parameters/equipment/{equipmentId}/conflicts`：冲突查看和解决；
- `/v1/device-parameters/equipment/{equipmentId}/versions`：草稿、历史、差异和回退；
- `/v1/device-parameters/equipment/{equipmentId}/effective`：按业务时间和认知时间查询有效参数；
- `/v1/device-parameters/equipment/{equipmentId}/retroactive-impact`：追溯时间线和公式影响预览；
- `/v1/device-parameter-reviews`：提交、撤回、批准和拒绝；
- `/v1/device-parameter-recalculations`：参数追溯重算任务状态、失败明细和恢复；
- `/v1/device-parameter-audits`：脱敏审计分页。

设备上行契约不复用管理 API；具体 MQTT/适配器路由由配置承载，不在 URL 或 Java 常量中猜测厂家路径。

响应必须显式返回 `allowedActions`、版本状态、修订号、冲突状态、生效时间和来源摘要。前端不能自行推断
角色权限、版本状态机或冲突结果。

## 13. 校验和稳定错误码

核心校验包括：

1. 设备存在且设备、类型和建筑关系一致；
2. 用户角色和建筑范围满足操作；
3. 标准定义启用、设备类型匹配且具备专业依据；
4. 来源类型只能是四个固定值；
5. 原始单位可以映射到标准单位；
6. 数值满足类型、精度和已确认边界；
7. 映射版本与协议模板匹配；
8. 选中候选属于同一设备和标准定义；
9. 冲突已经显式解决；
10. 完整版本中同一标准参数只有一个值；
11. 基础版本、修订号和当前有效版本未变化；
12. 待审核草稿未被修改；
13. 回退来源属于同一设备；
14. Excel 批次不跨建筑且没有重复行；
15. 公式只读取正式版本和允许公式读取的定义。
16. 创建人、提交人或回退发起人不能批准同一版本；
17. 当前时间线修订内业务有效区间不重叠；
18. 追溯发布具备专用权限、原因、证据、影响预览和重算任务；
19. 认知时间查询不能使用认知时间之后发布的时间线修订。

稳定机器错误码至少包括：

- `DEVICE_PARAMETER_VALIDATION_FAILED`；
- `DEVICE_PARAMETER_DEFINITION_NOT_FOUND`；
- `DEVICE_PARAMETER_MAPPING_NOT_FOUND`；
- `DEVICE_PARAMETER_UNIT_INCOMPATIBLE`；
- `DEVICE_PARAMETER_PRECISION_INVALID`；
- `DEVICE_PARAMETER_VALUE_OUT_OF_RANGE`；
- `DEVICE_PARAMETER_CANDIDATE_CONFLICT`；
- `DEVICE_PARAMETER_DRAFT_CONFLICT`；
- `DEVICE_PARAMETER_VERSION_CONFLICT`；
- `DEVICE_PARAMETER_REVIEW_CONFLICT`；
- `DEVICE_PARAMETER_NO_EFFECTIVE_VERSION`；
- `DEVICE_PARAMETER_RETROACTIVE_APPROVAL_REQUIRED`；
- `DEVICE_PARAMETER_TIMELINE_OVERLAP`；
- `DEVICE_PARAMETER_RECALCULATION_PENDING`；
- `DEVICE_PARAMETER_RECALCULATION_FAILED`；
- `DEVICE_PARAMETER_IMPORT_REJECTED`；
- `DEVICE_PARAMETER_LEGACY_MAPPING_MISSING`；
- `DEVICE_PARAMETER_FORBIDDEN`；
- `DEVICE_PARAMETER_NOT_FOUND`。

HTTP 状态保持：校验失败 `400`，未登录 `401`，越权 `403`，不存在 `404`，状态/引用/并发冲突 `409`。

## 14. 事务、并发和幂等

- 候选单条写入及冲突投影在一个事务内完成；
- Excel 全批候选和冲突投影全部成功或全部回滚；
- 设备参数报告以设备身份、报告 ID/来源版本和内容哈希幂等；
- 草稿使用 `config_revision` 显式乐观并发，审核提交保存修订号；
- 审核批准、回退和追溯发布锁定参数集及当前时间线修订；
- 新版本、完整时间线修订、当前指针、审核、影响事实和审计同事务提交；
- 追溯重算任务使用与时间线修订关联的稳定幂等键，可失败恢复且不能重复作废同一结果；
- 旧设备档案字段实际参数变化必须在进入设备档案写事务前拒绝；
- 外部报文解析失败不写部分候选；
- 审计失败不允许业务发布成功；
- 不使用数据库级联删除正式版本、候选来源或审计事实。

## 15. 既有扁平字段迁移

现有 `rated_capacity/rated_power/design_cop` 是可变当前值，不是版本历史。除非另有可靠审计事实，否则
只能迁移执行时快照，不能推断过去每次变更。

迁移按以下顺序执行：

1. 创建标准定义、映射、候选、参数集、版本、审核、审计和导入表；
2. 扫描 `biz_equipment.rated_capacity/rated_power/design_cop` 非空值；
3. 无损保存设备、旧字段名、原始值、已有单位证据、原表引用、批次和迁移时间；
4. `LEGACY_MIGRATION` 只作为一次性迁移证据，不冒充 `MANUAL`，也不增加为日常第五种来源槽位；
5. 单位、物理含义或零值语义不明确时标记 `PENDING_MAPPING/PENDING_PROFESSIONAL_REVIEW`；
6. 只有设备类型存在已确认且唯一的旧字段到标准定义映射时才归一化并生成初始完整版本草稿；
7. 初始草稿必须经过批量审核后才能形成 `V1`，迁移脚本不得自动发布专业有效版本；
8. 有可靠历史证据时可以按受控追溯流程确定业务生效时间；没有证据时只从审核发布时间生效；
9. 切换后设备详情优先读取有效治理版本并同步只读兼容投影；未切换设备继续标记
   `LEGACY_UNGOVERNED`，不能供新公式静默读取；
10. 保留旧列作为原始迁移证据和读取投影，首版不删除；
11. 迁移工具支持预演、批量问题报告、安全重跑、失败恢复和迁移前后数量核对，不重复创建事实。

现有种子数据中某些“额定容量”值可能与额定功率相同，不能据此推断容量含义。专业映射未确认前必须
保持待确认状态，不能为了迁移通过而自动创建参数定义或宣布历史数据业务有效。空值保持缺失；零值
是实际值还是未填写必须由专业依据确认。

## 16. 验证与验收标准

### 16.1 自动化验证

#### 数据模型与迁移

- MySQL 迁移契约覆盖表、索引、唯一键、外键和可重跑检查；
- H2 测试结构覆盖参数治理表和旧字段兼容；
- 已确认旧字段映射只生成待审核初始版本，不能自动生效；
- 未确认“容量”映射只形成待确认迁移事实；
- 迁移预演、失败恢复和重跑不重复候选、版本或审计。

#### 来源、映射和冲突

- 四类来源均能生成候选；
- 相同标准值形成一致状态，不同值形成冲突；
- 没有固定来源优先级；
- 映射缺失、单位不兼容、转换失败、存储精度溢出和违反专业硬限制均不能发布；
- 超出专业建议范围需要理由和审核，专业范围未配置必须显式提示但不伪装成硬失败；
- 映射升级不重写历史候选；
- 重复设备报告幂等，变化报告创建新候选。

#### Excel

- 正常固定模板整批生成候选；
- 任一错误行让整批不生成候选；
- 校验通过但未经明确确认的批次不生成候选；
- 跨建筑、重复行、公式单元格、外部链接、加密或宏文件被拒绝；
- 文件和行级错误不泄露敏感内容。

#### 状态、事务和并发

- 具备提交能力的人员提交、另一名具备审核能力的人员发布完整通过；
- 创建人、提交人和回退发起人自审均被拒绝；
- 版本发布原子切换，任一步失败全部回滚；
- 待审核草稿冻结；
- 过期修订号和过期基础版本返回 `409`；
- 回退创建更高版本，不修改历史；
- 必填参数缺失禁止发布，可选参数明确未配置并保存原因；
- 审计失败使业务事务回滚。

#### 双时间、追溯与重算

- 立即生效和受控追溯都生成不可变时间线修订；
- 当前认知时间线区间不重叠，追溯插入默认截止到下一个既有业务边界；
- `businessTime + knowledgeTime` 能分别得到当前已知事实和平台当时所知；
- 追溯发布缺少专用权限、原因、证据或影响预览时被拒绝；
- 设备候选不能凭观测时间自行追溯发布；
- 公式尝试保存参数版本和公式版本，跨版本统计按区间拆分；
- 受影响旧结果保留并标记待重算，新尝试追加写入；
- 重算成功、失败、部分失败、幂等重试和恢复路径均可追溯；
- 重算未完成或失败时，当前口径查询显式返回陈旧或失败状态。

#### 权限和建筑范围

- 各动作按照现有 RBAC 权限与建筑范围组合校验；
- 建筑数据权限不能用于修改全局标准定义和映射；
- 追溯审批必须具备独立平台级能力；
- 客户端伪造建筑 ID 不能越过设备真实归属。

#### 查询、公式和兼容

- 当前认知、指定业务时间和指定认知时间命中正确时间线与版本区间；
- 差异正确区分新增、删除、值和来源变化；
- 公式解析器只返回正式、允许读取的参数并携带版本来源；
- 缺少有效版本不回退到模板、候选或旧列；
- 现有四项公式结果和输入保持不变；
- 旧设备页面契约字段保持兼容；
- 旧接口实际参数变化被明确拒绝，非参数档案字段仍可按既有规则更新；
- 当前生效版本与旧字段只读投影保持一致，投影不能反向覆盖权威版本。

#### 测试隔离

- 普通测试使用 H2、Mock、Stub 和合成 Excel/报文；
- 不连接真实 MySQL、MQTT Broker、厂家设备、现场网络或外部文件服务；
- 自动化结果不得描述为真实设备或现场验收。

### 16.2 业务验收

1. 能源专家确认首批参数定义、设备类型适用范围、标准单位、精度和边界；
2. 硬件方提供至少一个设备参数报文样例、字段路径、单位和版本说明；
3. 四类来源可形成可查询候选，且不会自动生效；
4. 同值来源显示一致，不同值显示冲突且无默认优先级；
5. 具备提交能力的人员能够选择候选形成完整草稿并提交；
6. 另一名具备审核能力的人员批准后整组参数立即或受控追溯生效，发布事实不可修改；
7. 查询能够区分当前已知事实与平台当时所知，并返回来源和版本差异；
8. 平台回退生成更高版本，不向设备发送命令；
9. 旧设备页面不修改仍可读取三个兼容字段，但实际参数修改被后端明确拒绝；
10. 未声明参数依赖的现有公式结果不变化；
11. 追溯发布展示影响范围，公式结果保留参数版本证据，作废和重算失败均可追溯；
12. 目标 MySQL 8 迁移、真实 Excel 和厂家报文联调单独记录证据；
13. 独立验收和用户批准与代码合并保持分离。

## 17. 实施范围与顺序

本候选后续作为一个独立实现 PR 完成后端软件闭环，不与空间语义、计量分摊或前端改造混合。建议顺序：

1. MySQL 迁移、全局标准定义、适用关系、候选、冲突、参数集版本、双时间线、审核和审计模型；
2. 标准定义和映射治理 Service/API；
3. 四类来源候选入口、Excel 导入和参数报文适配；
4. 参数集草稿、职责分离审核、立即/受控追溯发布、差异和回退；
5. 建筑范围、角色、错误码、事务、并发和幂等；
6. 双时间查询、`DeviceParameterResolver`、公式参数依赖和参数版本证据；
7. 追溯影响预览、结果陈旧标记、既有重算任务扩展和失败恢复；
8. 旧设备档案只读兼容、既有扁平字段无损迁移和受控切换；
9. 定向测试、完整后端验证、前端兼容验证和状态文档同步。

实现 PR 必须保持一个完整闭环，不能交付“只有表没有发布状态机”“只有导入没有冲突处理”或“只有
版本 API 没有查询/公式读取”的半完成状态。具体厂家映射和专业参数定义没有输入时可以保持未映射和
拒绝路径，但不能用合成规则伪装现场能力。

## 18. 已确认事项与未解决边界

### 18.1 已确认

- 参数治理是独立于空间语义的后端闭环；
- 标准参数代码全局唯一，设备类型通过独立适用关系声明必填性、边界、容差和公式可读性；
- 厂家、型号属于设备/产品档案上下文，不进入参数版本；设备生命周期另行治理；
- 首版只治理可精确保存的十进制数值，存储精度与展示精度分离；
- 参数集以单台设备完整快照为版本粒度；
- 来源固定为 `DEVICE/MANUAL/EXCEL/TEMPLATE`，不设置自动优先级；
- 冲突必须显式选择和记录原因后才能发布；
- 提交人与审核人严格分离，不设置管理员直接发布例外；
- 支持批准后立即生效和受控追溯生效，首版不做未来预约生效；
- 参数版本使用业务有效时间与平台发布时间双时间模型；
- 追溯发布必须展示影响范围、保存参数和公式版本证据、追加作废与可恢复重算事实；
- 查询同时支持“按当前已知事实回看过去”和“还原平台当时所知”；
- 历史版本不可修改，回退创建更高版本；
- 旧前端不修改，旧接口实际参数变化由后端拒绝，旧字段降为只读兼容投影；
- 设备参数使用独立只读上行契约，不混入时序指标；
- Excel 限定单建筑，经过整批校验和明确确认后整批形成候选，永不直接发布；
- 产品模板只产生候选；
- 查询和公式只读取正式有效版本；
- 现有公式不自动使用设计 COP、额定功率或容量；
- 遗留字段可以提前无损迁移，但必须经过专业确认和审核才能形成生效 `V1`；
- 不向设备下发参数，不实现设备端修改、校验或回滚；
- 受控追溯、公式血缘和历史重算属于同一个参数治理实现 PR；空间语义另用独立 PR。
